## 修法

### 1. `loadChatHistory(paperId)` 改造（處理新 dict 格式 + in_progress）

- 接收 17-2 後端回傳：可能是舊 list 或新 dict `{messages, in_progress}`
- `Array.isArray(data) ? data : (data.messages || [])` 提取 history
- `in_progress` 只在 dict 路徑且非 null 才取
- empty 條件：`!history.length && !in_progress` → 顯示「針對文件提問」
- history 渲染邏輯不變（既有 user/ai msg 渲染保留）
- **in_progress 處理**：
  - 不重複 render user query（已在 history 內、17-1 後端進入時 DB append）
  - 只 render 一個 `.msg-ai` + partial + 閃爍 cursor（`.cursor-blink`）
  - 呼叫 `attachToStream(paperId, aiMsg, partial)` 接續 broker

### 2. `attachToStream(paperId, aiMsg, alreadyRenderedPartial)`（新函式）

```js
const es = new EventSource(`/api/papers/${paperId}/chat/attach`);
currentEventSource = es;

let accumulated = alreadyRenderedPartial || '';
let replayCharsSeen = 0;
const baselineLen = (alreadyRenderedPartial || '').length;
```

**replay chunk 處理（§replay chunk 處理說明）**：
- 17-2 broker 對 late attach 先回放 `chunks_buffer`、每個 chunk 標 `replay: true`
- 前端 loadChatHistory 已 render `in_progress.partial`（含當下 buffer 內容）
- attach 後 broker 仍會回放整個 buffer——已 render 部分要 skip 避免雙重 render
- 累計 `replayCharsSeen`：
  - 累計到 `baselineLen` 內 → 完全 skip（在 partial 內）
  - 累計超出 → 取溢出字串 append（保險：broker 回放與 baseline 對齊度可能略差）
- 非 replay chunk → 正常 accumulated += sentence

**渲染**：
- 每次 sentence 進來：removeCursor → re-render markdown → appendCursor → scroll bottom
- `chunk.done`：removeCursor + 最終 render（無 cursor）+ render grounding_sources + `es.close()`
- `chunk.error`：失敗訊息已在 sentence 內、不另處理
- `es.onerror`：log warning + close + removeCursor（保留已收 partial）

## replay chunk 處理說明（renderedFromReplay 邏輯）

**情境**：
1. paper A 提問 → 前端 sendMessage POST `/chat`、broker 開始累積 chunks_buffer（已有 partial = `"他擔任 OLED 顯示驅動 IC"`）
2. sendMessage 在 background 持續讀 reader、寫到 aiMsg DOM
3. 切到 paper B → 前端 currentPaperId='B'、舊 aiMsg DOM 被 17-1b 清掉（messages.innerHTML='' 在 loadPaper 開頭）；但 sendMessage 的 reader 仍在背景跑、寫到已被清掉的 DOM（無害）
4. 切回 paper A → loadChatHistory:
   - 從 `GET /chat/history` 拿到 `{messages: [user query], in_progress: {query, partial: "他擔任 OLED 顯示驅動 IC"}}`
   - render history（user query）+ 新 aiMsg + partial 內容
   - **呼叫 attachToStream(paperId, aiMsg, "他擔任 OLED 顯示驅動 IC")**
5. broker 對 late attach 先回放 chunks_buffer：
   - replay chunk 1: `"他擔任"`（replay=true）
   - replay chunk 2: `" OLED 顯示驅動 IC"`（replay=true）
   - 之後新 chunks: `"，主要負責..."`（replay=false）
6. 前端 attachToStream:
   - 收 replay chunk 1：`replayCharsSeen += 3` → ≤ 18（baseline）→ skip
   - 收 replay chunk 2：`replayCharsSeen += 17` → 20 > 18 → overflow="`IC`" 之後的字（理論上應對齊到 0、本 case 無溢出）
   - 收正常 chunk：accumulated += `"，主要負責..."`，render markdown

關鍵：`replayCharsSeen` 是「broker 回放字串的累積長度」、`baselineLen` 是「前端 loadChatHistory 拿到 partial 時的字數」——只要 broker 在 `pump_to_client` 內回放完整 buffer + 前端 baseline 來自同一個 broker state（同一次 `GET /chat/history`），兩者**理論上完美對齊**。`baselineLen - before` 用於極端情況（broker buffer 後續被截斷、或 chunks 沒按字邊界）的保險。
