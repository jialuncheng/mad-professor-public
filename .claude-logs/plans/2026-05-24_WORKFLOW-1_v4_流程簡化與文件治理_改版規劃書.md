## §6 P1-2 落地：Active Baton 改「baton 資料夾」方案

### §6.1 baron 提議的核心邏輯

> 「直接開一個資料夾、放置交接文件、每次必讀、沒有要交接的就讀不到東西」

```

- **下一步動作**：產執行計劃 + 拆 commit
- **預期工作流類別**：BE-Refactor
- **特殊注意事項**：<可選、若有則寫>
- **建立時間**：2026-05-24 14:30
```

### §6.4 強制讀取機制（在 CLAUDE_CODE_ENTRY 加入）

```markdown
CLAUDE_CODE_ENTRY.md §1 強制讀檔順序（v4 修正）：
1. CLAUDE_CODE_ENTRY.md 自身（包含本入口）
2. .claude-logs/baton/*.md（必讀、若無 active 檔則跳過、READ.md 也讀）  ← v4 新增
3. .claude-logs/ref/WORKFLOW_SOP.md
4. .claude-logs/ref/PROJECT_PROGRESS_CONTROL_FRAMEWORK.md
5. .claude-logs/TODO.md
6. 任務專屬改版規劃書 / 執行計劃
7. 對應 SOP
```

### §6.5 快取影響分析

| 設計 | 快取影響 |
|---|---|
| 放 CLAUDE_CODE_ENTRY.md（Antigravity 原提議） | 🔴 每次交接更新都破壞穩定文件前綴 |
| **放 baton/ 資料夾（baron 修正）** | 🟢 baton/ 內檔案本身就是動態、不混入穩定文件、不破壞主前綴 |

**好處**：
- 平時無交接 → baton/ 只有 README.md（永久檔、可快取）
- 有交接 → 額外讀 1 個短檔（~10 行）、cost 極低
- 任務完成 → 刪除 active 檔、恢復「無交接」狀態
- 完美隔離動態 / 靜態內容

| **BE-Hotfix** | < 10 行 + 純 `*.py` + 無 schema/API 簽名 | WORKFLOW_SOP §4.4 | _hotfix | bug fix / NPE |

### §7.2 判定流程圖

```
收到 baron 提示詞
       ↓
[判定 1] 改動規模 < 10 行 且 無 schema/API 簽名影響？
       ↓ Yes                              ↓ No
   進入 hotfix                        進入 refactor
       ↓                                  ↓
[判定 2-hotfix] 主要影響範圍是？     [判定 2-refactor] 主要影響範圍是？
   ↓                                       ↓
   ├── static/* → FE-Hotfix               ├── static/* / design/* → FE-Refactor
   ├── *.py → BE-Hotfix                   ├── *.py / tests/* → BE-Refactor
   └── .claude-logs/*.md / design/docs/   └── .claude-logs/*.md / design/docs/
       → 走 DOC 流程（簡化版 hotfix）       *.md → DOC-Refactor（v4 新增）
```

### §7.3 DOC-Refactor 涵蓋範圍

| 範圍 | 範例 |
|---|---|
| `.claude-logs/` 框架 / SOP 改動 | PROJECT_PROGRESS_CONTROL_FRAMEWORK.md 加 §10 |
| `.claude-logs/` template 改動 | template_plan.md 加 §0 |
| `design/docs/` 設計規範改動 | components.md 加 §11.3 |
| 跨多份文件的流程治理改動 | WORKFLOW-1 自身 |

### §7.4 DOC-Hotfix 為何不獨立第六類

- DOC 類改動通常牽動多份文件、單一文件 < 10 行也屬於 refactor 範疇
- 若真有「單一 typo 修正」場景、可走 BE-Hotfix（檢視是否有對應業務代碼）或不走 hotfix（直接走 DOC-Refactor 最小 commit）
