# 2026-05-23_QUEUE-1_文件佇列與優先權管控_plan.md

本文件為 **Mad Professor 專案優先權協同讓路調度機制 (QUEUE-1)** 的落地實作計畫。本計畫嚴格看齊 `PROJECT_PROGRESS_CONTROL_FRAMEWORK.md` 規範，建立純後端運作的文件優先權避讓管控機制。

---

## 1. TL;DR (技術與問題概述)

* **問題**：系統同時處理多個文件時，可能會有大型書籍佔用 CPU 與 LLM API 配額，導致使用者剛上傳的小型履歷/簡報需要等待數分鐘，嚴重降低 UX。
* **根因**：目前 `web_server.py` 在 `confirm_type` 後直接透過 FastAPI `background_tasks` 非同步呼叫 `PipelineCore.process`，多個任務直接競爭執行緒與 API 資源，無優先權排隊與併發控制機制。
* **解法**：在 `PipelineCore` 內部引入全域執行緒安全的任務註冊表，以 **「階段級協同讓路 (Cooperative Stage Throttling)」** 機制實作。大型文件在進入下一個處理階段前，若偵測到有小型文件（如履歷）正在處理，會自動 `time.sleep(2)` 避讓，直到高優先權任務完成。
* **協同優化（Synergy with OPTIMIZE-1）**：**優先權判定將以被 `OPTIMIZE-1` 無損壓縮優化後的磁碟檔案大小為基準**。許多使用者產生 PDF 時未設定適當參數導致檔案異常膨脹，透過先優化、再判定，能反映文件真正的實體複雜度，避免誤判。
* **受影響範圍**：僅限後端 `pipeline_core.py` 內部階段流程，前台與 API 無須任何改動，對用戶 100% 透明。
* **相依性**：相依於 `OPTIMIZE-1` 在上傳階段落地的無損優化。

## 3. 觀察到的問題與證據

* **證據 1**：在 `web_server.py:752` 行，`background_tasks.add_task` 只是交給 FastAPI 背景執行，一旦多個大文件同時處理，會在 `loop.run_in_executor` 中開闢多個 Thread 同時跑。
* **證據 2**：`pipeline_core.py` 的管線在 `process` 開始後，便會一路同步執行到結束，中間無任何檢查或資源調度的機制，大檔案（如書籍，動輒跑數分鐘）與小檔案（如履歷，通常 20 秒完成）會同時爭搶 Gemini API，容易觸發 `429 Rate Limit`，且小檔案被大檔案卡住。

---

## 4. 設計方案

* **實作細節**：
  - 在 `PipelineCore` 中加入靜態變數：`_active_tasks = {}` 與 `_registry_lock = threading.Lock()`。
  - 判定優先權（檔案大小皆以經 `OPTIMIZE-1` 無損壓縮優化後的磁碟實體大小為準）：
    - High (1): `_doc_type in ('resume', 'slides')` 或優化後檔案大小 $< 2\text{ MB}$。
    - Low (3): 優化後檔案大小 $> 10\text{ MB}$ 或 `_doc_type == 'book'`。
    - Medium (2): 其他。
  - 在 `PipelineCore.process` 入口處調用 `self.register_task(task_key, priority)`，並用 `try...finally` 包裹階段循環，在 `finally` 區間調用 `self.unregister_task(task_key)`。
  - 於階段循環 `while i < len(self.stages):` 頂端，檢查 `self.should_yield(priority)`：
    ```python
    while self.should_yield(priority):
        time.sleep(2)
        # 額外確認任務是否已被取消（刪除）
        with self._registry_lock:
            if task_key not in self._active_tasks:
                return output_paths
    ```

## 5. 變動風險與相容性評估

* **破壞性變更 (Breaking Changes)**：無。
* **衝擊評估**：本設計不需要任何資料庫 schema 變動或 API 簽名修改。當單一用戶依序處理大、小文件時，後端執行緒會自行協調 CPU/API 資源。即便 `time.sleep` 在 `run_in_executor` 執行緒中會使該執行緒暫時阻塞，但在 Python 多執行緒環境下會自動釋放 GIL，不影響整體事件迴圈的非同步響應，也不影響其他 HTTP request。
