## 2. 觀察到的問題與證據

### 問題 #1：跨文獻查詢被「單篇」鎖死

- **證據**：`AI_professor_chat.py:43` `process_query_stream(query, visible_content, paper_id, ...)` 只接受單一 `paper_id`；`rag_retriever.retrieve_with_context` 只查單一 vector store
- **影響**：用戶輸入「光合作用」想跨 3 篇植物論文比較、現在只能逐篇切換 paper、效率極低
- **跟 baron 需求 3 對齊**：TODO.md L161 `RAG-1 跨文件查詢（baron 需求 3 / Commit 15 plan Q7）` — RAG-1 的原始定義就是跨文件

### 問題 #2：translated_abstract 後端永遠是空、Phase 1 R1 子項 F fallback 永遠走英文

- **證據**：`metadata_extractor._ALL_FIELDS` 無 `translated_abstract`；Phase 1 R1 ship 的 fallback `abstractZh = v('translated_abstract') || abstractEn` 中、`v('translated_abstract')` 永遠回 None
- **影響**：用戶切到中文模式、toolbar 摘要永遠顯示英文（fallback）、雙語體驗破碎；Phase 1 R1 子項 F 的 fallback 設計是「未來向」、實際 user-facing 受益不足
- **修法**：Hashtag Backend Plan §1 已規範、加進 `_ALL_FIELDS` + pipeline_core translate 階段寫入

### 問題 #3：用戶不知道對話框支援 `#tag`

- **證據**：grep 證實 chat-input placeholder 為「輸入問題（Ctrl+Enter 送出）...」、無任何 hashtag 提示
- **影響**：即使 Phase 2 後端 ship 了 hashtag 路由、用戶不知道怎麼觸發；功能像「隱藏」一樣
- **baron 需求**：對話框加提示文字「輸入 #標籤（逗號分隔）可跨文獻搜尋」、文案可調整

### 問題 #4：純文字 `#hr 問題` 體驗破碎、需要互動回饋

- **證據**：Phase 1 R2 ship 的 tag-modal 是「彈窗式」編輯體驗、用戶在 chat-input 直接打 `#hr` 沒有任何視覺回饋（autocomplete 不存在）
- **baron 需求**：類似 Claude 對話框輸入 `/skill` 的行為——
  - 用戶輸入 `#` → 偵測現有 user_tags、顯示 autocomplete dropdown
  - 用戶點選 / 按 Enter → 該 `#tag` 變為**藍色不可編輯 token**（一整塊、用 backspace 一次刪掉）
  - 多個 tag 可逗號分隔（依 hint 規範）

```python
def list_paper_uuids_by_tag(session, owner_id: int, tag: str) -> list:
    """掃該 owner 所有 status='done' 的 Paper、回 metadata_json.user_tags 含 tag 的 paper_uuid 列表。

    依 .claude-logs/ref/2026-05-23_RAG-1_Hashtag_Backend_Implementation_Plan.md §2 L43-44
    + RAG-1 Phase 1 ship 的 _normalize_tag（單一真理源、tag 比對也走 normalize）

    Args:
        tag: 用戶輸入的 tag（會走 _normalize_tag 標準化、確保 case-insensitive 比對）

    Returns:
        list[str]: paper_uuid 清單（含此 tag 的 paper）
    """
    normalized = _normalize_tag(tag)
    if not normalized:
        return []

    rows = session.query(Paper).filter_by(
        owner_id=owner_id, status='done'
    ).all()
    result = []
    for p in rows:
        if not p.metadata_json:
            continue
        try:
            meta = json.loads(p.metadata_json)
            if not isinstance(meta, dict):
                continue
            user_tags = meta.get("user_tags", []) or []
            # Phase 1 _normalize_tag 保證寫入時已 lowercase、此處直接比對
            if normalized in user_tags:
                result.append(p.paper_uuid)
        except (json.JSONDecodeError, TypeError):
            continue
    return result
```

**設計重點**：
- 用 `_normalize_tag` 為 tag 比對基準（單一真理源、跟寫入路徑對齊）
- 過濾 `status='done'`（避免處理中的 paper）
- `metadata_json` 解析 corrupt graceful（continue）

#### 3.2.2 `paper_manager.parse_query_hashtag(owner_id, query) -> tuple[Optional[str], str]`

依 Hashtag Plan §2 L45-47、**長標籤優先排序**防誤攔：

```python
def parse_query_hashtag(session, owner_id: int, query: str) -> tuple:
    """從 query 開頭解析 #tag、回 (tag, cleaned_query)。

    依 Hashtag Plan §2 L45-47：
    - 從該 owner 所有 user_tags 蒐集 distinct tag 集合
    - 依字串長度由長到短排序匹配（防 #complex 誤攔截 #complex_system）
    - 若 query 開頭為 `#<tag> `、回 (normalized_tag, 剩餘 cleaned query)
    - 否則回 (None, query 原樣)

    Returns:
        (tag_or_None, cleaned_query)
    """
    if not query or not query.startswith("#"):
        return (None, query)

    # 蒐集該 owner 所有 distinct user_tags
    all_tags = set()
    rows = session.query(Paper).filter_by(
        owner_id=owner_id, status='done'
    ).all()
    for p in rows:
        if not p.metadata_json:
            continue
        try:
            meta = json.loads(p.metadata_json)
            if isinstance(meta, dict):
                for t in (meta.get("user_tags", []) or []):
                    if isinstance(t, str):
                        all_tags.add(t)
        except (json.JSONDecodeError, TypeError):
            continue

    # 長度由長到短排序、防 #complex 攔 #complex_system
    sorted_tags = sorted(all_tags, key=len, reverse=True)

    q_lower = query[1:]  # 去掉開頭 #
    for tag in sorted_tags:
        # 比對 `<tag> ` 開頭（含空白分隔）
        if q_lower.lower().startswith(tag + " "):
            cleaned = q_lower[len(tag):].lstrip()
            return (tag, cleaned)
        elif q_lower.lower() == tag:
            # query 就是 `#tag`、無後續問題
            return (tag, "")

    return (None, query)
```

**設計重點**：
- 排序防禦：`sorted(..., key=len, reverse=True)` 確保 `#complex_system` 優先匹配
- query 比對用 `q_lower.lower()`（user 可能輸入 `#HR`、`_normalize_tag` 寫入時是 `hr`、所以比對時也 lower）
- 兩個情境：`#tag<空白>剩餘問題` / `#tag<EOL>`

#### 3.2.3 `rag_retriever.retrieve_multi_with_context(owner_id, query, paper_ids, top_k=7) -> str`

依 Hashtag Plan §2 L49-54：

```python
def retrieve_multi_with_context(
    self,
    owner_id: int,
    query: str,
    paper_ids: list,
    top_k: int = 7,
) -> str:
    """跨 paper FAISS 全域 Merge-Sort top-k 檢索。

    依 .claude-logs/ref/2026-05-23_RAG-1_Hashtag_Backend_Implementation_Plan.md §2 L49-54

    流程:
    1. 對每個 paper_id 個別呼叫 retrieve_with_context（或內部 vs 操作）
    2. 收集所有 (score, chunk, paper_id) candidate
    3. 全域降序排序、取前 top_k
    4. 格式化為「## 摘自文件《paper_title》」段落式 context、便於 LLM 引用

    Returns:
        統合 RAG context 字串
    """
    all_candidates = []  # list of (score, chunk_text, paper_id, paper_title)
    for pid in paper_ids:
        # 取單 paper 的 chunks + scores（內部呼叫既有 retrieve_with_context 的低層 API）
        vs = self._load_vector_store(owner_id, pid)
        if vs is None:
            continue
        docs_and_scores = vs.similarity_search_with_score(query, k=top_k)
        paper_title = self._get_paper_title(owner_id, pid)
        for doc, score in docs_and_scores:
            # 注意 FAISS MAX_INNER_PRODUCT 已是 cosine similarity（依 MODEL-1+2 L2 normalize）
            all_candidates.append((score, doc.page_content, pid, paper_title))

    # 全域降序排序、取 top_k
    all_candidates.sort(key=lambda x: x[0], reverse=True)
    top_chunks = all_candidates[:top_k]

    # 格式化為段落式 context
    sections = []
    for score, chunk, pid, title in top_chunks:
        sections.append(
            f"## 摘自文件《{title}》\n"
            f"{chunk}\n"
        )
    return "\n".join(sections)
```

**設計重點**：
- 全域 Merge-Sort 防 prompt 爆炸（Hashtag Plan Open Question 已定 N=7）
- 每個 chunk 標明來源 paper title、讓 LLM 引用時不混淆
- 內部 `_load_vector_store` / `_get_paper_title` 依現況決定是用既有 API 還是新建小 helper
- **L2 normalize 後 score 已是 cosine similarity**（依 MODEL-1+2 B2 ship）、降序排序即可

#### 3.2.4 `AI_professor_chat.process_query_stream` 入口分流

依 Hashtag Plan §2 L56-61：

```python
def process_query_stream(self, query, visible_content=None, paper_id=None, ...):
    # ...既有 owner_id / session 處理不動...

    # P2-2 新增：parse hashtag
    with db.SessionLocal() as s:
        tag, cleaned_query = paper_manager.parse_query_hashtag(s, owner_id, query)

    if tag:
        with db.SessionLocal() as s:
            tagged_uuids = paper_manager.list_paper_uuids_by_tag(s, owner_id, tag)
        if len(tagged_uuids) == 1:
            # 單篇符合：沿用既有單篇路徑（傳 cleaned_query 給 LLM、避免 # 干擾）
            paper_id = tagged_uuids[0]
            query = cleaned_query
        elif len(tagged_uuids) > 1:
            # 多篇符合：走 multi 檢索、合併 context
            context = self.retriever.retrieve_multi_with_context(
                owner_id, cleaned_query, tagged_uuids, top_k=7
            )
            # 直接用 context、不走既有 _get_rag_context 單篇邏輯
            return self._stream_with_context(cleaned_query, context, ...)
        else:
            # 標籤無對應 paper：回友善訊息、不阻塞
            yield {"type": "warning", "message": f"找不到含 #{tag} 的文獻"}
            return

    # 沒 hashtag、走既有單篇路徑
    # ...既有邏輯不動...
```

**設計重點**：
- 單篇 hashtag 仍走既有 `_get_rag_context` 路徑（不重複實作）
- 多篇 hashtag 走新 `retrieve_multi_with_context`、context 直接餵 LLM
- `cleaned_query` 傳給 LLM 而非含 `#` 的原 query、避免決策器誤判
- 無對應 paper 回 warning、不阻塞 stream

#### 3.3.5 補強防護設計（v2 新增、4 點 contenteditable 健壯性）

> **背景**：P2-3 將 `<textarea>` 改為 `<div contenteditable="true">` 是高風險 DOM 重構（§4 已標🔴 高），原 plan 僅敘述高層 JS 邏輯、未涵蓋瀏覽器相容性與既有提交鏈的細節。本節 4 點全數**採納並列入 P2-3 必做工作清單**，理由如下。

##### 補強 #1：contenteditable div 的 CSS Placeholder 規則 ✅ **採納**

**評估理由**：`<div contenteditable>` 沒有原生 `placeholder` 屬性、§3.3.2 已用 `data-placeholder` 但**只是資料屬性、不會自動顯示**。沒有對應 CSS `:empty::before` 規則時、用戶看到的是空白方塊、體驗破碎。這是業界標準寫法、零成本必補。

**落地位置**：`static/index.html` chat-input 區塊 CSS

```css
/* §3.3.5-#1：contenteditable placeholder */
#chat-input:empty::before {
    content: attr(data-placeholder);
    color: var(--color-text-subtle);
    pointer-events: none;          /* 防誤觸 click */
    display: block;                /* contenteditable 排版正確 */
}
/* focus 時也保留（直到開始輸入才隱藏） */
#chat-input:empty:focus::before {
    opacity: 0.5;
}
```

**注意**：`:empty` 在用戶輸入第一個字後自動失效、placeholder 消失。

##### 補強 #2：Disabled 狀態視覺契約 ✅ **採納**

**評估理由**：既有 `<textarea id="chat-input" disabled>`（L1296）在 paper 未載入時為灰色禁用態。改成 `<div contenteditable>` 後、`disabled` 屬性對 div **無效**、需改用 `contenteditable="false"` + CSS 顯式對齊禁用樣式、否則用戶會在 paper 未載入時看到「看起來可輸入但實際不收輸入」的破碎 UX。

**落地位置**：`static/index.html` chat-input CSS + JS 切換邏輯

```css
/* §3.3.5-#2：disabled 視覺契約 */
#chat-input[contenteditable="false"] {
    background: var(--color-surface);          /* Kahn/Mies 表面色 */
    color: var(--color-text-subtle);
    cursor: not-allowed;
    user-select: none;
}
#chat-input[contenteditable="false"]:empty::before {
    opacity: 0.4;                              /* 禁用態 placeholder 更淡 */
}
```

**JS 對齊**：既有所有 `chatInput.disabled = true/false` 全部改為 `chatInput.setAttribute('contenteditable', 'true'/'false')`（含 paper 載入完成 / 切換語言 / 切換 paper 三條路徑）。

##### 補強 #3：全 codebase `.value` / keydown handler grep 替換 ✅ **採納（升等為 P2-3 必做工作項）**

**評估理由**：§4 風險表已標🔴 高、§3.3.2 也提及「序列化 textContent」、但**沒明列為工作項**——v1 plan 漏點。實際上既有 `static/index.html` 內 chat-input 的 `.value` 提取、`textarea` 專屬 attr / event、Ctrl+Enter 監聽都需逐一檢查、漏一個就 break submit。升為 §3.3.5 顯式工作項：

**P2-3 落地時必做 grep 清單**：

```bash
# 全 codebase grep（不限 static/index.html、其他 .html / .js / .py 也要掃）
grep -rn "chat-input" static/ design/ web_server.py | grep -v "tag-input\|file-input"
grep -rn "chatInput\." static/ | grep -E "\.value|\.disabled|\.placeholder"
grep -rn "getElementById('chat-input')" static/
grep -rn "querySelector.*chat-input" static/
grep -rn "addEventListener.*keydown" static/    # 確認 Ctrl+Enter handler 兼容 contenteditable
```

**逐項替換規則**：

| 原 textarea 寫法 | contenteditable 替換 |
|---|---|
| `chatInput.value` | `chatInput.textContent.trim()` |
| `chatInput.value = ''` | `chatInput.textContent = ''`（清空、保留 placeholder） |
| `chatInput.disabled = true` | `chatInput.setAttribute('contenteditable', 'false')` |
| `chatInput.setAttribute('placeholder', ...)` | `chatInput.setAttribute('data-placeholder', ...)` |
| `keydown` 取 `e.target.value` | `e.target.textContent` |
| Ctrl+Enter handler 內 reset `textarea` height | 移除（contenteditable 自然撐高） |

**P2-3 commit message 必須列出本次掃過的所有檔案 + 行號**、避免漏點。

##### 補強 #4：Autocomplete Dropdown 定位錨點 ✅ **採納**

**評估理由**：§3.3.2 JS 邏輯第 3 步「渲染 .hashtag-popup-item、定位於 cursor 下方」過於模糊——若用 `getBoundingClientRect()` 取 cursor 座標、會撞到三個邊界問題：
1. cursor 接近視窗右側、dropdown 溢出畫面
2. cursor 接近視窗底部、dropdown 被瀏覽器邊界截斷
3. 多行輸入時 cursor 跳行、dropdown 位置突變、視覺抖動

**解法**：定位錨點綁 `#chat-input-area` 容器、固定「正上方」展開、跟 Claude `/skill` 行為完全對齊：

```css
/* §3.3.5-#4：autocomplete 定位錨點 */
#chat-input-area {
    position: relative;                /* dropdown absolute 的定位上下文 */
}
#hashtag-autocomplete {
    position: absolute;
    bottom: 100%;                      /* 永遠在 input 正上方 */
    left: var(--space-3);              /* 跟 input padding 對齊 */
    right: var(--space-3);
    max-height: 240px;                 /* 限制高度、超過捲動 */
    overflow-y: auto;
    margin-bottom: var(--space-2);     /* 跟 input 留間隙 */
    box-shadow: var(--shadow-popup);   /* 浮起效果、避免融進背景 */
    z-index: 100;
}
```

**好處**：
- 永遠整齊懸浮、不抖動、不溢出
- 即使 chat-input 多行展開、dropdown 仍貼齊頂部、視覺穩定
- 對齊 Claude `/skill`、components.md §3 `.ctx-popup` 規範

**design 規範補充**：§11.2 Hashtag Token 內加「Autocomplete 定位」小節、註明「綁容器、非綁 cursor」。
