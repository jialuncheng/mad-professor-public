# 2026-05-19 Phase 4.6：pipeline 三問題修復（domain/doc_type 入庫 + MinerU 圖檔路徑解耦）

修改業務邏輯。scope 嚴格限於 `pipeline_core.py` / `paper_manager.py` /
`processor/pdf_processor.py`；未動 metadata_extractor / web_server / ai_core /
rag_retriever / models.py（domain/doc_type 欄位 Phase 1 已存在，無 schema 變動）。

## 問題 1：upsert_paper 未寫 domain / doc_type 進 DB

### 來源（pipeline_core，已查證）
- `domain`：`output_paths.get('_domain')`（detect_domain stage 寫入；失敗時為 `''`）
- `doc_type`：`output_paths.get('_confirmed_doc_type', 'academic')`（web_server
  run_pipeline 以 `existing_paths={'_confirmed_doc_type': doc_type}` 帶入）

### 修改
- `paper_manager.upsert_paper`：簽名加 `domain: Optional[str]=None`、
  `doc_type: Optional[str]=None`（選參、放最後，既有呼叫端零改動即相容）。
  `domain_val=(domain or '').strip() or None`、`doc_type_val` 同。
  - create：`Paper(... domain=domain_val, doc_type=doc_type_val ...)`
  - update：`if domain_val: p.domain=...`、`if doc_type_val: p.doc_type=...`
    （空值不覆蓋——避免單次 detect_domain 失敗清掉先前正確 domain，與既有
    title/translated_title 的 `if x:` 鏡寫策略一致）
- `pipeline_core` upsert 呼叫點：加
  `domain=output_paths.get('_domain')`、
  `doc_type=output_paths.get('_confirmed_doc_type', 'academic')`。

### 驗證（臨時 sqlite，實測通過）
- CREATE：`domain='AI Infrastructure' doc_type='academic'` 正確入庫。
- UPDATE：傳 `domain=''` → 既有 domain 保留；`doc_type='news'` → 更新。
- NOARGS（舊呼叫路徑 `upsert_paper(out, uid, uuid, fp)`）：domain/doc_type
  皆 None、不崩——向後相容。

### scope 決策（誠實標註）
未把 domain/doc_type 加進 `_to_dict`（API 回應）。需求僅「寫進 DB / 驗證
DB 有值」，未要求前端曝露；加入屬未請求的 API 行為變更，故不做（最小變更）。
若日後前端要顯示，再於 `_to_dict` 補 2 行即可（欄位已入庫）。

## 問題 2：pdf_processor MinerU 圖檔搬移路徑與本機 paper_name 耦合

### 查證結論（重要——與 summary 描述有出入，誠實標註）
追原始碼鏈：`web_server.upload_paper` 一律存
`paper_dir/"original.pdf"`（web_server.py:276）→ `_pdf_path` →
`run_pipeline` → `pipeline.process(pdf_path=…/original.pdf)` →
`_stage_pdf_to_md` → `pdf_processor.process(str(pdf_path))`。
故 `paper_name = pdf_path.stem` **在現行碼路徑下已恆為 `"original"`**
（≠ summary 所稱 `800-vdc-…`；`800-vdc-…` 是 `paper_id`/`paper_dir`，非
`pdf_path.stem`）。MinerU API 以 `files=(pdf_path.name="original.pdf")` 送出，
MinerU 端 ZIP 內目錄即 `original/`。

→ **現行 `_copy_images` 實際已產生正確路徑 `…/original/auto/images/`。**
本次修改的真正價值是**把這層隱性耦合顯式化、可設定化**（解除「碰巧因
web_server 存成 original.pdf 才對」的脆弱耦合），非修復一個現存路徑錯誤。
**若 OrcStack 上 image_caption 仍失敗、`_images_info.md` 仍空，根因不在此**
（應查：MinerU server 端命名是否真為上傳 stem、scp 連線/權限、task_id、
MINERU_OUTPUT_DIR 掛載），需端到端實測定位。

### 修改
- `PDFProcessor.__init__`：加
  `self.MINERU_PAPER_NAME = os.getenv("MINERU_PAPER_NAME", "original")`。
- `_copy_images`：簽名由 `(self, paper_name, output_dir, task_id=None)` 改
  `(self, output_dir, task_id=None)`（`paper_name` 在此函式已全數被
  `self.MINERU_PAPER_NAME` 取代 → 移除死參數，非保留未用參數）。4 處 src
  構造（遠端 task_id / 遠端 ls-t fallback / 本地 task_id / 本地最新目錄
  fallback）一律改用 `mineru_name = self.MINERU_PAPER_NAME`。
- `process()`：`self._copy_images(output_dir, task_id)`（配合新簽名）。
- **延伸（超出字面「只動 _copy_images」，同根因，已標註）**：
  `process()` 解 ZIP 取 markdown 的 `tmp_md` 路徑
  （`_tmp/{X}/auto/{X}.md`）兩段 X 同屬 **MinerU 端 ZIP 內命名**，亦改用
  `mineru_name`；落地檔 `markdown_path = output_dir/f"{paper_name}.md"`
  **保留 `paper_name`**（純本機輸出檔名，不影響下游路徑預期）。理由：
  env 覆寫 `MINERU_PAPER_NAME` 的目的是「防上游改名」，若只改
  `_copy_images` 而 ZIP 解壓仍用 `pdf_path.stem`，覆寫時會「圖片對、
  markdown 抽取壞」——留下潛在不一致即等於明知留 bug。本機 vs MinerU 端
  命名已嚴格區分：`paper_name`=本機輸出檔名（line 65/75）；
  `mineru_name`=MinerU 端 ZIP/目錄名（解壓 + 圖檔複製）。

### grep 確認
`processor/pdf_processor.py` 改後 `paper_name` 僅剩 line 65（定義）、
line 75（本機 md 檔名）——MinerU 端用法已全部切到 `mineru_name`。
