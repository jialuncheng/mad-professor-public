## score logging 後續使用說明

收集足夠數據後（建議跑 1-2 週實際 query）、用以下指令分析 score 分布：

```bash
# 1. 所有 retrieve 行
grep "\[retrieve\]" logs/*.log > /tmp/retrieve_scores.log

# 2. 抽出 scores 陣列、轉成 CSV
grep -oP "scores=\[\K[^\]]+" /tmp/retrieve_scores.log | tr ',' '\n' | tr -d ' '

# 3. 統計 top-1 score 分布（看門檻 0.22 是否仍合理）
grep -oP "scores=\[\K[\d.]+" /tmp/retrieve_scores.log | \
  awk '{print $1}' | sort -n | \
  awk 'BEGIN{c=0;sum=0} {arr[c++]=$1; sum+=$1} END{
    print "n=" c, "mean=" sum/c
    print "p10=" arr[int(c*0.1)], "p50=" arr[int(c*0.5)], "p90=" arr[int(c*0.9)]
  }'

# 4. 判斷：
#    若 p90 仍 ~0.25 → 閾值 0.22 OK
#    若大量正確 hit 落到 < 0.22 → 降閾值到 0.20 / 0.18
#    若大量無關 hit 過 0.22 → 升閾值或加 reranking
```

未來 15-1 chunk 結構優化落地後、score 分布**會變**（Context 前綴讓相關 query top score 預期上升），那時依新分布重新校準閾值。
