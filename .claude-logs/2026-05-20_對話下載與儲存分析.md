## 結論先講
1. **AI 對話寫入 DB 只靠前端**：`POST /api/papers/{id}/chat` 與
   `ai_core.query_stream` **都不寫 DB**；對話僅透過前端 `sendMessage` 在
   SSE `done` 後呼叫 `saveChatHistory()` → `POST /chat/history` 持久化。
2. **下載 endpoint 讀寫對齊**（同一張 `conversations` 表、同一 schema）：
   寫讀無錯位。
3. **「loading 進度」最可能成因 = 端點回 404**（該 paper 在 `conversations`
   表為空），瀏覽器把 `window.location.href` 導航到 JSON 錯誤頁；spinner 是
   navigation phase 的短暫指示，之後 SPA 被換成 `{"detail":"沒有對話紀錄"}`
   純 JSON 頁——使用者觀感像「載入完成卻沒下載」。**並非後端 stuck**。
4. **MD 從未存檔**：每次匯出皆**請求時即時組合**。baron 印象中的「舊版存
   MD 檔」應為誤記；Phase 1.6 前是 `chat_history.json`（非 MD），1.6 後遷
   DB，**從來沒有 MD 落地**。

## A. AI 對話儲存機制

### A-1 儲存位置
| 載體 | 位置 |
|---|---|
| **DB 表** | `conversations`（SQLite） |
| Schema（models.py:146–170）| `id` PK / `paper_id` FK→`papers.id` (CASCADE) / `user_id` FK→`users.id` / `session_id` String(64) nullable / `role` String(20) `'user'\|'assistant'` / `content` Text / `grounding_sources` JSON nullable / `tokens_used` Int nullable / `created_at` DateTime server_default now |
| Index | `ix_conversations_paper_id (paper_id, id)` |
| 對話 MD / 檔案 | **無**。MD 為下載時即時組裝（web_server.py:543–552），不落地 |

### A-2 寫入時機（**只在前端**）
| 步驟 | 位置 | 行為 |
|---|---|---|
| sendMessage 入口 | `static/index.html` ~2132 | 顯示 user/ai 泡泡、開 SSE |
| 收 SSE `chunk.sentence` | ~2128–2134 | 累積文字、即時 `marked.parse` 進 `.msg-ai.innerHTML` |
| 收 SSE `chunk.done` | ~2185–2192 | `isStreaming=false`、寫 `dataset.groundingSources`、`renderSources`、**`await saveChatHistory(currentPaperId)`** |
| saveChatHistory | ~2107–2130 | 掃 DOM `.msg-user/.msg-ai` 組 history 陣列 → `POST /api/papers/{id}/chat/history`（fetch；**`catch(e){}` 靜默吞錯**） |
| Server save_chat_history | web_server.py:461–469 → paper_manager:350–370 | `_ensure_db` → **整包覆寫**：`DELETE FROM conversations WHERE paper_id=...` → 逐筆 `INSERT` |

### A-3 後端 `POST /api/papers/{id}/chat` 是否同步寫 DB？
**否**。endpoint（web_server.py:423–444）只把 `ai_core.query_stream` 的 yield 包成 SSE 回傳。`grep -nE "Conversation|save_chat|conversations|SessionLocal|paper_manager|db\." ai_core.py` → 0 行。`ai_core` 完全不碰 DB。

### A-4 寫入失敗/中斷的情境（DB 會留空）
1. SSE 在 `done:true` 之前**異常中斷**（網路斷、reader throw）。新 SSE try/catch
   只設 `isStreaming=false`，**不呼叫 saveChatHistory**。
2. `ai_core` 例外路徑（ai_core.py:83）仍 yield `done:true` → 正常會觸發
   saveChatHistory；但若 chunk 流被 transport 截斷則同 1。
3. saveChatHistory POST 本身失敗（後端 401/500/網路）→ 業務碼 `catch(e){}`
   **靜默吞錯**（~2129），DB 不寫、使用者無感。
4. 使用者**關閉/重整分頁**於 done 與 saveChatHistory 完成之間。
5. AI 完成但使用者立即點 export（罕見人為時序差）。

### A-5 「整包覆寫」副作用
每次 saveChatHistory 都 `DELETE` 該 paper **全部**舊對話再 re-insert。
若**前端 DOM 訊息不完整就送出 POST**（例如使用者捲離後 DOM 被截、或
loadChatHistory 尚未把舊訊息渲染好就被 saveChatHistory 蓋掉）→ 既有對話
會被截短甚至清空。**目前未發現此時序問題的觸發路徑**，但 schema 風險仍在。

## B. 下載對話 MD 完整呼叫鏈

### B-1 前端
`static/index.html` ~2039:
```
document.getElementById('export-btn').onclick = () => {
  if (!currentPaperId) return;
  window.location.href = `/api/papers/${currentPaperId}/chat/export`;
};
```
- 機制為**整頁導航**（非 `fetch` + `Blob`）。瀏覽器 tab spinner 開始；
- 200 + `Content-Disposition: attachment` → 多數瀏覽器**取消頁面導航、
  觸發下載**（SPA 保留）。
- 非 200 / 無 attachment → 瀏覽器**完成導航**，把 SPA 換成回應內容（如
  JSON 錯誤頁）。

### B-2 後端 `GET /api/papers/{paper_id}/chat/export`（web_server.py:530–559）
```
db_id = paper_manager.get_paper_db_id(current_user.id, paper_id)
history = paper_manager.load_chat_history(db_id, current_user.id) if db_id else []
if not history:
    raise HTTPException(status_code=404, detail="沒有對話紀錄")

paper = paper_manager.get_paper(OUTPUT_DIR, current_user.id, paper_id)
title = (paper.get('translated_title') or paper.get('title') or paper_id) if paper else paper_id

lines = [f"# {title} — 對話紀錄", ""]
for msg in history:
    if msg['role'] == 'user':  lines.append(f"**問：** {msg['content']}")
    else:                       lines.append(f"**答：**\n\n{msg['content']}")
    lines.append("")
md_content = "\n".join(lines)

return Response(
    content=md_content.encode('utf-8'),
    media_type="text/markdown",
    headers={"Content-Disposition": f"attachment; filename={paper_id}_chat.md"},
)
```
- `get_paper_db_id`（paper_manager:315）：`SELECT papers.id WHERE owner_id=? AND paper_uuid=?`，回 `Paper.id` 或 `None`。
- `load_chat_history`（paper_manager:325）：`SELECT * FROM conversations WHERE paper_id=? ORDER BY id`，純讀，毫秒級。
- Response：`text/markdown` + `Content-Disposition: attachment; filename={paper_uuid}_chat.md`（檔名直接內嵌 paper_uuid；中文 paper_uuid 經 sanitize 不會出現，但**未做 RFC 5987 編碼**——目前 paper_uuid 因 `sanitize_paper_id` 已限 ASCII，沒事；未來若放寬會踩雷）。

### B-3 預期 UX
- 有對話 → 200 + attachment → 瀏覽器自動下載 `{paper_uuid}_chat.md`，SPA 不動。
- 無對話 → **404 + JSON `{"detail":"沒有對話紀錄"}`** → 瀏覽器完成導航、
  SPA 被替換為 JSON 純文字頁，需 Back 按鈕才能回 SPA。

## C. 「loading 進度」現象解釋

### C-1 路徑追蹤（端到端）
1. `window.location.href = /api/.../chat/export` → 瀏覽器發 GET。
2. 後端走 B-2 流程；對單筆 SELECT，TTFB ms 級，**不會 stuck**。
3. 兩種收尾：
   - 有對話 → 200 attachment → 下載觸發、SPA 保留、spinner 停。**正常**。
   - 無對話 → 404 → 瀏覽器完成導航到 JSON 錯誤頁、spinner 停、SPA 不在。
     **這是 baron 看到的「跑 loading 但沒結果」**——spinner 確實停了，但
     畫面換成了不像 SPA 的 JSON 純文字，產生「卡住沒下載」的觀感。

### C-2 不是 stuck 的證據
- `load_chat_history` 為純 `SELECT … ORDER BY id`，無 join、無 N+1、無外部 IO。
- `get_paper_db_id` 為單行 PK 查詢。
- 無 timeout / 無死迴圈 / 無 SSE / 無背景任務。
- 若真有「永遠不返回」，是 DB 鎖（極不可能在唯一 SELECT 上）或 SessionMiddleware
  上下文異常——這些都會在其他 endpoint 同樣顯現，**未見**。

### C-3 為何感覺像 spinner
`window.location.href` 是**整頁導航**：瀏覽器在請求發出到回應完成之間都
顯示 tab spinner（包括 200 attachment 的下載觸發前）。對 404 的情況，
spinner 結束時 SPA 已被換掉，畫面是 JSON——對使用者像是「載入完了但啥
都沒發生」。在 SSE/長請求等場景才會出現「持續 spinner」，本端點不會。

### C-4 其他可能（不太像，但列出）
- Session 過期 → auth_guard 對 `/api/*` 回 401 JSON → 同 404 觀感（導航到 JSON）。
- 瀏覽器把 `text/markdown` 當文字檔內聯顯示（罕見，現代瀏覽器有 attachment 即下載）。
- `Content-Disposition` 缺引號或值有 LWS 被某些舊瀏覽器忽略 → 內聯顯示 MD 文字而非下載。本端點無此問題（paper_uuid 已 sanitized）。

## E. 對齊性分析

### E-1 寫讀對齊（同源同 schema）
- 寫：frontend `saveChatHistory` → `POST /chat/history` → `paper_manager.save_chat_history` → **`conversations` 表（整包覆寫）**
- 讀（export）：`paper_manager.load_chat_history` → 同 `conversations` 表（ORDER BY id）
- 讀（loadChatHistory，loadPaper 時讀回 UI）：同 endpoint `GET /chat/history` → 同表
- **資料源完全一致、欄位完全一致**。export 不會「找不到對應 MD」——它根本
  不找 MD，而是從同一張表組 MD。

### E-2 真正 bug 點：寫入是否真的發生
- export 對齊面零問題；**404 的真因是 DB 該 paper 的 `conversations` 為空**。
- DB 為空的最大可能來源（依風險高低）：
  1. saveChatHistory POST 失敗被 `catch(e){}` 靜默吞（網路/auth/500）。
  2. SSE 在 `done` 前中斷（新 try/catch 跳過 saveChatHistory）。
  3. 使用者沒實際送過任何訊息（首次開 paper 直接點 export）。
  4. 瀏覽器/分頁在 done→POST 之間關閉。
  5. paper 尚未 pipeline 完成（無 Paper row → db_id=None → 同樣 404）；
     但 enableChat 只在 done 後跑、export-btn 才 visible，正常流程不會走此路。

### E-3 副生風險（非本次 bug，但同源）
- 「整包覆寫」設計使得**任何一次成功 POST 即把當前 DOM 視為 ground truth
  覆蓋 DB**。若 DOM 不完整（罕見競態）即會清空既有對話。觀察 saveChatHistory
  與 loadChatHistory 都讀同 DOM，理論上未出現此 race，但屬潛在設計脆弱性。

## F. 修法選項（**不執行**，待 baron 裁示）

### F-1 最小修補：把 404 改成「下載空 MD」或前端攔截 404
**a. 後端把空 history 改為 200 + 空訊息 MD**
- 改 `web_server.py` export endpoint：移除 `raise 404`，改回 `# {title} — 對話紀錄\n\n_尚無對話紀錄_\n` 200 attachment。
- 影響檔：`web_server.py`（單一 endpoint，~5 行）。
- 工程量：**小（< 15 分）**。
- 風險：UX 上會下載一份空檔，但**不會把 SPA 換掉**；spinner 自然結束、Save 對話框出現。
- 副益：消除 baron 觀察的「loading 後沒下載」假象。

**b. 後端維持 404，但前端改用 fetch 預檢、404 顯示提示而非導航**
- 改 `static/index.html` 業務 JS 約 5–8 行：`fetch /chat/export`，
  `if (res.ok) → blob 觸發下載；else customAlert('尚無對話紀錄')`。
- 影響檔：`static/index.html`。
- 工程量：**小（15–30 分）**。
- 風險：低；純前端、不動後端。
- 副益：404 不再導航離開 SPA；可順便觀察其他 HTTP 失敗類型。

### F-2 中度：export 改 fetch + Blob，永久消除導航副作用
- 把 `window.location.href = …` 換成 `fetch + response.blob() + URL.createObjectURL + <a download>.click()`。
- 任何失敗（404/401/500）都用 `customAlert` 通知、SPA 不離開。
- 影響檔：`static/index.html` 業務 JS（~10–15 行）。
- 工程量：**中（30–60 分）**。
- 風險：低；需處理 cleanup (`URL.revokeObjectURL`) 與 attachment header 解析（從 `Content-Disposition` 取檔名）。
- 副益：所有 export 失敗類型統一以 modal 呈現。

### F-3 大改：把 AI 對話寫入移到後端，不再依賴前端 POST
- 在 `POST /api/papers/{id}/chat` 內，於 SSE 累積期間或 done 時，直接寫
  `conversations` 表（user 訊息 + accumulated assistant 訊息 + grounding）。
- 廢除（或保留為 fallback）前端 `saveChatHistory`。
- 影響檔：`web_server.py`（chat endpoint）、可能 `paper_manager.py`（加
  `append_message` API）、`ai_core.py`（不需改，仍只 yield）。
- 工程量：**中-大（60–120 分）**。
- 設計問題需釐清：
  - 串流中斷的 partial assistant 訊息要不要落地？
  - 「整包覆寫」改「append」要不要保留？或兩段並存（append 即時、整包覆寫
    保留給 future「編輯/刪除對話」）？
  - 既有 frontend `saveChatHistory` 怎麼處理（避免雙寫衝突）？
- 風險：較大；牽涉資料完整性、SSE error 場景、與既有「整包覆寫」相容性。
- 副益：對話**確定**被持久化，使用者關分頁/網路問題不再丟訊息；
  export 永遠有資料可下載。

### F-4 推薦（純分析者意見，仍待 baron）
- **立即**：F-1b（前端攔截 404）或 F-1a（後端回空檔）——15–30 分修掉 UX
  假象，止住「loading stuck」誤判。
- **下一輪**：F-2（fetch + Blob）統一錯誤處理，使 SPA 永不離開。
- **戰略**：F-3 視「對話遺失發生率」決定。若實際丟訊息少，先不動；若高，
  排程實作（同步另強化前端 saveChatHistory 的錯誤回報，至少改為非靜默）。
