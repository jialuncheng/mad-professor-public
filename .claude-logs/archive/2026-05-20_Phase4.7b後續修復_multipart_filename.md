# 2026-05-20 Phase 4.7b 後續修復：multipart filename 強制 original.pdf

最小修補，只動 `processor/pdf_processor.py` 一處。未動 web_server /
paper_manager / metadata_extractor / pipeline_core / _copy_images /
markdown 搬移 / _tmp 解壓 / data 參數。

## 真因
Phase 4.7b 後本機 PDF 存成 `{paper_id}.pdf`。POST MinerU 時
`files={"files": (pdf_path.name, f, ...)}` → multipart filename =
`{paper_id}.pdf`，MinerU 據此命名 ZIP 內子目錄與 .md。但程式查找
hardcode `_tmp/{MINERU_PAPER_NAME}/auto/{MINERU_PAPER_NAME}.md`
（MINERU_PAPER_NAME 預設 "original"）→ 路徑不符，`from_exists=False`
→ 後續 `read_text` ENOENT。800-vdc（短檔名）能跑只是同一條路徑、檔名
短沒踩到不一致；本修法對長短檔名皆正確（800-vdc 不回歸）。

## 修法（與 spec 的小差異，已標註）
spec 要求硬編 `"original.pdf"`。實際改用
`mineru_upload_name = f"{self.MINERU_PAPER_NAME}.pdf"`——因程式碼查找端
本就用 `self.MINERU_PAPER_NAME`（既有常數，env 可覆寫），綁同一常數可
保證「上傳 filename」與「ZIP 查找路徑」對任何 MINERU_PAPER_NAME 值都
恆一致（硬編字面則 env 一旦覆寫即再次破裂）。預設值 = "original" →
送出即 `original.pdf`，與 spec 預期行為等價，且更穩健。符合 spec 自述
之「由 MINERU_PAPER_NAME env 約定」精神。`with open(...)` 區塊不變，
fileobj 在 with 內有效；三元組 `(filename, fileobj, mimetype)` 標準寫法。
