# 2026-05-20 Phase 0 — `ai_core._generating_lock` 真實使用情況分析

純讀分析。未動任何檔案、未 commit。

> **核心發現先講**：鎖**真正保護**的是 `self.ai_chat`（AIProfessorChat 單例）
> 的 mutable 實例狀態（`conversation_history` / `last_grounding_sources` /
> `current_paper_id` / `current_paper_data`），**不是** LLM API 限流。
> 因此**單純把鎖改 per-user 不夠**——`ai_chat` 仍是 process-wide singleton，
> Phase 2 多帳號上線時跨 user 的 conversation_history 仍會互相污染。
> **完整解需要 per-user `AIProfessorChat` 實例**搭配 per-user lock；
> 工程量比 baron 預估的 60–90 分大（**真實 90–150 分**）。

---

## A. 真實使用情況

### A-1 鎖的定義
- 位置：`ai_core.py:19`
- 形態：**`threading.Lock()`**（標準同步原語，非 `asyncio.Lock`、非 RLock）
- scope：`self._generating_lock`（**instance attribute**，依附於 `AICore` 實例）
- 實例數：web_server 啟動時建 1 個 module-level `ai_core = None` 後 init 1 次
  → **process-wide singleton**

### A-2 全 repo 使用點（grep 確認）
| 檔 : 行 | code | context |
|---|---|---|
| `ai_core.py:18` | `self.is_generating = False` | flag 初始化 |
| `ai_core.py:19` | `self._generating_lock = threading.Lock()` | 鎖建構 |
| `ai_core.py:59` | `if not self._generating_lock.acquire(blocking=False): yield 'busy'; return` | `query_stream` 入口 **非阻塞**搶鎖；失敗 → 立刻吐「目前有其他對話正在生成中，請稍候再試」回 SSE，return |
| `ai_core.py:64` | `self.is_generating = True` | 鎖到手後設 flag |
| `ai_core.py:79` | `if not self.is_generating: break` | streaming for-loop 每句檢查 flag（cancel 信號）|
| `ai_core.py:94` | `self.is_generating = False`（finally 內）| flag 重置 |
| `ai_core.py:95` | `self._generating_lock.release()`（finally 內）| 鎖釋放 |
| `ai_core.py:99` | `def cancel(self): self.is_generating = False` | cancel 方法 |

**全 repo 無其他位置碰 `_generating_lock` 或 `is_generating`**（grep 0 命中
其他 .py，`_deprecated/` 內有 `is_generating_response` 但屬已棄用 AI_manager
路徑、本架構不用）。

### A-3 配套狀態
- **`is_generating`**：純 `bool`，非 `threading.Event`。
- **`cancel()` 方法**：line 99 存在，**但 `grep ai_core.cancel()` 全 repo
  0 caller**。是死碼。
- **Cancel 不依賴 lock 狀態**：cancel() 純粹改 bool flag；streaming 迴圈
  每生成一句檢查 flag → break out → finally 釋放。即使 cancel 也走正常
  finally 釋放鎖、無 deadlock 風險。
- **無第二把鎖**：`web_server.tasks_lock` 與 `_login_lock` 為各自獨立用途，
  與 generating lock 互不影響。

### A-4 鎖**真正**保護什麼？

鎖位於 `query_stream`，緊接 `is_generating=True` 與
`self.ai_chat.process_query_stream(...)` 呼叫。**真正受保護的共享狀態**：

| 狀態 | 位置 | 是否在 query_stream 期間被讀/寫 | race risk |
|---|---|---|---|
| `self.ai_chat.conversation_history` (`AIProfessorChat`) | 處理流程內 `append(user query)` + `process_query_stream` 結束時 `append(assistant reply)` + 超 10 truncate | ✓ 大量寫 | **高** — 兩流交錯會混訊息、長度倒置、truncate 邏輯卡 |
| `self.ai_chat.last_grounding_sources` | streaming 後寫入 | ✓ 寫 | **中** — 後流覆蓋前流的 sources，造成 SSE 末段 `done` 帶錯的 grounding |
| `self.ai_chat.current_paper_id` / `current_paper_data` | `set_paper_context` 寫；`process_query_stream` 讀 | 寫端為 `set_paper_context`（dead code），讀端為 process_query_stream（但本架構走 `paper_data=` 參數路徑，不依賴 self.current_*）| **低**（dead code 寫端不觸發）|
| `self.is_generating` | flag 自身 | True/False 切換 | 低（atomic）|
| `self._paper_cache` (`AICore`) | query_stream 內**讀**；load_paper_cache **寫**；remove_paper **刪** | query 期間僅讀；寫由 paper_manager preload / load_paper_resources 觸發（不同 thread）| **低-中** — Python dict 讀寫不 atomic，**但 GIL 保護單一 get/set；** 跨 query 與 load 並發理論上可能 mid-resize race，實務罕見 |

**鎖的功能 ≈「serialize 整個 query_stream 入口」**，效果是：
- 同時間最多 1 個 chat streaming
- 第 2 個並發 chat 收到 busy 提示、不會排隊（`acquire(blocking=False)`）

**並非**為了：
- ❌ LLM API 限流（`google-genai` client 對並發無限制；Gemini API rate
  limit 是 per-key per-minute、不是 per-process）
- ❌ 保護 `_paper_cache`（讀只用 .get；GIL 即足，無需鎖）
- ❌ DB 一致性（DB SessionLocal 各 with-block 各自隔離）

## B. 為什麼有這個鎖（git history）

**Commit `61cea4b` 「AICore 加入單一生成鎖，避免並發對話交錯」**（早期 Phase）

從 commit message 推斷設計意圖：
- 「並發對話**交錯**」：明確指 `AIProfessorChat.conversation_history` 與
  `last_grounding_sources` 在兩個並行 chat 下會交錯寫入。
- 「**單一**生成鎖」：刻意設成 process 單鎖（當時是 Qt 桌面版單 user，
  process 鎖即等於「使用者鎖」）。
- 設計時假設 = **單一使用者偶爾誤觸雙開 tab**。多帳號從未在當時 scope 內。

→ **鎖的真實目的至今仍存在**（保護 `ai_chat` 實例狀態），**不是多餘**。
但**鎖的粒度（process-wide）已過時**（多帳號需 per-user）。

## C. 改造選項

### C-1 per-user lock（只改 lock，不動 ai_chat）
```
self._generating_locks: Dict[int, threading.Lock] = {}
self._is_generating: Dict[int, bool] = {}
```
- 每次 acquire 前 `setdefault(owner_id, threading.Lock())`
- **問題**：`self.ai_chat` 仍是 process singleton → A 與 B 並發時，雖各自
  搶到自己 lock，但 `self.ai_chat.conversation_history` 仍**共用**——
  A 寫 user query "今天天氣"、B 寫 user query "AI 是什麼"，兩者 append
  到同一 list → 互相污染。
- 此方案**只解 1/3 問題**（解除互相阻塞，但**沒解互相污染**）。
- 工程量：30 分。
- 風險：**high false sense of security**——測單帳號雙 tab 沒問題、上 Phase 2
  立即發現對話內容互相混入。
- 鎖回收：user_id 集合是 small bounded set（< 100），永不釋放鎖物件無洩漏
  風險；可不做 GC。

### C-2 per-paper lock `(owner_id, paper_id)`
- 同 C-1 問題：ai_chat 仍 singleton；conversation_history 仍互相污染。
- 工程量：35 分。
- 風險：同 C-1，**且粒度過細**（單一 user 通常一次只 chat 一篇）。
- **不建議**。

### C-3 直接拿掉鎖
- B 節證明鎖保護的 race 至今仍存在 → 拿掉會讓**單帳號雙 tab** 也出現交錯。
- commit `61cea4b` 反例。
- **不建議**。

### C-4 Semaphore（限全機並發數）
```
self._gen_semaphore = threading.Semaphore(value=4)
```
- 解決「LLM API 限流」場景——**但 A-4 已證明不是這個 race**。
- 不解決 `ai_chat` 共用狀態污染。
- **不建議**。

### C-5（**推薦**）per-user lock **＋** per-user `AIProfessorChat` 實例
```
self._chats: Dict[int, AIProfessorChat] = {}
self._generating_locks: Dict[int, threading.Lock] = {}

def _ensure_chat(self, owner_id):
    if owner_id not in self._chats:
        chat = AIProfessorChat()
        chat.retriever = self.retriever  # 共用 retriever（其本身已 owner-aware）
        self._chats[owner_id] = chat
        self._generating_locks[owner_id] = threading.Lock()
    return self._chats[owner_id], self._generating_locks[owner_id]
```
- `query_stream(owner_id, ...)` 改為：取 user 自己的 chat + lock，呼叫該
  chat 的 `process_query_stream`。
- 每個 user 有獨立 `conversation_history`、`last_grounding_sources`。
- lock 仍存在（保護**同一 user 的雙 tab 並發**）。
- 工程量：**90–120 分**（不只是改 lock，是把 ai_chat 也 per-user 化）。
- 風險：低-中。
- 回收策略：跟 lock 一樣，bounded user set，可不做 GC。
- **真正解多帳號隔離**。

### C-6（也可考慮）保留 process lock、ai_chat 改 stateless
- 把 `AIProfessorChat` 改為純函式式：每次 `process_query_stream` 收
  `conversation_history` 為**參數**（前端傳，或從 DB conversations 拉），
  不 keep self state。
- 這個改動更深、但更乾淨。
- 工程量：**120–180 分**。
- 影響面大（_make_decision / _get_macro_context / _prepare_final_messages
  / process_query_stream 都需重構）。
- 與 Phase 2 切割較模糊；此為「重新設計 chat module」級工作，不只是 Phase 0。

## D. 推薦下一步

### D-1 真實結論
baron 對 0-δ 估「60–90 分」基於「只是改鎖 per-user」假設。實際完整解需
**順帶把 `ai_chat` 也 per-user 化**——工程量 **90–150 分**（包含驗證）。

若只做 C-1 而不改 ai_chat singleton，Phase 2 上線會立即出現「跨 user
conversation_history 污染」bug——**比 lock 互鎖更糟**（顯性 UX 災難 vs
互鎖只是阻塞）。

### D-2 推薦執行路徑

**方案 R（推薦）：合做 C-5（per-user lock + per-user AIProfessorChat）**
- 工程量：90–120 分
- 範圍：
  - `ai_core.py`：lock 與 chat 都 dict 化（owner_id 為鍵）
  - `query_stream(owner_id, ...)`：取 user 自己的 chat 與 lock
  - `add_paper_vector_store` / `load_paper_cache` / `remove_paper`：**不需改**
    （這些都走 retriever，已於 0-α/β 完成 owner 隔離）
  - `web_server.py`：呼叫 `ai_core.query_stream` 已於 0-α 加 owner_id，無需再改
- 驗證：單帳號回歸 + Phase 2 預演（mental walk-through：兩 user 同時 chat
  應有獨立 conversation_history）
- 風險：低（per-user dict 模式已於 0-α/β 驗證可行）

**方案 S（過渡）：只做 C-1，文件標註 Phase 2 launch 前升級 C-5**
- 工程量：30 分
- 適合：Phase 2 launch 還很遠、想先解阻塞讓 single-user 雙 tab 不卡
- **不建議**：自欺欺人；不如直接做 C-5

**方案 T（不做 Phase 0，留到 Phase 2 一起）**
- 工程量：0（現在）；Phase 2 啟動再做
- 適合：Phase 2 完整規劃時把「per-user ai_chat」當必做項
- 風險：Phase 2 啟動前的部署仍有「單 user 雙 tab 互卡」（既有狀況、UX
  可接受）；多帳號功能未上線就無多帳號污染風險

### D-3 建議
**選方案 R**（合做 per-user lock + per-user ai_chat）。理由：
1. 完整解、無半套 false sense of security
2. 工程量 90–120 分仍在「一輪 commit 內」可控
3. 與 0-α/β 同 pattern（dict keyed by owner_id），架構一致
4. 為 Phase 2 多帳號鋪好對話隔離地基

baron 已決定「Phase 2 多帳號前先做 0-δ」→ 推薦升級為「per-user lock +
per-user ai_chat」一次到位，避免兩階段修。

### D-4 替代：D-1 估算修正
若 baron 仍想 60–90 分內結束、接受「Phase 2 launch 前再加做 ai_chat
per-user」拆兩 commit：**先做 C-1**（30 分），同時加 `TODO(Phase 2):
ai_chat 需 per-user` 註解，**並在 Phase 2 launch checklist 列為必做項**。
（但分析者立場：兩段做總工程量比一段大、commit 多、容易遺漏，不推薦。）

## 附：完整 query_stream 控制流（reference）
```
query_stream(query, owner_id, paper_id, ...):
  acquire(blocking=False) ─┐ 失敗 → yield busy；return
                            │
                            ↓ 成功
  try:
    is_generating = True
    paper_data = _paper_cache.get((owner_id, paper_id))
    for sentence in ai_chat.process_query_stream(...):  ← 共用 ai_chat singleton
      if not is_generating: break  ← cancel 信號（cancel() 無 caller）
      yield {'sentence': ..., 'done': False}
    yield {'done': True, 'grounding_sources': ai_chat.last_grounding_sources}
  except:
    yield {'done': True, 'sentence': err}
  finally:
    is_generating = False
    release()                ← 即使 cancel/exception 也釋放
```
