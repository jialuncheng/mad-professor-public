## C. doc_type 在各階段的可得性

### C-1 通用結論
- **上傳 → confirm → pipeline 入口**：doc_type 已是 ground truth（使用者選的，
  後端已驗證）。
- **pipeline 內各 stage**：透過 `output_paths['_confirmed_doc_type']` 鎖
  鏈傳遞；每個 `_stage_*` 都從 output_paths 取值（**已 thread-through**）。
- **AI chat 階段**：**目前無法直接取得**（見 C-3）。

### C-2 pipeline 各 stage 的 doc_type 取得點

| stage 方法 | 行 | 取得方式 | 帶給 processor |
|---|---|---|---|
| `_stage_pdf_to_md` | 513–515 | `output_paths.get('_confirmed_doc_type','academic')` | 自身用：`if doc_type == 'slides'` → SlidesProcessor，否則 MinerU |
| `_stage_analyze` | 531–532 | 同上 | `doc_analyzer.analyze(markdown_path, doc_type)` |
| `_stage_translate` | 568–570 | 同上 | `translate_processor.process(... doc_type=doc_type ...)` |
| `_stage_extra_info` | 596–598 | 同上 | `if doc_type in ('news','web','slides')` → `generate_document_summary`，否則 `process` |
| upsert（最末）| 462 | 同上 | `paper_manager.upsert_paper(... doc_type=...)` |

→ pipeline 端 doc_type **完全可用且已被使用**。增加 prompt 注入只需擴用既有變數。

### C-3 AI chat / 對話階段
- `web_server.py:423` POST /chat → `ai_core.query_stream(query, paper_id, visible_content, use_web_search)`：**沒有 doc_type 參數**。
- `ai_core.query_stream` 內取 `self._paper_cache.get(paper_id)`（line 65）；
  `paper_data` 來自 `ai_core.load_paper_cache(paper_id, rag_tree_path)`
  （line 93–106）載入的是 **rag_tree.json**，無 doc_type 欄位。
- `AI_professor_chat.set_paper_context(paper_id, paper_data)` 與
  `process_query_stream` 都不接收 doc_type。
- `grep doc_type AI_professor_chat.py ai_core.py` → **0 命中**。

→ **AI 對話完全不知道當前文件的 doc_type**。這也是 ai_character_prompt
跨 doc_type 共用、且 router prompt 上輪只能改通用詞的根本原因。

### C-4 哪裡有 doc_type 可摸到（AI 階段可注入點）
| 取得方式 | 成本 | 備註 |
|---|---|---|
| **`Paper.doc_type` 查 DB**：以 `(owner_id, paper_uuid)` 查 → `paper_manager` 加 helper（如 `get_paper_doc_type`）；既有 `get_paper_db_id` 範式可仿 | 小 | 每次 chat 多 1 SELECT（毫秒級） |
| **paper_data 內嵌**：`load_paper_cache` 載入 rag_tree 時順手讀 DB `Paper.doc_type` 並注入 `paper_data['_doc_type']`；preload / load_paper_resources 兩處同步 | 小-中 | 跟既有 cache 同生命週期、零 DB 查詢於 chat 時 |
| **web_server chat endpoint 查並傳入**：在 /chat 入口查 doc_type 並透過新 kwarg 傳給 `query_stream` → `process_query_stream` | 中 | 改 3 處簽名 |

最小變更：**paper_data 內嵌**（preload / load_paper_resources / 新建即時）
比 chat 入口查詢更省、與既有 cache 模型一致。

## D. doc_type 是否可信、會不會漏

### D-1 是否可信
- **前端強制有值**：dropdown HTML 預設 `data-value="academic"`，且 `showConfirmModal`
  會以 `suggested_doc_type` 覆寫；使用者必須按「確認」才推進——必然帶值。
- **後端強驗證**：`ConfirmTypeRequest` 缺欄會 422、值不在 6 種會 400。
- **DB 寫入**：post-Phase-4.7 的 upsert 永遠帶值（pipeline 用
  `output_paths.get('_confirmed_doc_type','academic')` 預設兜底）。

→ 「新上傳必有值」。**唯一例外 = Phase 4.6 之前的舊資料**（migrate 進來時
未補 doc_type；`Paper.doc_type` 為 `nullable=True`）。

### D-2 預設值 / fallback
- 前端預設 `academic`。
- 偵測 hint：`is_slides_pdf` → 'slides' / else 'academic'（web_server:286–294）。
- pipeline 各 stage 預設兜底 `'academic'`（`output_paths.get(..., 'academic')`）。
- doc_analyzer 未知型別 → fallback `'academic'`（line 47–49）。
- translate_processor style_hints 用 dict.get → 未知型別 hint 為空字串。
- **DB 仍可能 NULL**（pre-Phase-4.7 舊資料 / 萬一 upsert 跳過）。AI 端取 doc_type
  時需處理 None / 未知 → 用通用名詞「文件」。

### D-3 使用者選錯了會怎樣
- 系統**完全信任**使用者選擇：沒有「LLM 二次驗證」、沒有「結構解析後反推」。
- 後果：履歷選成 technical → 走 technical 的 heading_fix / structure /
  translate hint / extra_info（過 RAG 仍可用，但精煉框架不貼）。
- 選 slides 與否影響最大：pipeline 完全分流（SlidesProcessor 用
  PyMuPDF+Gemini Vision，不走 MinerU）。誤選後體驗顯著不同。
- 沒有 UI 告警/事後修正入口（前端無「改 doc_type」功能）。

## E. 對 prompt 注入的影響（修正前份）

### E-1 三層 prompt 對 doc_type 的可得性

| prompt 群 | doc_type 可得？ | 注入工程量 |
|---|---|---|
| `prompt/doc/`（heading_fix / structure）| ✓ 已分流 | 0（既有設計） |
| `prompt/translate/`（translate / summary / question / formula）| ✓ pipeline-stage 帶值；translate_processor 已用於 style_hints | 小：caller 已有 doc_type 變數在 scope，只需 `.format(doc_noun=NOUN_MAP[doc_type])` |
| `prompt/ai/`（character / explain / router）| ✗ chat 階段未知；router 已避學術詞 | 小-中：需把 doc_type 帶進 chat（C-4 內嵌 paper_data 為最小） |

### E-2 {doc_noun} 注入可行性（重新評估）
- 前份 D-3a 假設「caller 需打通 doc_type 傳遞」——**對 pipeline 端是錯誤的，
  已經打通**（output_paths 全程帶值）。translate_processor 甚至**已有
  per-doc_type style_hints 內建**（line 222–232），同 pattern 可複製到 prompt。
- AI 端**確實需要打通**——是 C-3 描述的「目前 0 命中」。但工程量小：在
  paper_manager.preload_vector_stores / load_paper_resources 各加 1 行
  `paper_data['_doc_type'] = p.doc_type` 即可，零 chat-time DB 查詢。
- 結論：D-3a 仍可行且**工程量比原估更小**。

### E-3 已存在的「{doc_noun} 等價」設計：translate_processor.style_hints
`processor/translate_processor.py:222–230` 已用 dict 形式為每 doc_type 加翻譯
風格 hint（「文件為學術論文 / 書籍 / 技術文件 / 簡報 / 新聞 / 網頁文章」），
這是 **per-doc_type 提示動態組裝**的既有範式，可直接外推到其他 prompt。
**不需要新建模板系統，只需複製這個模式。**

## F. 推薦下一步（**不執行**）

### F-1 立即（止血，今晚可做）
**只動 3 個 user-facing prompt 為「doc_type-agnostic 措辭」（複製 router 上輪修法）**：
- `prompt/ai/ai_character_prompt.txt`：「論文」→「文件」、「文獻/期刊/機構」→
  「文件中提及的資料/出處」、「論文本身」→「文件內容」、「論文未涵蓋」→「文件未涵蓋」。
- `prompt/ai/ai_explain_prompt.txt`：「論文或書籍」→「文件」、「學術導師」→
  「文件閱讀助手」。
- `prompt/translate/summary_generation_prompt.txt`：通篇「論文」→「文件」、
  「論文章節」→「章節」、IMRaD 例舉（L27–31）放鬆為「依文件結構自適應」。
- 工程量：**小（30–60 分）**；零 .py 改動；prompt 為純文字檔即時讀取，
  改完不需重啟。
- 風險：academic summary 失去 IMRaD 強框架——可在 prompt 內加「若為學術
  論文，可採引言/方法/結果/討論的章節敘事」軟引導，academic 仍享深度。
- 不需資料回填：既有資料的 summary 已寫入，不會自動重生（要重跑
  extra_info 或重新上傳該文件）；但 ai_character 即時生效。

### F-2 中期（兩天內），實裝 `{doc_noun}` per-doc_type 注入
**4 個 prompt 加 `{doc_noun}` 變數 + 各 caller 套用 NOUN_MAP**：
- `prompt/ai/ai_character_prompt.txt`：通篇「文件」可改成 `{doc_noun}`
  （academic 自動變回「論文」）。
- `prompt/ai/ai_explain_prompt.txt`：同上。
- `prompt/translate/summary_generation_prompt.txt`：通篇「文件/論文」→
  `{doc_noun}`。
- `prompt/translate/question_generation_prompt.txt`：「學術論文段落」→
  `{doc_noun}段落`。
- caller 改動：
  - **translate / extra_info 端**：pipeline_core 已把 doc_type 帶到
    `translate_processor.process` 與 `extra_info_processor.process`；
    在這兩個 processor 載入 prompt 後 `.format(doc_noun=NOUN_MAP[doc_type])`。
    工程量：每 processor +3–5 行。
  - **AI 端**：`paper_manager.preload_vector_stores` (line 383) 與
    `load_paper_resources` (line 402) 已遍歷 Paper、呼叫
    `ai_core.load_paper_cache(paper_uuid, str(rtree))`——在此處將
    `p.doc_type` 注入 `ai_core._paper_cache[paper_id]['_doc_type']`。
    或更簡單：在 `load_paper_cache` 內 `paper_data['_doc_type']` 由 caller 傳。
    AI_professor_chat 載入 ai_character_prompt 時依 `paper_data.get('_doc_type')`
    取 noun 並 `.format(...)`。
    工程量：paper_manager +2 行、ai_core load_paper_cache 簽名加 1 kwarg、
    AI_professor_chat 載入 prompt 時 +3 行。
- 工程量總計：**中（2–4 小時）**。
- 風險：低；變更皆是「既有 doc_type 變數的延用」，無架構新增。
- 不必每 doc_type 一份 prompt 檔（D-3b 路線取消，6×檔案維護負擔不必要）。
