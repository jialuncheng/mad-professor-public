# MinerU 模組化 — 工程影響分析

> 範圍：純讀分析，無任何檔案改動。
> 目標：把 MinerU 變成「介面 + 實作」分離的可替換元件，避免之後換 PDF 解析工具/換版時主程式要大改。

---

## TL;DR（先給結論）

1. **現況已半模組化**：`processor/pdf_processor.py` 已是一層 wrapper，主程式（pipeline_core）只透過 `self.pdf_processor.process(pdf_path, paper_dir) -> Path` 呼叫，**全 codebase 僅 1 處 call site**（`pipeline_core.py:522`）。
2. **真正洩漏的 MinerU 細節**不在 call site，而在三個邊邊角角：
   - `metadata_extractor.py` 有硬編字串 `"source": "mineru"`（語意污染）
   - `md_cleaner.py` / `md_restore_processor.py` 註解提到「MinerU 特殊產物」（清理邏輯隱性依賴 MinerU 行為）
   - `pdf_processor.py` 內部**自己**知道 MinerU 端 ZIP 結構（`_tmp/{name}/auto/{name}.md`）、scp 路徑、x-mineru-task-id header——這層耦合是合理的（這就是 adapter 本來的職責），但介面定義從未明文化。
3. **推薦方案 X（Protocol 介面）+ 局部去語意污染**，工程量 30–60 分。
   - 方案 Y（獨立 package）目前**價值不高**：MinerU adapter 是 1 個檔 251 行、僅 1 個 caller，抽 package 只是搬家。
   - 方案 Z（HTTP service）**已經是現況**：MinerU 本身就是外部 HTTP service，主程式呼叫的是 `requests.post(MINERU_API_URL)`。再包一層 service 是多餘的。
4. **跟 GCP 部署的關係**：MinerU 早就是「外部 service」設計（`.env.example` 寫 `MINERU_HOST` 留空=本地 / 有值=遠端 scp）。**GCP 部署不需要先做模組化**；反過來，模組化也不阻擋 GCP 部署。兩者正交。

## A. 當前 MinerU 整合現況

### A-1 MinerU 在哪裡跑？

依現況證據（README、`.env.example`、`pdf_processor.py`）：

| 部署模式 | 觸發條件 | 主程式如何取圖 |
|---|---|---|
| **本機/bind-mount** | `MINERU_HOST=""`（空） | 直接讀 `MINERU_OUTPUT_DIR` 路徑（本機 path） |
| **遠端 ssh/scp** | `MINERU_HOST=user@host` | `scp -r user@host:MINERU_OUTPUT_DIR/{task_id}/{name}/auto/images/` |

- **啟動點**：MinerU **不是主程式啟動**，是另起的 HTTP service（README 給 systemd unit 範例：`mineru-api --host 0.0.0.0 --port 8000`）。
- **部署方式**：自架 venv + systemd（README 寫法）。codebase 內**無 docker / docker-compose / k8s manifest**。
- **OrcStack/GCP 證據**：codebase 內無實證；baron 訊息提到「集中部署到 GCP」是未來規劃，目前 `MINERU_API_URL` 預設仍指 `http://localhost:8000/file_parse`。

### A-2 主程式如何呼叫 MinerU

**完整 call chain**：

```
pipeline_core._stage_pdf_to_md (pipeline_core.py:512-525)
  └─ if doc_type == 'slides': SlidesProcessor.process()        # 不走 MinerU
     else:
        self.pdf_processor.process(pdf_path, paper_dir)        # ← 唯一 MinerU 入口
          ↓ (processor/pdf_processor.py:35)
          requests.post(MINERU_API_URL, files=..., data={...}, timeout=300)
          ↓
          ZIP 解壓 → 重命名 md → _copy_images (scp / 本機 copytree)
          ↓
        return markdown_path: Path
  └─ self.md_cleaner.clean(markdown_path)
```

- **介面類型**：**HTTP**（multipart POST + ZIP response）。**不是** Python library import、不是 SSH+CLI、不是 RPC。
- **次要通道**：`_copy_images` 在 `MINERU_HOST` 有值時走 `subprocess.run(["scp", ...])` 或 `["ssh", host, "ls -t ..."]`——這是**圖片取回**的副通道，主體解析仍是 HTTP。

### A-3 輸入 / 輸出

| | 內容 |
|---|---|
| **輸入** | `pdf_path: str`（本機檔路徑）、`output_dir: str` |
| **上傳細節** | multipart filename **強制** = `f"{MINERU_PAPER_NAME}.pdf"`（預設 `original.pdf`），與本機檔名解耦（Phase 4.7b 後本機是 `{paper_id}.pdf`） |
| **API params** | `return_md=true`, `response_format_zip=true`, `backend=pipeline`, `return_images=true` |
| **輸出（回給 caller）** | `Path`（指向 `{output_dir}/{pdf_path.stem}.md`） |
| **副作用輸出** | `{output_dir}/images/*`（圖檔資料夾，best-effort，可缺） |
| **中間狀態** | `{output_dir}/_tmp/` 解壓暫存，processor 完成後 `rmtree` |
| **logs** | 大量 `[pdf_processor] ...` info log，含 task_id、stderr、ZIP namelist |

### A-4 配置與環境

| 項目 | 在哪 |
|---|---|
| **MinerU 版本鎖定** | **無**。requirements.txt 內**不含** MinerU；MinerU 是外部 service，版本由部署者自行管理（README 註明）。 |
| **環境變數** | `MINERU_API_URL` / `MINERU_HOST` / `MINERU_OUTPUT_DIR` / `MINERU_PAPER_NAME`（皆讀 os.getenv，有預設值） |
| **credentials** | scp 路徑用 `subprocess.run(["scp", ...])`——依賴**OS 層** ssh agent / `~/.ssh/config` / key file。codebase 內**不管 key**。 |
| **timeout** | HTTP 300s、scp 60s、ssh ls 30s（硬編於 pdf_processor.py） |

### A-5 緊耦合點（最重要）

> 「主程式知道 MinerU 內部細節」的位置：

| # | 檔案:行 | 內容 | 嚴重度 |
|---|---|---|---|
| **1** | `processor/pdf_processor.py:107` | ZIP 內部結構硬編：`_tmp/{mineru_name}/auto/{mineru_name}.md` | 🟡 中（合理：adapter 本來就該知道） |
| **2** | `processor/pdf_processor.py:166,179,193,217,231` | 圖檔目錄結構硬編：`{mineru_name}/auto/images/` | 🟡 中（同上） |
| **3** | `processor/pdf_processor.py:77,83` | 知道 MinerU response header `x-mineru-task-id` | 🟡 中（同上） |
| **4** | `processor/pdf_processor.py:32` | `MINERU_PAPER_NAME` env 名稱本身就帶 MinerU 字 | 🟢 低（不影響重構） |
| **5** | `processor/metadata_extractor.py:98,554` | `"source": "mineru"` 字串污染進 metadata schema | 🔴 **高**：寫入 `_metadata.json`，**外洩到永久資料** |
| **6** | `processor/metadata_extractor.py:494,501` | comment / prompt 說「MinerU markdown」 | 🟢 低（純文字） |
| **7** | `processor/md_cleaner.py:18` | comment：「移除 MinerU 從圖表解析出的純數字行」——清理規則**隱性依賴 MinerU 輸出習性** | 🟡 中（換解析工具時這些 rule 可能不再適用，但不會 break） |
| **8** | `processor/md_restore_processor.py:25` | comment：「MinerU 解析特殊字元產生的亂碼」 | 🟢 低 |
| **9** | `README.md` 多處 | 文件層耦合（自然，不算 bug） | — |
| **10** | `scripts/diagnose_mineru.py` | 整支腳本針對 MinerU；非生產路徑 | 🟢 低 |

**結論**：真正的「介面洩漏」只有 **#5**（schema 寫死字串），其餘都在 adapter 內部（合理）或註解層（純文字）。

## B. 介面設計

### B-1 理想介面（依現況具體化）

```python
# processor/pdf_parser.py（建議新增）
from abc import ABC, abstractmethod
from pathlib import Path

class PDFParseError(RuntimeError):
    """PDF 解析失敗（任何 impl 都用此 type）"""

class PDFParser(ABC):
    """PDF → Markdown 的抽象介面。

    語意契約：
    - 同步 call（與 pipeline 階段化邏輯相容）
    - 失敗 raise PDFParseError（不要 raise impl-specific exception）
    - 圖檔以 side-effect 寫入 output_dir/images/（best-effort，可缺）
    - 不對 caller 暴露 task_id / ZIP 結構 / scp 等內部細節
    """
    @abstractmethod
    def parse(self, pdf_path: str, output_dir: str) -> Path:
        """
        Args:
            pdf_path:   本機 PDF 絕對路徑
            output_dir: 輸出資料夾（會建立 _tmp/, images/ 等子目錄）
        Returns:
            markdown_path: Path  # output_dir/{stem}.md
        Raises:
            FileNotFoundError: pdf_path 不存在
            PDFParseError:     解析服務錯誤、ZIP 損壞、超時等
        """
```

- **同步 vs 非同步**：保持**同步**。pipeline_core 是線性階段化（pdf2md → analyze → translate ...），非同步會破壞既有結構。HTTP timeout 300s 已是事實上限。
- **回 Path 還是 str**：回 `Path`（與現況一致）。
- **error 統一**：用 `PDFParseError` 包裝。現況 raise `RuntimeError`（含 connection / status / missing markdown 三種混在一起），語意不清。
- **進度回報**：**不在介面內**。MinerU 是 black-box HTTP，進度只能靠 log。pipeline_core 階段層已有 `progress_callback`，不必下推到 parser。

### B-2 主程式應該怎麼用

```python
# pipeline_core.py
from processor.pdf_parser import PDFParser  # ← import 介面，不 import MinerU

class PipelineCore:
    def __init__(self, pdf_parser: PDFParser | None = None):
        self._pdf_parser = pdf_parser  # 可注入；None 時走 default factory

    @property
    def pdf_parser(self) -> PDFParser:
        if self._pdf_parser is None:
            from processor.pdf_parser_mineru import MinerUParser  # lazy
            self._pdf_parser = MinerUParser()
        return self._pdf_parser
```

- **不該** `from processor.pdf_processor import PDFProcessor`（class 名洩漏 MinerU 出身——實際上 `PDFProcessor` 名字尚算中性，但 module 名 `pdf_processor.py` 內 docstring 寫死「透過本機 MinerU API」）。
- **factory** 可從 env var 決定：`PDF_PARSER_BACKEND=mineru|other` → factory 回對應 impl。但**現階段只 1 個 impl**，先別過度設計，留 hook 就好。

## C. 重構方案

### C-1 範圍提案

#### 方案 X：抽 Protocol 介面，內部仍用 MinerU ✅ **推薦**

**工程量**：30–60 分

**動作**：
1. 新增 `processor/pdf_parser.py`（ABC + Exception）—— ~30 行
2. `processor/pdf_processor.py` 改名 → `processor/pdf_parser_mineru.py`（或就地不改名）；class 繼承 `PDFParser`；`process` → `parse`（或保留別名）；exception 改 raise `PDFParseError`
3. `pipeline_core.py:8,92-95,522` 改 import / 屬性名
4. **去語意污染**：`metadata_extractor.py:98,554` 的 `"source": "mineru"` 改 `"source": "pdf_parser"`（或更具語意的 `"markdown_extracted"`）；遷移既有 `_metadata.json` 不必動（讀取端只是字串標籤）

**涉及檔案**：
- 新：`processor/pdf_parser.py`
- 改：`processor/pdf_processor.py`（rename + 繼承）
- 改：`pipeline_core.py`（3-4 行 import / attr）
- 改：`processor/metadata_extractor.py`（2 處字串）

**風險**：
- 既有 `_metadata.json` 的 `"source": "mineru"` 標籤若被任何讀取端**值匹配**，會 break。**已掃**：codebase 內無 `== "mineru"` / `"source"] == "mineru"` 形式的 reader。安全。
- `PDFProcessor` class 名被外部腳本 import 的可能：`scripts/diagnose_mineru.py` 會用——它確實 import。需同步改或保留別名。

**跟 GCP 部署**：無關。GCP 部署只動 `MINERU_API_URL` env，介面不變。

#### 方案 Y：抽獨立 package（mineru-client）

**工程量**：90–180 分

**動作**：
1. `processor/pdf_processor.py` + `processor/pdf_parser.py` → 獨立 `mineru_client/` package
2. 寫 setup.py / pyproject.toml；版本鎖定
3. 主程式 `pip install -e ./mineru_client` 或發布到內部 PyPI

**風險**：
- 目前只有 1 個 caller、1 個 impl，抽 package **沒給來 ROI**——只是搬家。
- 增加開發流程複雜度（雙 repo 或 monorepo workspace）。
- `mineru_client` 真要獨立，那 `slides_processor.py` 是不是也要？容易擴張。

**跟 GCP 部署**：無關（部署仍是改 env）。

#### 方案 Z：抽獨立 service（HTTP/gRPC）

**工程量**：4–6 小時 **但實際上已經做完了**

> ⚠️ MinerU 本身就是 HTTP service（`MINERU_API_URL`）。主程式呼叫的就是 `requests.post(...)`。再包一層 service 是套娃。

唯一有意義的版本是：**包一層自家的 PDF Service**，內部多 impl（MinerU / pdfplumber / 自家解析），對外只有 `/parse` endpoint。但這只在**多 impl 同時運行**時才有價值，現況不需要。

## D. 跟既有狀況的關係

### D-1 之前已做的 MinerU 改進

從 commit / 程式碼追：
- **Phase 4.7b**：本機檔名改 `{paper_id}.pdf`，但 MinerU multipart filename **解耦**為固定 `original.pdf`（避免 MinerU 端用長 UUID 命名 ZIP 內子目錄）→ 這已是「介面正規化」的一個動作。
- **return_images=true**：ZIP 自帶圖，scp 變 fallback —— 也是「去 server 端細節」方向。
- **pdf_processor.py 是抽象層？** **半是**。它是 wrapper（隔離了 HTTP/ZIP/scp 細節），但**沒有正式介面合約**（沒 ABC / 沒統一 exception type）。
- **還欠什麼才算「真模組化」**：
  1. 正式 ABC（方案 X 步驟 1-2）
  2. 統一 exception type
  3. 去除 `metadata_extractor` 的字串污染（A-5 #5）
  4. **可選**：env var 改名 `MINERU_*` → `PDF_PARSER_*`（這是大動作，需要遷移文件，**不建議現在做**）

### D-2 跟 SlidesProcessor 的關係

| | MinerU 路徑 | SlidesProcessor 路徑 |
|---|---|---|
| 觸發 | `doc_type != 'slides'` | `doc_type == 'slides'` |
| 解析方式 | 外部 HTTP service | 本機 PyMuPDF + Gemini Vision |
| 輸入 | PDF | PDF |
| 輸出 | markdown_path: Path | markdown_path: Path（同型） |
| 失敗模式 | HTTP error / ZIP 損壞 | Vision API error |

**該不該共用介面？** ✅ **該**。兩者輸入輸出契約一模一樣（PDF → MD path），只是 impl 不同——這正是 `PDFParser` ABC 最該抽象的兩個實作。

**建議**：方案 X 同步讓 `SlidesProcessor` 也繼承 `PDFParser`。`_stage_pdf_to_md` 改成：

```python
parser = self._slides_parser if doc_type == 'slides' else self._pdf_parser
markdown_path = parser.parse(str(pdf_path), str(paper_dir))
```

工時 +10 分（總計 55 分）。

### D-3 跟 GCP 部署的順序

| 問題 | 答案 |
|---|---|
| GCP 部署先做？後做？ | **正交，誰先都可以** |
| MinerU 模組化阻擋 GCP？ | **不阻擋**。GCP 部署只動 `MINERU_API_URL`，不需動 codebase |
| GCP 需先模組化才好部署？ | **不需要**。adapter 已將 endpoint env 化 |
| 兩者的關係 | 完全解耦。模組化是「換 impl 變容易」，GCP 是「換 endpoint」 |

**唯一交集**：如果 GCP 用 IAM token 而非 ssh key 取圖，那 `_copy_images` 的 scp 邏輯要改——但那是 **adapter 內部**的事，方案 X 完成後改一個檔即可。

## E. 推薦執行順序

### 推薦：**方案 X**（5 個小 commit，總 45–55 分）

| Commit | 內容 | 工時 | 可獨立 |
|---|---|---|---|
| 1 | 新增 `processor/pdf_parser.py`（ABC + PDFParseError，純新增、無 caller） | 10 分 | ✅ |
| 2 | `PDFProcessor` 繼承 `PDFParser`、`process` 加別名 `parse`、exception 統一 | 15 分 | ✅ |
| 3 | `SlidesProcessor` 繼承 `PDFParser`、`process` 加別名 `parse` | 10 分 | ✅ |
| 4 | `pipeline_core._stage_pdf_to_md` 改走統一 `parser.parse()` | 10 分 | ✅ |
| 5 | `metadata_extractor` `"source": "mineru"` → `"markdown_extracted"`（去語意污染） | 5 分 | ✅ |

### 跟 P1 群、GCP 部署的優先順序

| 工作 | 優先序 | 理由 |
|---|---|---|
| Stage A chat stateless | ✅ 已完成 | — |
| **MinerU 模組化（方案 X）** | **P2**（中優先） | 預防性、無使用者可見效果，但**做了之後換解析工具/做多 impl 實驗變容易** |
| GCP 部署 | **P1**（高優先） | 直接影響使用體驗 / scalability |
| Stage B（chat 抽 package） | P3 | 預防性 + 工程量大 |

**建議**：**先 GCP 部署，再做方案 X**。理由：
- GCP 部署是「即時痛點」（local MinerU 速度/容量限制）
- 方案 X 是「將來才痛」（換工具/換版時痛）
- GCP 部署完成後，若 MinerU 換版/換工具的需求真的出現，再做方案 X 也只是 45 分鐘的事

但**反過來也合理**：方案 X 工程量極小（< 1 小時），可作為**飯後甜點**，做完再進 GCP，避免將來 GCP migration 時同時改太多東西。

## F. 風險點

### F-1 既有資料相容性

| 風險 | 評估 | 緩解 |
|---|---|---|
| 既有 paper reload 壞掉 | **無風險**。介面抽象僅在「處理新 paper」時生效，reload 只讀既有檔案 | — |
| pipeline 重跑既有 paper | **無風險**。pdf_path / paper_dir 介面不變，輸出檔案位置不變 | — |
| `_metadata.json` 的 `"source": "mineru"` 標籤 | 字串改名後，**舊資料仍是 `"mineru"`，新資料是 `"markdown_extracted"`**。若有 UI 顯示這欄會混合 | 加 reader 端 normalize（`if source in ("mineru", "markdown_extracted")`）或保留舊值不動，只改新寫入路徑 |
| `PDFProcessor` class 名被外部 import | `scripts/diagnose_mineru.py` 會用 | rename 時同步改；或保留 `PDFProcessor = MinerUParser` 別名一段時間 |

### F-2 錯誤恢復

| 風險 | 評估 |
|---|---|
| 抽象化後錯誤訊息變模糊 | **可能**：原本 `RuntimeError("MinerU API 回傳錯誤: 500 ...")` 變 `PDFParseError("...")`。**緩解**：`PDFParseError(str(e)).with_traceback(...)` 保留原訊息，只統一 type |
| Debug 難度增加 | **不會**。adapter 內 log 全留（`[pdf_processor] ...`），介面層只是包一層 exception |
| 多 impl 後 caller 不知道是哪個 impl 失敗 | **緩解**：`PDFParseError` 帶 `impl_name` 屬性，log 時印出 |
