## title fallback 鏈（設計風險 #1 對應，已驗證）
`resolve_title(metadata, rag_tree_path, paper_uuid)`：
1. `metadata['title'].value` 2. `metadata['title'].alternates` 任一非空
3. rag_tree 的 title（既有邏輯）4. `paper_uuid`（不會空）
實測：None→`paper_x`；有 value→`Real Title`；只有 alternate→`Alt T`。

## spec 與實際差異（誠實標註）
1. **未改 db.py / scripts/migrate_to_db.py**（spec G 列為「可能需要」）：
   `init_db` 的 create_all 對可清空庫自動建新欄；`migrate_to_db.py` 的
   `Paper(...)` 未帶 metadata_json → 預設 None，`_to_dict` 已容 NULL。
   故兩檔無需變更（更小 diff、更低風險）。
2. **Stage A 未用 asyncio 並行**：spec D 範例為 `async def process` +
   `asyncio.gather`，但實際 `pipeline_core.process` 是**同步**（由
   `web_server.run_pipeline` 以 `run_in_executor` 跑），內部並行用
   `ThreadPoolExecutor`。改 async 會破壞 web_server 的 executor 契約、屬高風險
   大改。採「Stage A 於 pdf2md 前序列執行」——Stage A（fitz+1 LLM）相對 MinerU
   （數分鐘）極短，序列化對總牆鐘影響可忽略；設計意圖（兩階段、soft、title 從
   metadata、abstract 從 MinerU）完整保留，僅「與 pdf2md 重疊」最佳化延後。
3. **upsert_paper 簽名**：spec 示意 `upsert_paper(db, owner_id, paper_uuid,
   title=..., metadata=...)`；實際既有簽名為
   `upsert_paper(output_dir, owner_id, paper_uuid, final_paths)`，沿用並加
   `metadata=None` 選參（保持唯一呼叫端 pipeline_core 相容），未改既有位置參數。
4. **真實端到端（上傳 800-vdc）未能在此環境跑**：`output/` 空、無 GEMINI 金鑰，
   無法實際 upload→pipeline→看 DB metadata_json。已用：DB schema 檢查、
   resolve_title/upsert 行為實測、web_server 啟動、既有單元測試 等效驗證接線正確。
   **須於 OrcStack（有金鑰+資料）執行 I 節端到端**：清庫→init_db→migrate→
   啟動→上傳 800-vdc→確認 DB `metadata_json` 有完整 schema v2、title 正確
   （非 null、非 Contents）、authors 補回、abstract 由 MinerU 補上。

## 風險
1. DB schema 變動需重建（設計已允許清資料，無遷移負擔）。
2. 舊 paper 缺 metadata → `_to_dict` 容 NULL（已驗不崩）。
3. pipeline 多 1（Stage A LLM）+ 條件性 0~1（Stage B 規則命中則 0 次 LLM）次呼叫；
   全 soft fail，任一失敗不影響 pipeline（metadata 退化為空結構、title 走 fallback）。
4. Stage A 序列化（非並行）使含 LLM 的首頁抽取在 MinerU 前；對總時間影響小但非零，
   後續可於 4.x 再做並行最佳化（已標記）。
