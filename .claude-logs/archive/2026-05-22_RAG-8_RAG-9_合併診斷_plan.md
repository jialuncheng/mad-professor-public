## §3 觀察到的問題與證據

### 3.1 RAG-9 證據（前端）

#### 江元杰履歷 markdown 含單 `~` 範圍語法：
```
（電子零件、半導體業 100~500人）
... 機電整合研發副理 (2003/8~仍在職)
```

#### marked.js 9.1.6 GFM 預設啟用 strikethrough：
- `grep "marked.setOptions\|marked.use" static/index.html` → **0 處**
- marked.js GitHub 9.x source: `extensions/gfm.ts` 內 strikethrough tokenizer 對 `~+...~+` 匹配

#### 確認：
```javascript
// marked.js 9.1.6 + 預設 + 沒自訂
> marked.parse("100~500人 ... 2003/8~仍在職")
"<p>100<del>500人 ... 2003/8</del>仍在職</p>"
```

`100` 後的單 `~` 與 `2003/8` 後的單 `~` 在同段 `<p>` 內配對為 `<del>`、user 看到整段被劃線。

#### 是否有合法 `~~text~~` 用法（grep 整份 worktree）？

```bash
grep -rn "~~[^~]" static/ output/ 2>/dev/null | grep -v ".jpg\|.png" | head
# 結果：0 行（worktree 內無歷史合法用法）
```

→ **拿掉 GFM strikethrough 零代價**。

### 3.2 RAG-8 證據（後端）

#### DeHunt 學歷 4 個 stage 對照

##### Stage 1: `.md`（pdf2md + md_cleaner 後）
```
90:## Educational Background
92:<table><tr><td></td><td>2003/09 - 2008/06 National Chiao Tung University</td>...</table>
```
→ HTML `<table>` 一行、無 \n 內嵌。

##### Stage 2: `_structured.json`（md2json 後）
```json
{
  "title": "Educational Background",
  ...
  "content": [
    "<table><tr><td>...</td></tr></table>"
  ],
  ...
}
```
→ content[0] 是字串、整個 `<table>` 字面、單行。

⚠ **發現**：DeHunt 的 table content 在 `content` 陣列內是**字串（不是 dict）**，**不是 `{'type':'table', 'content':...}` 格式**。

##### Stage 3: `_translated.json`（translate 後、不在樣本內、推測）
推測 LLM 翻譯時 table 內容（HTML `<table>` 字串）被當 text item 翻譯、變成翻譯後的中文 HTML table。

##### Stage 4: `final_*_zh.md`（md_restore 後、user 看到）
```
## 學歷背景

<table><tr><td></td><td>2003/09 - 2008/06 國立交通大學...</td></tr>...</table>

## 核心技能
```
→ HTML `<table>` 仍是一行、無 row 間空行。

#### **DeHunt 樣本看不到 row 間空行的 bug！** ⚠

DeHunt 用 HTML `<table>`（MinerU OCR 輸出格式）、不是 pipe table。HTML `<table>` 內 `<tr>...</tr>` **沒有 `\n` 分隔**、所以 regex `\n(?!\n)` → `\n\n` 不會破壞 HTML table。

#### **真正撞 bug 的應是 slides + pipe table** ⚠

`SLIDE_PROMPT` 強制 slides 輸出 pipe table、rows 之間用單 `\n` 分隔：
```
| 欄位 1 | 欄位 2 |
| --- | --- |
| 資料 | 資料 |
```

→ Slides 翻譯後 pipe table 進 text item content（推測；slides processor 把整頁輸出當文字 chunk）、L683-684 regex 把每行間 `\n` 改 `\n\n`：
```
| 欄位 1 | 欄位 2 |

| --- | --- |

| 資料 | 資料 |
```
→ markdown 解析器看到 paragraph 間空白行、認為這 3 行是 3 個獨立 paragraph、不再是 table、渲染為純文字。

#### **完整斷言（需 §4 補證）**：

只有「在 text item 內含單 `\n` 的內容」會被 L683-684 撞爆。Pipe table（slides 全部）+ markdown list（部分？）+ 多行段落（部分）都可能受害。

## §4 設計方案

### 4.1 RAG-9 修法

**推薦 A：marked.js 9.x extension 移除 strikethrough**：

```javascript
// static/index.html 在 <script src=".../marked.min.js"> 之後加：
marked.use({
  extensions: [{
    name: 'del',
    level: 'inline',
    start(src) { return src.indexOf('~'); },
    tokenizer() { return undefined; }    // 永不匹配、相當於關閉
  }]
});
```

或更乾淨的方式（marked 9.x 支援）：
```javascript
marked.use({ gfm: true });  // 確認 gfm 仍開（保 table / autolink）
// 但 marked 9.x 沒有 strikethrough: false 開關、需 extension override
```

**最簡且明確**：
```javascript
marked.use({
  extensions: [{
    name: 'del', level: 'inline',
    start() { return -1; },               // 從不主動匹配
    tokenizer() { return false; },
    renderer() { return ''; }
  }]
});
```

落地位置：`static/index.html` `<script>` 載入 marked.js 後、所有 `marked.parse()` 呼叫之前（建議放第一個 `<script>` block 內 module 載入後）。

### 4.2 RAG-8 修法

依 §3.2 診斷、最可能病灶是 **C（md_restore）**、修法兩條路線：

#### 修法 1（推薦）：精準 regex、不破壞 pipe table

`processor/md_restore_processor.py:683-684` 改寫：

```python
# 原：
# en_content = re.sub(r'\n(?!\n)', '\n\n', en_content)
# zh_content = re.sub(r'\n(?!\n)', '\n\n', zh_content)

# 改為：偵測 pipe table 區塊不動、其他單 \n 改 \n\n
def _preserve_pipe_table(text: str) -> str:
    """單 \n 改 \n\n、但 pipe table 區塊（以 | 開頭 + 連續行）保留原 \n。"""
    lines = text.split('\n')
    out_lines = []
    in_table = False
    for line in lines:
        is_table_row = bool(re.match(r'^\s*\|', line))
        if is_table_row:
            in_table = True
            out_lines.append(line)
        elif in_table and not line.strip():
            # table 結束（遇空行）
            in_table = False
            out_lines.append(line)
        elif in_table:
            # table 結束（遇非 | 開頭非空行）
            in_table = False
            out_lines.append('')   # 補空行作 table / 後續 paragraph 分隔
            out_lines.append(line)
        else:
            out_lines.append(line)
    text = '\n'.join(out_lines)
    # 一般 paragraph 內單 \n 仍要轉 \n\n
    text = re.sub(r'(?<!\|)\n(?![\n\|])', '\n\n', text)
    return text

en_content = _preserve_pipe_table(en_content)
zh_content = _preserve_pipe_table(zh_content)
```

#### 修法 2（簡化、退路）：對 text item 不做 \n → \n\n 強轉

L683-684 整段刪除、單純：
```python
en_content = ' '.join([part[1] for part in en_parts])
zh_content = ' '.join([part[1] for part in zh_parts])
# 不做 re.sub
```

⚠ 但此法可能破壞「單 `\n` 段落」的 academic / news 文本（原本依賴此 regex 把多行段落變成 paragraphs）。需 §6 e2e 對 academic / news 樣本回歸驗證。

#### 修法 3（保險）：先 diagnose 階段 + log

加診斷 log 看 L683-684 regex 對 slides text content 實際做了什麼：
```python
import re
# 在 L683 之前
table_lines_before = sum(1 for ln in en_content.split('\n') if ln.startswith('|'))
en_content = re.sub(r'\n(?!\n)', '\n\n', en_content)
table_lines_after = sum(1 for ln in en_content.split('\n') if ln.startswith('|'))
if table_lines_before != table_lines_after:
    self.logger.warning(f"[md_restore] regex 改變 pipe-table 行數: {table_lines_before} → {table_lines_after}")
```

**推薦執行順序**：
1. 先做修法 3（diagnose log）部署到 OrcStack 重跑 slides 樣本、確認 §3.2 假設成立
2. 確認後做修法 1（精準 regex）
3. 若修法 1 對 academic / news 有 regression → 退到修法 2
