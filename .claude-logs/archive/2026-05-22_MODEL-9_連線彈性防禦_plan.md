## §1 TL;DR

- **問題與挑戰**：當前 `google-genai 2.3.0` SDK client 初始化時**未設 timeout、未共享 httpx.Client、未啟用 connection pool**；baron 觀察到 Gemini 3 Pro Preview 偶發 `httpx.RemoteProtocolError`（已加進 retry token、§2.3 證實）+ SSE 卡死（17-1b 已用 `asyncio.to_thread` 解 event loop 阻塞、但底層 socket 卡 read 仍會耗盡 worker）。
- **核心根因**：
  1. `llm/client.py:48` 與 `config.py:22` 都是 `genai.Client(api_key=GEMINI_API_KEY)` 零 http_options
  2. SDK 預設 httpx transport 無顯式 timeout（依底層 OS socket、可能無限）
  3. 每次呼叫 SDK 內部各自管 httpx.Client、無 Keep-Alive pool 共享、TCP handshake 重複
  4. 既有 `llm/retry.py` 用 `delay = base * (2 ** attempt) + random.uniform(0, 1)` 是「指數退避 + 小線性抖動」、不是提案推薦的「全隨機抖動」`t_wait = random(0, min(t_max, base * 2^attempt))`
- **設計解法**：1 commit 合 3 項——
  - 4.1 注入 `http_options.httpxClient = httpx.Client(timeout=httpx.Timeout(connect=5, read=30, write=30, pool=60))`
  - 4.2 同 `httpx.Client` 配 `httpx.Limits(max_keepalive_connections=20, max_connections=100, keepalive_expiry=30)`
  - 4.3 `llm/retry.py` 改用全隨機抖動公式（不破壞既有介面、語意小升級）
- **影響範圍**：
  - **動**：`llm/client.py` (LLMClient.__init__)、`config.py` (EmbeddingModel.__init__)、`llm/retry.py` (delay 公式)、新增 `llm/_http_client.py` (集中共享 client + factory)
  - **不動**：`pipeline_core` / `web_server` / `processor/*` / RAG retrieval / 任何業務邏輯
- **預估**：1 commit、半天（含 4 個新 pytest）。**SDK 原生支援 `httpxClient` 注入**（§2.5 已 probe 確認）、不需 e2e POC 前置。

### 2.4 17-1b 改 asyncio.to_thread 後仍卡死的場景

baron 之前觀察：
- Gemini 3 Pro Preview latency 高（30-90s 多頁 Vision call）
- 偶發 `Server disconnected without sending a response.`（httpx `RemoteProtocolError`）→ 已被 retry 抓
- SSE 卡死症狀（17-1b before 是 event loop 阻塞、17-1b 後是底層 socket 卡 read 耗 thread pool worker）

**推測**：SDK 預設無 read timeout、socket 卡死的 thread 永不 return、`asyncio.to_thread` 仍占 default executor worker → 多次發生會把 thread pool 耗盡 → 後續所有 LLM call 排隊卡死。

## §3 觀察到的問題與證據

### 3.1 Timeout 問題（對應提案 §4.1）

- **證據**：`llm/client.py:48`、`config.py:22` 兩處 `genai.Client(api_key=GEMINI_API_KEY)` 完全無 `http_options` 參數
- **SDK 預設**：未明文設定 → 走 httpx 預設（httpx 0.28 預設 5 秒 connect + 無限 read = 卡 read 風險）
- **影響**：Gemini 3 Pro Preview 多頁 Vision call 偶發 socket 卡死、thread 永不 return、占 default `asyncio.to_thread` executor worker（max ~32）；連續發生會把 worker 耗盡

### 3.2 連線池問題（對應提案 §4.2）

- **證據**：LLMClient + EmbeddingModel 各自獨立 `genai.Client(...)`、無共享 httpx.Client、無顯式 `keepalive_expiry`
- **影響**：每次新建 TCP connection 多 1-2 RTT handshake（台灣 → Gemini us-east endpoint ~150ms × 2 = 300ms 額外延遲）；高併發下 TIME_WAIT 堆積、極端可能撞 ephemeral port 上限

### 3.3 Retry 策略問題（對應提案 §4.3）

- **證據**：`llm/retry.py:75-76`
  ```python
  delay = base * (2 ** attempt) + random.uniform(0, 1)
  ```
- **問題**：這是「指數退避 + 0-1 秒線性抖動」、不是「全隨機抖動」
- **提案推薦公式**：`t_wait = random(0, min(t_max, t_base * 2^attempt))`
- **語意差異**：
  - 既有：attempt=3 → `2*8 + [0,1) = [16, 17)` 秒（窄窗、所有 retry 大約同時撞）
  - 提案：attempt=3 → `random(0, min(60, 16)) = random(0, 16)` 秒（寬窗、徹底打散）
- **影響**：多 worker 同時 retry 時驚群效應、再次撞 429

## §4 設計方案

### 4.1 新增 `llm/_http_client.py`（集中工廠）

**動機**：避免 LLMClient + EmbeddingModel 各自配置、單一來源、便於未來調整。

```python
# llm/_http_client.py
"""共享 httpx.Client 工廠（Phase 4.7? MODEL-9）。

提供集中配置的 httpx.Client、給 google-genai SDK 透過 http_options.httpxClient 注入。
LLMClient + EmbeddingModel 共用同一個底層 client、保 Keep-Alive pool 共享。
"""
import threading
import httpx
from google.genai import types

# 4.1 + 4.2：timeout + Keep-Alive pool 一次配齊
_HTTP_TIMEOUT = httpx.Timeout(
    connect=5.0,    # TCP connect 上限（baron 觀察過 Gemini endpoint 有時 4-5s）
    read=30.0,      # 等 response 上限（Vision call 較長、可改高）
    write=30.0,     # 送 request body 上限（多頁 vision 圖較大）
    pool=60.0       # 從 pool 拿 connection 上限
)

_HTTP_LIMITS = httpx.Limits(
    max_keepalive_connections=20,
    max_connections=100,
    keepalive_expiry=30.0,  # idle connection 保留 30s（避免 server 端先斷）
)

_lock = threading.Lock()
_shared_client: httpx.Client = None


def get_shared_httpx_client() -> httpx.Client:
    """singleton: 全 process 共享 httpx.Client。"""
    global _shared_client
    if _shared_client is None:
        with _lock:
            if _shared_client is None:
                _shared_client = httpx.Client(
                    timeout=_HTTP_TIMEOUT,
                    limits=_HTTP_LIMITS,
                )
    return _shared_client


def build_http_options(*, vision: bool = False) -> types.HttpOptions:
    """產生 SDK http_options、注入共享 httpx.Client。

    Args:
        vision: 若為 True（Vision call）、回 client 用更寬鬆的 read timeout（60s）
                預設 False 用標準 30s read timeout。
    """
    client = get_shared_httpx_client()
    return types.HttpOptions(httpx_client=client)
```

### 4.2 修改 `llm/client.py::LLMClient.__init__`


### 4.4 修改 `llm/retry.py` delay 公式（4.3 jitter）

**改動點 1**：`retry_call` 內 L74-76
```python
# 原:
# delay = base * (2 ** attempt) + random.uniform(0, 1)

# 改為（全隨機抖動指數退避）:
MAX_BACKOFF = 60.0  # 上限 60s
exp_window = min(MAX_BACKOFF, base * (2 ** attempt))
delay = random.uniform(0, exp_window)
```

**改動點 2**：`retry_stream` 內 L106-108 同上修改。

**語意**：
- attempt=0: `random(0, min(60, 2)) = random(0, 2)`
- attempt=1: `random(0, min(60, 4)) = random(0, 4)`
- attempt=2: `random(0, min(60, 8)) = random(0, 8)`
- attempt=3: `random(0, min(60, 16)) = random(0, 16)`
- attempt=4: `random(0, min(60, 32)) = random(0, 32)`

新增 module-level constant：
```python
# 4.3：上限 60 秒、避免 attempt 很大時 wait 過久
MAX_BACKOFF_SEC = 60.0
```

## §5 變動風險與相容性評估

| 風險 | 等級 | 緩解 |
|---|---|---|
| Read timeout 30s 對 Gemini 3 Pro Preview 長 Vision call 不夠 | 🟡 中 | 建議 read=60s（兼顧）、若仍不夠可再調寬 |
| Connect timeout 5s 過短誤殺 | 🟢 低 | baron 觀察 Gemini endpoint connect <= 1s、5s 充裕 |
| `keepalive_expiry=30s` 太長被 server 端先斷 | 🟢 低 | httpx 自動偵測 broken connection + 重連、retry 抓得到 |
| Retry 公式從窄窗→寬窗變得「總等待時間」可能增加 | 🟢 低 | 隨機分布期望值仍小於原線性抖動 ceiling、實測影響不大 |
| `httpx.Client` 共享 + multi-thread 安全性 | 🟢 低 | httpx.Client 本身是 thread-safe |
| SDK 不支援自定 httpx.Client | ✅ **已解** | §2.5 probe 確認 SDK 2.3.0 原生支援 `http_options.httpxClient` |
| 既有 `@retry_call` decorator 與 SDK 內建 retry 衝突（重複退避） | 🟢 低 | §4.5 選項 C 拒絕、不用 SDK retry；既有 decorator 一切不變、只升級公式 |
| `tests/test_llm_retry.py` 既有 test fixture 依賴舊公式 | 🟡 中 | §6 需確認既有 test 對 delay 值的硬編碼斷言（grep 確認） |
