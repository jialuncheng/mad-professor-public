# Phase 4.7c — 前端顯示 metadata + doc_type 分支抽取策略 分析報告

> 純讀分析、零檔案改動。
> 目標：把後端早就抽好的 metadata 端到端接到使用者眼前，並依 doc_type 改善抽取結果。

---

## TL;DR

1. **後端 metadata 早就抽好、寫進 DB**——`pipeline_core` Stage A（fitz + LLM page1 + 雙來源 merge）+ Stage B（markdown abstract）+ `paper_manager.upsert_paper` 一條龍齊全。`models.Paper.metadata_json` 也存了；`/api/papers` 也回傳了 `metadata` 欄位。
2. **前端**整包拿到 `paper.metadata`，**但完全沒用**。`paper-item` 只渲染 `p.translated_title || p.title`，`content-area#current-title` 拿的是 `loadPaper(id, title)` 傳入字串——同樣只是 DB title。
3. **DB title 已經是 metadata 抽取結果**：`paper_manager._to_dict` → `p.title` 是 `upsert_paper` 時 `resolve_title(metadata, rag_tree, paper_uuid)` 寫進去的。所以前端「沒接 metadata」**不完全是顯示問題**——當 metadata.title 為空時，DB title fallback 到 `rag_tree.title`，再 fallback 到 `paper_uuid`（醜 UUID）。
4. **真正的問題分兩條**：
   - **問題 A（顯示層）**：當 title fallback 到 `paper_uuid` 時，前端應該至少顯示 `original_filename`（已存 DB、`/api/papers` 已回傳，**目前 fallback 鏈未含**）。
   - **問題 B（抽取層）**：generic Stage A LLM prompt 是「給 academic 用的」（找標題、作者、abstract、DOI、期刊…）。對 technical（白皮書封面是 TOC）、resume（沒 title，要的是 candidate_name）、slides（封面結構彈性大）效果差。
5. **建議拆 5 個 commit**：1 顯示層 fallback、2 metadata schema 加 `candidate_name`、3 resume 走專用 prompt、4 technical 改 multi-page LLM、5 content-area 顯示完整 metadata 區塊。
6. **不阻擋 GCP 部署**。**跟 P1（rename paper）正交**——rename 是 user override，metadata 是 auto-extract。**跟 Resume Phase 2 高度重疊**（resume 專用 prompt 兩邊都要做，建議併單一輪做完）。

## A. 後端現況完整盤點

### A-1 metadata_extractor.py 完整邏輯

**Schema v2 結構**（`create_empty_metadata()`）：

```python
{
  "_schema_version": 2,
  "_stage_b_ran": bool,
  # 11 個欄位，每個都是 {value, source, confidence, alternates}：
  "title":                   {...},
  "translated_title":        {...},
  "authors":                 {...},  # list
  "publication_date":        {...},  # YYYY-MM-DD
  "abstract":                {...},
  "journal_or_conference":   {...},
  "doi":                     {...},
  "keywords":                {...},  # list
  "publisher":               {...},
  "organization":            {...},
  "version":                 {...},
}
```

每欄位的 `source` 列舉：`pdf_metadata | llm_page1 | markdown_extracted | both_agree | manual | "llm_page1 (conflict with pdf_metadata)"`。
`confidence`：`high | medium | low | None`。

**抽取三路**（pipeline_core 內）：

| 路 | 時機 | 函式 | source 標籤 |
|---|---|---|---|
| 1 | Stage A 第一步（同步） | `extract_pdf_metadata` (fitz) | `pdf_metadata` |
| 2 | Stage A 第二步（同步、`pdf2md` 之前） | `extract_metadata_from_first_page_llm`（LLM 看 page1 文字+圖） | `llm_page1` |
| 3 | Stage B（`pdf2md` 之後） | `fill_abstract_stage_b`（**只補 abstract**） | `markdown_extracted` |

**合併規則**（`merge_stage_a`）：
- 兩者皆有且 norm 後相等 → `both_agree` / high
- 一有一空 → 用有的 / high
- 衝突 → 取 LLM、標 `llm_page1 (conflict with pdf_metadata)` / medium
- abstract 在 Stage A **永遠強制空**（等 Stage B markdown）

**doc_type 是否影響抽取？**
**❌ 完全不影響。** `_STAGE_A_PROMPT` 是固定模板（要 title/authors/abstract/DOI/期刊/keywords/publisher/organization/version），對 resume / technical / slides 等非學術文件**用同一個 prompt**。pipeline_core 在 Stage A 時甚至**還沒拿到 doc_type 確認**（_confirmed_doc_type 是另外的流程），這是個結構性問題。

- 中文標題：`translated_title || title`（兩者都來自 metadata 鏡像 / fallback 鏈）

- 原文標題（12px / 2-line clamp / muted）
- 右上 ⋯ 按鈕

**spec 沒明確說「metadata 缺漏時顯示什麼 fallback」。** copywriting.md 內也搜不到「未命名 / Untitled / 無標題」這類 fallback 文案。

**gap**：
- `paper-title-zh` / `paper-title-en` 拿到 paper_uuid 時會顯示一坨醜字（如 `800-vdc-architecture-for-ai-infrastructure` 還算可讀；但 `1763964129445952184` 完全是亂碼）

## C. doc_type 分支抽取策略提案

### C-1 academic
- 維持現況 Stage A prompt
- ✅ 信任度高

### C-2 technical（白皮書，封面常為 TOC / Cover image）
**核心痛點**：800-vdc 案例——封面是 TOC，現行 prompt 「排除 Contents 作為 title」反而讓 title=None。

**建議**：**multi-page LLM**（看頭 3 頁）+ 放寬規則：
- 看 page 1, 2, 3 並由 LLM 自己挑「最像主標題的」
- 若仍抓不到 → fallback 到 PDF metadata.title（不過濾 Word/PowerPoint 雜訊正則，因為白皮書通常是 LaTeX/InDesign 匯出，metadata title 較可靠）
- 信心度：medium

**新增 prompt 檔**：`prompt/processor/metadata_technical.txt`

### C-3 slides
**核心痛點**：1763964129445952184 連檔名都不友善。

**建議**：**SlidesProcessor 內順便寫 metadata**——它已經用 Vision 看每一頁，page 1 的 title 它早就知道：
- 在 `SlidesProcessor.process()` 結尾，把 page 1 的 `title` 寫進 `paper_info` 或 sidecar
- pipeline_core Stage A 對 slides 跳過 LLM 看 page1（避免雙看），直接用 SlidesProcessor 結果
- **不新增 LLM 呼叫**（零成本）

**或更保守**：保留 Stage A 通用流程，slides 接受 medium 信心度即可。

### C-4 resume
**核心痛點**：DeHunt 案例——履歷沒「title」概念，要的是 **candidate_name**。

**建議**：
- **schema 新增 `candidate_name` 欄位**（list 與其他欄位對稱，{value, source, confidence, alternates}）
- resume 走專用 prompt（`prompt/processor/metadata_resume.txt`），抽：candidate_name / contact_email / years_experience / current_role / latest_employer / skills_summary
- title 欄位**強制設為 candidate_name 鏡像**（前端 paper-item 顯示候選人姓名）
- abstract / authors / DOI / journal 一律設 None
- 信心度：high（履歷頭幾乎一定有姓名）

**這跟 Resume Phase 2 高度重疊**——Resume Phase 2 也計畫做 resume 專用 prompt，建議**合併單一輪做完**。

### C-5 news / book / web
**暫不做。** 三者數量稀少，academic 通用 prompt 表現夠用。等未來真有具體痛點再加分支。

## D. metadata_json 結構演進

### D-1 是否新增欄位

| 選項 | 內容 | 評估 |
|---|---|---|
| 1 | schema 加 `doc_type_fields: dict[doc_type, fields]` | ❌ 過度設計，增加 reader 複雜度 |
| 2 | 保持 generic schema，欄位有就填、沒就 None | ✅ 簡單，但 resume 的 candidate_name 無處放 |
| 3 | title 對 academic = 論文標題、對 resume = 候選人姓名（**語意 overload**） | 🟡 簡單但語意混淆，前端難分辨 |
| **4** | **schema 加 `candidate_name` 一個 nullable 欄位**，與其他欄位對稱；對 academic 永遠 None；對 resume 是主資料 | ✅ **推薦** |

**推薦選項 4**。理由：
- schema 仍是 flat，無 reader 複雜度
- 對其他 doc_type 是 `{value: null, source: null, ...}`，零負擔
- title 欄位語意明確（對 resume 鏡像 candidate_name 但保留原語意）
- 前端可決定：`paper-item` 對 resume 優先顯示 candidate_name、對其他用 title

需動 `_ALL_FIELDS`（metadata_extractor.py:80）和 `_LLM_FLAT_KEYS`（L312）—— 兩處 grep 加一個字串即可。`_LIST_FIELDS` 不動（candidate_name 是 scalar）。

### D-2 既有資料 migration

**不做 backfill**。理由：
1. `metadata_json` 整包是 JSON，schema v2 結構新加欄位前端只需 optional access
2. 既有 paper 重新跑 pipeline 成本高（fitz + LLM + MinerU 全跑一遍）
3. 既有醜 title 的 paper 透過「P1 rename」由 user 手動 override 更合理

**新邏輯**：只對新上傳 paper 生效，舊資料保持不動（讀取端 `metadata?.candidate_name?.value` optional chain）。

- 後端：`resolve_title` 新增一層 fallback：`metadata → rag_tree → original_filename → paper_uuid`

| 場景 | 顯示 |
