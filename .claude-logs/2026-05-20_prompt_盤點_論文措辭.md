## D. 修法選項（**不執行**）

### D-1 最小改（C-1 三檔靜態替換）
- 動的檔：`ai_character_prompt.txt`、`ai_explain_prompt.txt`、
  `summary_generation_prompt.txt`（C-1 三檔）。
- 做法：「論文」→「文件」、「學術導師」→「文件閱讀助手」、IMRaD 章節
  例舉改通用敘述（「核心章節 / 細節章節 / 結論章節」）。
- 工程量：**中（60–90 分）**——`summary_generation_prompt.txt` 18 命中要
  保持精煉品質、避免單純替換損品質；建議真改前先小規模 A/B（academic
  vs resume vs news 各一份精煉抽樣比對）。
- 風險：summary 對 academic 的精煉品質可能微降（從「論文 IMRaD 框架」
  變「通用文件」會少一些結構導向）；可於提示中加「依文件結構靈活
  套用」保底。
- 已對齊：router prompt 上輪已修；ai/ + summary 改完即可解決
  「AI 稱履歷為論文」的可見問題。
- 不必重建 RAG：summary 是 pipeline 生成階段的產物，**既有資料已存的
  summary 不會自動更新**——需重跑 extra_info stage 或重新上傳該文件
  才會用新 prompt。

### D-2 中度（C-1 + C-2 七檔靜態替換）
- 動的檔：C-1 三檔 + `content_translate_prompt.txt` /
  `title_translate_prompt.txt` / `question_generation_prompt.txt` /
  `formula_analysis_prompt.txt`（7 檔合計）。
- 工程量：**大（2–4 小時）**——translate 兩檔牽連譯文 register（重大）；
  formula 對 academic 重要，需小心。
- 風險：translate 改後既有翻譯不會回填；只影響新上傳。
- 副益：履歷/新聞譯文不再帶學術腔；RAG 生成問題也跟著去學術化。
- 仍是「一刀切」：academic 與 non-academic 共用同一份 prompt，academic
  深度可能輕度降。

### D-3 大改（per-doc_type 變體 / 變數注入）
- 兩條路：
  - **3a. 模板變數注入**（建議）：每 prompt 內把「論文」改成 `{doc_noun}`
    這樣的變數；caller 載入時依 doc_type 注入對應名詞（academic→「論文」、
    book→「書籍」、news→「新聞」、slides→「簡報」、resume/web→「文件」、
    technical→「技術文件」）。變數可能不只一個（「章節」也可條件化）。
  - **3b. 每 doc_type 一份檔**：仿 `doc/` 既有架構，`translate/` 與 `ai/`
    也建 academic/book/news/slides/web/technical 變體。
- 動的檔：
  - 3a：7 個 prompt + AI_professor_chat.py、translate_processor.py、
    extra_info_processor.py（caller 加 `.format(doc_noun=...)`、需從
    DB / pipeline 拿 doc_type 傳進來）。
  - 3b：7 × 6 = **42 個新 prompt 檔** + 對應 caller 路由表。
- 工程量：
  - 3a：**大（4–8 小時）**——caller 需打通 doc_type 從 DB（Paper.doc_type）
    傳到所有 prompt 載入點；翻譯/精煉 stage 跑時已有 doc_type 可拿；
    AI 對話端要從 paper_id → Paper.doc_type 查（paper_manager 有
    get_paper 可用）。
  - 3b：**很大（1–2 天）**——多檔維護成本高，但 caller 改動小（沿用
    `doc/` 字典 pattern）。
- 風險：
  - 3a：跨檔變動但維護單一文案；模板套到非預期 doc_type 會降一階輸出
    品質直到 prompt 微調。
  - 3b：維護成本（修一個共同規則要改 6 處）；但邊界清晰、academic
    深度可保留、各 doc_type 可獨立優化。
- 副益：academic 仍享有「論文」框架的深度；non-academic 拿到 properly
  framed 的 prompt；長期是正解。

## E. 推薦（純分析者意見）

### 短期（立即止血）：**D-1 最小改**
理由：
1. 解決 baron 觀察到的具體問題（AI 稱履歷為論文）；
2. 對 academic 風險可控（summary IMRaD 框架放鬆為「依文件結構」，
   academic 仍會用 IMRaD，因 doc_analyzer 已給 LLM 結構訊號）；
3. 1–2 小時內可完成（含 A/B 抽樣比對品質）；
4. router prompt 上輪剛改、ai_character 一改即見效。

### 中期（next sprint）：**D-3a 模板變數注入**
理由：
1. 規模化解：之後新增 doc_type 不必改 prompt；
2. caller 端工程量中等，且 doc_type 在多數階段已可取得；
3. academic 仍享「論文」框架的深度，non-academic 得到合適名詞；
4. 比 D-3b 維護成本低（單一檔，無 6×重複）；
5. 與既有 `doc/` 字典分流形成「結構走分流檔、措辭走模板變數」的互補。

### 不建議
- D-2 中度：仍是一刀切，academic 品質會被拉低、non-academic 不見得貼題；
  收益小於 D-3a。
- D-3b 每 doc_type 一份：維護負擔過高、6 倍檔案不利於後續 prompt 演化。

### 操作建議
1. 立刻做 D-1（不超過今晚），止住「AI 稱履歷為論文」的觀感問題。
2. 同步開 ticket 排 D-3a（兩三天內），把 `{doc_noun}` 模板系統建起來，
   翻譯/精煉/AI 三層一次到位。
3. C-2 / formula_analysis 可緩——它們對非 academic 觸發機率低（formula）
   或影響非關鍵（title/question_generation）。
