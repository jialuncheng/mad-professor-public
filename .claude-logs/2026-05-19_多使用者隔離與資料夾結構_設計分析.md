# 2026-05-19 多使用者隔離 + 文件資料夾結構：資料結構影響分析（純設計，未改任何程式碼）

## 任務
即將正式部署（目前單帳號 admin、所有論文共用一庫）。分析兩個未來需求對現有資料結構的影響：
(1) 每登入者獨立論文庫/問答歷史/設定；(2) 文件列表支援資料夾。要求不改程式碼，只做設計分析並存檔。

## A. 現有資料結構盤點（依實際程式碼）
- output 根：`web_server.py:74` `OUTPUT_DIR=BASE_DIR/"output"`（全域單一）。每篇 `output/{paper_id}/`：
  original.pdf / 中間檔 / final_{id}_zh|en.md / final_{id}_rag_tree.json / vectors/(FAISS) / images/ / chat_history.json
- `paper_id = sanitize_paper_id(filename)`（web_server.py:247）= 檔名衍生、全域命名空間（多使用者同名會撞）。
- papers_index.json schema（paper_manager.py:63-68）：`[{id,title,translated_title,paths{article_en,article_zh,rag_md,rag_tree,rag_vector_store,images,original_pdf}}]`，**無 owner/folder/created_at**，upsert 以 id 為唯一鍵。
- 對話歷史：`output/{paper_id}/chat_history.json`（per paper，非 per user）。
- rag_tree.json：純文件內容，無個人化資訊（可共用）。
- 向量庫：一篇一個 `output/{paper_id}/vectors/`；啟動 preload 掃全 index；rag_retriever 以 paper_id 為 key。
- ai_core：`_paper_cache{paper_id→rag_tree}` 全域；對話歷史在 AIProfessorChat 單實例 in-memory；`_generating_lock` 全域單鎖（多人排隊）。
- 登入：settings.AUTH_USERNAME/HASH 單帳號；`session["user"]` 已設但資料層從未使用 → 零租戶概念。
- 關鍵風險：paper_id 全域＋檔名衍生→撞檔；index/cache/retriever/preload/processing_tasks 全以全域 paper_id 為鍵；chat 無 user 維度；API 無 user 區段但 session 已知 user。

## B. 多使用者三方案
- A per-user 目錄 `output/{user}/{paper_id}/`＋`output/{user}/papers_index.json`：改 ~150-250 行/6 檔；隔離強（FS 級）；pipeline 傳路徑即可；遷移＝搬到 output/admin/（上線前近零成本）；上線後改痛=高。
- B owner 標籤（共用目錄，index 加 owner，端點 filter）：改 ~80-150 行；隔離中（app 層）；**每個 /api/papers/{id}/* 端點都要授權檢查，漏一個=越權漏洞（安全風險最高）**；paper_id 命名空間問題仍在。
- C DB 化（users/papers/conversations/folders；檔案落地、metadata 進 DB）：改 ~300-500 行＋新依賴；隔離強；順帶解 papers_index 讀改寫並發 race；前期成本最高、上線後演進最省（migration）。

## C. 資料夾方案
- A1 純前端虛擬資料夾：最便宜過渡，但跨裝置/多使用者不同步。
- B1 後端 folder 欄位（paper entry 加 `folder:string|null`，`/` 表階層）：與 owner 天然整合，最小可行。
- C1 DB folders 表：支援一篇多資料夾/資料夾權限，非 DB 不建議多對多。
- 判斷：跨使用者拖曳不允許；folder 隨 owner 不需獨立權限；初期單 folder 字串（多對多延後到 DB）。

## D. 推薦組合
骨幹＝方案 A（per-user 目錄）＋ folder 用 B1 欄位 ＋ DB(C) 延後。
最終結構：`output/{owner}/papers_index.json` + `output/{owner}/{paper_id}/...`（內部結構不變）。
index entry 加 4 欄（向後相容）：`owner / folder / created_at / schema_version=2`。
paper_id 改 `{sanitize(filename)}__{short_uuid}`（消除撞名）。
API URL 不變，後端由 `session["user"]` 解析 owner＋每端點越權檢查；Phase 2 加 `PATCH /api/papers/{id}`(set folder)。

階段：
- Phase 0（上線前必做、最小、行為不變）：引入 {owner} 目錄層（恆 admin）、index 寫 owner/folder/created_at/schema_version、paper_id 唯一化。
- Phase 1（要多人時）：多帳號登入 + 端點 owner 過濾/授權 + cache/retriever/preload key 改 (owner,paper_id) + 視需要 per-user 鎖。
- Phase 2（資料夾）：前端樹 + PATCH folder（欄位 Phase 0 已預留）。
- Phase 3（選配）：papers_index 並發成痛點/需多對多 → 遷 SQLite/PG（靠 schema_version migration）。
上線前最低＝Phase 0 三件事；可晚做＝多帳號/folder UI/DB/per-user 鎖/跨裝置設定。

## E. 上線前最小準備（不啟用多使用者但讓未來不痛）
1. 目錄預留 user 階層：所有寫入走 `output/{OWNER}/...`，OWNER=AUTH_USERNAME。
2. papers_index 預留欄位：寫 owner/folder/created_at/schema_version；讀對舊資料容缺。
3. 對話歷史隨 paper 目錄移到 output/{owner}/{paper_id}/ 自動 per-user。
4. paper_id 唯一化（最痛不可逆項，務必 Phase 0 做）。
5. API URL 不改，後端 session→owner 解析（前端零改）。
6. 一次性遷移腳本（上線前資料量近零，成本可忽略）。
結論：Phase 0 只改「資料往哪寫」「index 帶哪些欄位」，不改任何使用者可見行為；不做 Phase 0 就上線→未來在有真實資料下搬目錄＋重編 id 是代價最高、最該避免的情境。

## 疑慮 / 待確認
