## §2 問題敘述

### 2.1 一句話總結
當前專案隨着模組擴大，正面臨「Claude Web 退出後的流程約束斷層」、「文件職責重疊與命名飄移」、「每次 Session 讀取全套 SOP 造成的 Token 成本暴漲」以及「跨 AI 工具協作時頻繁破壞 Prompt Caching 導致的資金浪費」四大痛點。v3 規劃書旨在解決這些問題，但其提出的**強約束硬規則**是否會在實際操作中引入新的「協作摩擦」與「快取失效」，需要 Antigravity 作為第三方進行深度的可行性驗證。

### 2.2 詳細描述與挑戰
1. **快取破壞危機**：v3 流程的核心節省手段是 Prompt Caching，但 v3 §15 強制要求所有文件在頂部加入「§0 改版規則」，這會直接破壞前綴快取，導致每一次微小的流程調整都會引發全局的 `cache miss`，造成成本反向暴漲。
2. **格式一刀切的局限**：v3 §11 強制要求所有改版規劃書套用統一格式，這對於「變動型文檔」非常合適，但對於「長期規格型文檔」（如 API 審計、數據庫分析）會產生結構坍塌。
3. **驗證成本過高**：v3 提示詞模板 D 要求 Antigravity 每次 Commit 跑 7 項驗證，這會強迫 AI 讀取大量無關文件，大幅稀釋上下文注意力。

#### 2. 強制性 vs 彈性的平衡策略
> [!IMPORTANT]
> **核心設計修正**：
> 我們必須在進度管控框架中區分「變動型文檔」與「規格型文檔」：

## §5 跨工具的 Prompt Caching 策略評估（核心關鍵）

> [!IMPORTANT]
> **Prompt Caching 戰略意義**：
> 快取能讓前綴 token 成本降至 10%（Claude）或 25%（Gemini）。然而，v3 流程中存在數個「快取殺手」，若不進行結構性優化，快取機制將徹底失效。

### 子題 5.1：跨 AI 工具的快取狀態盤點

| 工具 | 是否支援 prompt caching | 快取 TTL | 是否跨 session 持續 | 是否跨機器持續 |
|---|---|---|---|---|
| **Google Antigravity**（自身） | **✅ 支援 (Context Caching)** | **30 分鐘到 1 小時** | **否**（session 級） | **否** |
| **Claude Code** | ✅ 支援 | 5 分鐘（預設）/ 1 小時（可配置） | 否（session 級） | 否 |
| **Claude Web** | ✅ 自動快取 system prompt | 不公開 | 部分（24h 內） | 否 |
| **Claude Design** | ✅ 支援 | 不公開 | 部分 | 否 |

> [!NOTE]
> **Antigravity 自身快取機制分析**：
> Antigravity 基於 Gemini 3.5 Flash，其底層支持 **Context Caching（上下文快取）**。當我們連續發起多次對話，且讀取相同的 `.claude-logs/ref/` 目錄時，Gemini API 會自動將這些重複的參考文檔（約 30k tokens）快取在記憶體中。
> 相比於 Claude Code 每次啟動命令都需要重建快取（每次 `clode` 啟動都有 5-10 秒的快取建立延遲與 Token 消耗），**Antigravity 在長對話/複雜規劃場景下的快取命中率更高，成本大幅低於 Claude Code**。

### 子題 5.2：v3 流程對「跨工具快取」的友善度評估
*   *現狀痛點*：不同工具（Claude Code 與 Antigravity）雖然讀取同一個 repo 的文件，但由於各自的系統提示詞（System Prompt）和任務引導不同，**快取無法共享**。
*   *快取對齊設計*：為了在各個工具中都達成最高的快取命中率，我們必須**「把通用參考前綴跟工具專屬內容物理分檔」**。
    *   *做法*：將最龐大且通用的 `PROJECT_PROGRESS_CONTROL_FRAMEWORK.md` 與 `WORKFLOW_SOP.md` 放在讀檔順序的最前面，使其成為「冷快取單元（Cold Cache Block）」；而將頻繁變動的單個 `_plan.md` 或 `diff` 放在最後面，保護前方前綴不被破壞。

---

### 子題 5.3：v3 §15「§0 改版規則」對快取的衝擊與優化建議
*   *致命危機*：v3 §15 要求將「§0 改版規則」放在**文件最頂部**。
    *   當 baron 更新了某一處流程（例如在 `PROJECT_PROGRESS_CONTROL_FRAMEWORK.md` 頂部的 §0 增加了一行修訂記錄），由於**修改發生在文件頭部**，這會導致該文件後方所有的內容在 AI 讀取時，**快取全部失效（Cache Miss）**。
*   *結構優化方案（物理保護前綴）*：
    > [!WARNING]
    > **核心修正：將 §0 改版規則從「頂部」移至「文件末尾（Bottom-loading）」**。
    > 我們應將所有長期文檔的 `# 標題` 保持極簡，將頻繁變動的「§0 改版規則與修訂記錄」以及「治理規格表」**統一放置在文件的最底層**。
    > 這樣做能確保文件前 80% 的穩定章節（SOP 核心內容）形成一個完美的、永遠不會被破壞的快取前綴；只有最末尾的變動區會引發微小的 cache miss。

### 子題 5.4：v3 §14「文件治理規格表」對快取的衝擊
