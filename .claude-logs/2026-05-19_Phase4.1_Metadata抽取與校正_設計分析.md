## 0. 既有 pipeline 校正（重要：與題述簡化版不同）

實際 `pipeline_core.py` 的 `STAGE_NAMES`（單一權威來源）為：

```
pdf2md → (analyze ∥ detect_domain) → md2json → json_process → tiling
       → (translate ∥ image_caption) → md_restore → extra_info → rag
```

- `analyze` 與 `detect_domain` **並行**（`ThreadPoolExecutor(max_workers=2)`，
  detect_domain 失敗為 soft fallback 不中止）；`translate` 與 `image_caption` 並行。
- `domain_detector` **已存在「讀 PDF 第一頁（fitz get_text + 首頁截圖）→ LLM」**模式
  （`settings.LLM_DOMAIN_MODEL`、`chat_with_image`，全程 try/except 回 ''）。

- 目前 `title/translated_title` **僅在 `rag` 階段末**由 `paper_manager.upsert_paper`
  讀 `rag_tree`（`_read_title_from_rag_tree`）寫入 DB → title 正確性完全依賴
  MinerU/結構分析鏈，且要等到 pipeline 幾乎跑完才定案（本案痛點根因）。
- `_stage_*(pdf_path, paper_dir, paper_name, output_paths)` 統一簽名；新增階段需動：
  `STAGE_NAMES`、`STAGE_DISPLAY_NAMES`、`stage_identifiers`、`available_stages`、
  新 `_stage_metadata*` 方法、`_check_stage_exists`（resume）、新 processor 檔。

## J（先給結論）— 已依「MinerU 為元兇」修正

> 重大修正：原設計誤把 MinerU 結果列為高信任。實際 **MinerU 是現有錯誤元兇**
> （跳過封面頁、把第二頁「Contents」當 H1）。正確信任度：
> **LLM 看第一頁 > PDF metadata > MinerU 結果**。設計改為「雙來源先決，
> 必要時才呼叫第三方（MinerU）」，而非三來源並列仲裁。

**信任度排序（每欄位）**

| 來源 | title | author | abstract | date |
|---|---|---|---|---|
| LLM 看第一頁原始文字 | **最高** | 高 | 高（但純文字排版常亂，見 abstract 例外） | 高 |
| PDF metadata (fitz) | 中 | **高（通常正確）** | 無此資料 | 中（creationDate ≠ 發表日） |
| MinerU 結果 | **最低（已知會錯）** | 中 | **高（abstract 段落 MinerU 通常抽得出）** | 中 |

**插入點：方案 C 的精神，但流程改「雙來源先決 + 條件性 Stage B」**

- **Stage A（與 `pdf2md` 並行）**：同時做兩件事，互為驗證——
  - `fitz` 抽 PDF metadata → `raw_pdf_meta`
  - LLM 看第一頁原始文字 → `raw_llm_page1`（含中英 title）
- **Stage A 結束即時比對**（無需 LLM，純規則）：
  - 兩者**一致或互補**（一空一有）→ 直接採信，metadata（除 abstract）**已完成**，
    `confidence=high`，**不跑 Stage B**。
  - 兩者**衝突** → 標記該欄 → 進 Stage B。
  - 兩者**皆空** → 進 Stage B。
- **Stage B（條件性，僅衝突/皆空時才跑）**：在 `analyze` 後，LLM 看
  MinerU markdown 開頭 + Stage A 結果做仲裁；衝突欄解出 `confidence=medium`，
  三方仍不確定 `confidence=low`（前端提示使用者確認）。
- **abstract 例外**（見下節）：abstract **永遠等 MinerU**（Stage B 必跑於 abstract，
  與其他欄位的條件性無關）。
- 效益：多數文件 `PDF metadata + LLM 第一頁` 即可定案（除 abstract），
  **大部分文件不需要 Stage B → 省一次 LLM call 與牆鐘**；Stage A 又與 pdf2md
  並行（零額外牆鐘）。MinerU 結果僅作「最後仲裁素材」，不再污染高信任欄位。

**abstract 例外（單獨規則）**

- 學術論文 abstract 雖在第一頁，但常用雙欄/特殊排版，`fitz.get_text()` 純文字
  抽取會錯亂、不可靠 → **abstract 不在 Stage A 定案**。
- abstract 主要靠 MinerU 抽出的結構化段落 → **abstract 一律走 Stage B（看 MinerU
  markdown），其 MinerU 來源信任度視為高**。
- 結論：`title / author / date / doi / journal / keywords / publisher /
  organization / version` 盡量在 **Stage A 定案**；`abstract` **永遠 Stage B
  （MinerU）**。即使其他欄位 Stage A 已定案、Stage B 仍會為了 abstract 而跑
  （但僅針對 abstract 欄，prompt 可精簡為「只補 abstract」以省 token）。
- **DB 設計：混合制**——既有 `title / translated_title / domain / doc_type` **維持
  獨立欄位**（已被 `_to_dict`/列表/排序/上層邏輯使用，不可動）；其餘 metadata
  （authors/publication_date/abstract/doi/keywords/publisher/organization/
  journal_or_conference/version/_sources）存**單一 `metadata` JSON 欄位**。
  理由：未來新增欄位（如 grant、license）免 migration；這些欄位無 filter/sort/join
  需求不需獨立欄；與既有 `Conversation.grounding_sources` 用 JSON 的前例一致。
  因「測試資料會清」，schema 變更只需改 `models.py` + 重建空庫（`db.init_db()`
  的 `create_all`），**Phase 4.6 無需 Alembic**；待有正式資料才導入 Alembic。

## A. metadata 資料結構

落地為 `output/{owner_id}/{paper_uuid}/_metadata.json`（與既有 sidecar 慣例一致，
如 `_doc_structure.json`/`_extra_info.json`）＋ DB `papers.metadata`(JSON) 鏡像。
`title`/`translated_title` 同時寫入既有欄位（相容 `_to_dict`）。

每個欄位採「值 + 來源 + 信任度 + 候選」結構（取代舊的扁平 `_sources` 字串）：

```json
{
  "fields": {
    "title": {
      "value": "800 VDC Architecture for Next-Generation AI Infrastructure",
      "source": "llm_page1",
      "confidence": "high",
      "alternates": {
        "pdf_metadata": null,
        "mineru_h1": "Contents"        // 只有 Stage B 跑了才會有
      }
    },
    "translated_title": {
      "value": "用於次世代 AI 基礎設施的 800 VDC 架構",
      "source": "llm_page1", "confidence": "high", "alternates": {}
    },
    "author": {
      "value": ["Jared Huntington", "Mike Tu"],
      "source": "llm_page1 + pdf_metadata",   // 兩來源一致
      "confidence": "high", "alternates": {}
    },
    "abstract": {
      "value": "...",
      "source": "mineru",                      // abstract 永遠走 MinerU
      "confidence": "high", "alternates": {}
    },
    "publication_date": {
      "value": "2025-10-09", "source": "pdf_metadata",
      "confidence": "medium", "alternates": { "llm_page1": null }
    },
    "doi":   { "value": null, "source": null, "confidence": "low", "alternates": {} },
    "journal_or_conference": { "value": null, "source": null, "confidence": "low", "alternates": {} },
    "keywords":     { "value": ["GPU","Data Center","Power Distribution"], "source": "llm_page1", "confidence": "high", "alternates": {} },
    "publisher":    { "value": null, "source": null, "confidence": "low", "alternates": {} },
    "organization": { "value": "NVIDIA", "source": "llm_page1", "confidence": "high", "alternates": {} },
    "version":      { "value": null, "source": null, "confidence": "low", "alternates": {} }
  },
  "_extracted_at": "2026-05-19T12:00:00Z",
  "_stage_b_ran": false,
  "_schema_version": 2
}
```

- `source` 值域：`llm_page1` / `pdf_metadata` / `mineru` / `manual`，
  或以 ` + ` 連接表「多來源一致」（如 `llm_page1 + pdf_metadata`）。
- `confidence`：
  - **high**：兩來源一致，或唯一可信來源（如 title 只有 llm_page1 但明確）。
  - **medium**：兩來源衝突、已由 Stage B 仲裁完成。
  - **low**：三方皆不確定/皆空 → 前端標記，提示使用者確認（人工填則 source=`manual`）。
- `alternates`：保留被淘汰的候選值（debug 用）；只有 Stage B 跑過該欄才會有
  `mineru_*` 候選。
- `_stage_b_ran`：本篇是否觸發了 Stage B（衝突/空或 abstract）。
- 約定：字串欄找不到 `value=null`；陣列欄 `value=[]`；日期 `YYYY-MM-DD`，不確定 null。
- DB 鏡像：整個物件存 `papers.metadata`(JSON)；`fields.title.value` /
  `fields.translated_title.value` **另鏡寫既有 `title`/`translated_title` 欄位**
  以相容 `paper_manager._to_dict`/列表/排序。`_schema_version=2` 供演進判讀。

## B. PDF metadata 抽取（fitz）— 信任度「中」，非最高、非純 fallback

`fitz`（PyMuPDF，已為相依）`doc.metadata` 可得：`title / author / subject /
keywords / creationDate / modDate / producer`。

**全域信任度排序（修正後）：LLM 看第一頁 > PDF metadata > MinerU 結果。**
PDF metadata 不是「永遠 fallback」，而是與 LLM 第一頁**並列為 Stage A 雙來源**、
互相驗證；其中 **author 欄 PDF metadata 通常正確（信任度高）**，title 中等
（常被 Word 匯出污染），無 abstract，date 為製檔日（中等、非發表日）。
MinerU 結果信任度**最低**（已知會跳過封面、把「Contents」當 H1），僅在
Stage A 雙來源衝突/皆空時作為仲裁素材（abstract 為唯一例外，見 J）。

各 PDF 來源的 fitz metadata 可得性（供 Stage A 比對時判斷）：

| PDF 來源 | title | author | date | 備註 |
|---|---|---|---|---|
| arXiv PDF | 多半有 | 有 | creationDate 有 | author 相對可信 |
| Word 匯出 | 常空/檔名雜訊 | **有（可信）** | 有 | title 常為「Microsoft Word - xxx.docx」應視為雜訊 |
| 簡報轉 PDF | 多空 | 偶有 | 有 | title 幾乎不可用 |
| 掃描檔 | 全空 | 全空 | 製檔日 | 無語意 |

策略：
- `author`：fitz 有值且非空 → 與 LLM 第一頁比對；兩者一致 → `high`；
  互補（一空一有）→ 採有值方；衝突 → 進 Stage B。
- `title`：fitz title 若含 `.docx/.pdf/Microsoft Word/Untitled` 等樣式 →
  視為雜訊**不採**，title 以 LLM 第一頁為準。
- `creationDate`：解析為 `publication_date` 候選，但標 `confidence:medium`
  （製檔日 ≠ 發表日）；LLM 第一頁若抽到明確發表日則優先。
- `keywords`：fitz keywords 多空，主要靠 LLM 第一頁。

## C. LLM Prompt 草稿 — Stage A（第一頁）

輸入：`fitz` 第一頁 `get_text()`（截至約 4000 字，與 domain_detector 一致上限）。
模型：建議 `LLM_DOC_MODEL`（後台 Flash 級，已存在的細分變數）。

```
你是文件 metadata 抽取助手。以下是一份 PDF 第一頁的原始文字：

---
{page1_text}
---

抽取下列 metadata：
1. title：文件主標題（通常字體最大、置中、最上方；非副標、非章節名）
2. translated_title：將 title 翻成繁體中文（保留專有名詞/縮寫，如 GPU、NVIDIA）
3. authors：作者，字串陣列
4. publication_date：發表日，格式 YYYY-MM-DD（不確定填 null）
5. abstract：摘要整段（若該頁未出現，填 null，勿臆測）
6. journal_or_conference：期刊或會議名
7. doi：DOI（沒有就 null，嚴禁編造）
8. keywords：關鍵字字串陣列
9. publisher：出版社
10. organization：機構（如 NVIDIA、arXiv）
11. version：版本（如 v2、Rev. B）

規則：
- 排除「Contents / Introduction / Abstract / Table of Contents」等章節字眼當 title
- 排除頁碼、頁眉頁腳、投稿日期戳記
- 找不到的字串欄填 null、陣列欄填 []
- 嚴禁編造（DOI/date/journal 沒看到一律 null）
- 只輸出純 JSON，不要 markdown 圍欄、不要解釋

JSON 範本：
{json_template}
```

## D. LLM Prompt 草稿 — Stage B（MinerU 後校正）

輸入：`raw_metadata`（A 階段＋PDF metadata 合併後）＋ MinerU markdown 開頭
（前 3000 字；abstract 可能很長 → 截斷並標示 `…(truncated)`）。

```
以下是初步 metadata（來自 PDF metadata 與第一頁文字）：
{initial_metadata_json}

以下是 MinerU 從整份 PDF 抽出的 markdown 開頭（前 3000 字，可能截斷）：
---
{markdown_head}
---

請校正並補全這份 metadata：
- 初步 metadata 缺漏的欄位，從 markdown 補上（尤其 abstract 完整段落、author 名單）
- markdown 顯示更明確時更新（但 title 以「文件主標題」為準，勿被 H1 誤導為 Contents）
- 嚴禁編造；找不到維持原值或 null
- translated_title 跟著最終 title 一致（必要時重譯）

只輸出完整校正後的純 JSON（同範本，含 _sources：被你更新的欄位標 llm_after_mineru）。
```

兩 call 皆 `try/except` 軟失敗：A 失敗 → 用 PDF metadata；B 失敗 → 沿用 A 結果。
**永不中止 pipeline**（比照 detect_domain 的 soft 契約）。

- 不影響 `paperReadiness`／`loadPaper` 既有狀態機（metadata 與 readiness 正交）。

## H. 風險

1. **LLM 誤判**：副標/標語當 title、把 organization 當 author。緩解：A 用首頁原始
   文字（含版面語意）、B 用 MinerU 結構交叉校正、prompt 明確排除章節字眼。
2. **LLM 編造**：PDF 無 DOI/date 卻生成。緩解：prompt 強制「沒看到一律 null、嚴禁
   編造」；`_sources` 標來源供抽查；數值型欄位（DOI/date）可加格式驗證（後續實作層）。
3. **prompt 過長**：abstract 很長 → markdown_head 截 3000 字、page1 截 4000 字；
   截斷標示 `…(truncated)`。
4. **非英文 PDF**：中文/日文論文首頁版式不同、PDF metadata 多空。緩解：prompt 不假設
   語言；translated_title 一律輸出繁中；organization/journal 容許原文。效果需實測，
   列為已知限制。
5. **title 來源切換的回歸**：既有 `upsert_paper` 由 rag_tree 取 title；改為 metadata
   後，若 metadata 階段軟失敗則 title 可能空 → 需保留「metadata 缺 → rag_tree →
   檔名」的 fallback 鏈，避免列表出現空白標題（設計層已標明，實作 Phase 4.5 落實）。
6. **並行 worker 數**：pdf2md∥metadata_raw 需確認 `ThreadPoolExecutor` 容量與
   API rate limit（metadata_raw 用 Flash、單 call，影響小）。
7. **sidecar 與 DB 一致性**：以 DB 為真實來源，`_metadata.json` 僅 debug；重跑
   pipeline 時 `_check_stage_exists` 應允許 metadata 階段 idempotent 覆寫。

## I. 階段拆解與相依

| Phase | 範圍 | 相依 | 可獨立驗證 |
|---|---|---|---|

## J. 推薦總結

- **信任度（修正）**：LLM 看第一頁 > PDF metadata > MinerU 結果。MinerU 是現有
  錯誤元兇，僅作衝突仲裁素材；**唯一例外 abstract 走 MinerU（信任度高）**。
- **流程（修正）**：不再三來源並列仲裁。改「**雙來源先決**」——Stage A（與
  `pdf2md` 並行）同跑 fitz PDF metadata + LLM 第一頁 → 即時規則比對：
  一致/互補即定案（除 abstract），**僅衝突/皆空才條件性跑 Stage B**（看 MinerU）。
  多數文件不需 Stage B，省一次 LLM call 與牆鐘。
- **DB**：混合——保留 `title/translated_title/domain/doc_type` 欄位，新增單一
  `metadata` JSON 欄；測試資料可清故免 Alembic（改 model + `init_db` 重建），
  正式上線後再導 Alembic。
- **資料結構**：每欄位 `{value, source, confidence, alternates}`；`confidence`=
  high/medium/low（low 前端請使用者確認）；DB `metadata` JSON + sidecar；
  title/translated_title 鏡寫既有欄位以相容 `_to_dict`。
- **兩 prompt**：A=第一頁抽取；B=條件性仲裁（含 abstract 可用精簡「只補 abstract」版）；
  皆 soft fail、嚴禁編造、截斷長文。
- **最大風險**：title 來源由 rag_tree 改 metadata 需保 fallback 鏈（metadata→
  rag_tree→檔名）避免空標題；LLM 編造以 source/confidence＋prompt 約束緩解。
- **Phase 順序（修正）**：4.2 可獨立 commit 但**不單獨上線**；**4.2＋4.3 綁定同時
  上線**（雙來源互驗）；**4.4 條件性、可延後甚至略過**（依 4.2+4.3 實測衝突率決定，
  abstract 仍需最小 Stage B）。最划算先做＝4.2（純 fitz，可立即單測）。
