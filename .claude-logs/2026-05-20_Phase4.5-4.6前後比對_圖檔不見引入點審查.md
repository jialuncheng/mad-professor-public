## B. Stage A 對 pdf_processor 的潛在干擾（重點，已逐行看 fitz）

`processor/metadata_extractor.py`：
- `extract_pdf_metadata`（180）：`doc=fitz.open(...)` → **finally `doc.close()`**
  （220-224）。
- `get_first_page_text`（228）：同樣 **finally `doc.close()`**（242-246）。
- `get_first_page_render`（249）：`pix=doc[0].get_pixmap(...)`；
  **`return pix.tobytes("png")`**（258）——**PNG 在記憶體 bytes，不寫
  disk、無 tempfile、無 `pix.save()`**；**finally `doc.close()`**（263-267）。

逐項回答：
1. **fitz.open 後有沒有 close？** 有，三函式全部 `finally: doc.close()`。
   PyMuPDF close 後不持 OS 鎖；pdf_processor 之後 `open(pdf_path,"rb")`
   不受影響。→ **PDF 鎖：非肇因。**
2. **渲染第一頁 PNG 寫 disk 嗎？寫哪？** **不寫**。`tobytes("png")` 純記憶體，
   直接餵 Vision LLM。disk 上不產生任何 PNG/暫存。→ **磁碟污染：非肇因。**
3. **Stage A 後 PDF 狀態正常嗎？** 正常。Stage A 對 PDF 全唯讀、用完即
   close、不改檔、不移檔；pdf_path 內容/路徑/權限不變。→ 正常。

## C. Stage A 對 LLM 環境的影響

`extract_metadata_from_first_page_llm`（344）：
- **無 `os.chdir` / `os.getcwd`**：不改 cwd。
- **無 `os.environ[...]=` 寫入**：不設/改 env 變數。
- LLM 用 `config.LLMClient.get_instance()`（既有單例，doc_analyzer 等
  早就在用）走 HTTP 到 Gemini；**不碰 SSL/CA store、不改 SSL_CERT_FILE、
  不動 subprocess/ssh/scp 環境**。
- → **對後續 scp 連線環境零影響。非肇因。**
- 附帶（非肇因，僅記）：Stage A 多一次 LLM call 增加總牆鐘數秒~數十秒，
  在 pdf2md 之前；MinerU POST 自帶 timeout=300、pipeline 跑在
  BackgroundTasks/run_in_executor 無 HTTP 請求逾時，故延遲只「拖慢」
  不「弄丟圖」。

## D. paper_manager 改動副作用（upsert 與 _tmp / race）

- upsert_paper 在 **pipeline 最末**跑；`_tmp` 在更早的 pdf2md stage 內、
  pdf_processor.process() 結尾 `shutil.rmtree(_tmp)` 即已刪除。
  → upsert 跑時 **_tmp 早已不存在**，兩者無交集。
- race condition：pipeline 為 **同步**執行（web_server 以
  run_in_executor 跑單一 pipeline.process）；upsert 與 _copy_images 在
  同一執行緒、嚴格先後（_copy_images 早於 upsert 數分鐘），**無併發、
  無 race**。upsert 亦不觸 images 目錄。→ **非肇因。**

## E. pipeline_core.process() 時序確認

```
pre-loop : [新] Stage A (fitz 唯讀 + 1×LLM, soft)         ← 不碰 _tmp/images
stage loop: pdf2md{MinerU POST→解ZIP到_tmp→搬md→
            _copy_images(取圖)→rmtree(_tmp)} → analyze+detect_domain
            → md2json → ... （**迴圈本體與 b912a71 相同**）
pre-upsert: [新] Stage B (讀已落地 md, soft)               ← _tmp 已不存在
upsert    : [改] upsert_paper(+metadata/domain/doc_type)   ← 純 DB
```
Stage A 與 `_copy_images` 之間隔整個 MinerU（數分鐘），唯一交集是
**唯讀 pdf_path**（Stage A 用完即 close）。時序上無任何新的 _tmp/images
互動被引入。**diff 證實 stage loop 零改動。**

## F. 最可能引入點（排序 + 反證）

**排序 1（真因，非本範圍碼）：環境/部署漂移 + 既有設計脆弱性。**
- 為何：取圖路徑前後逐字元相同（b912a71 即 original.pdf）；MinerU 回的
  ZIP 本就含圖卻被 line 90 rmtree 丟棄、改賴 server 端
  `{task_id}/original/auto/images` scp。前一份報告 fact：GCP 最新目錄
  比本次跑早 12h、MinerU log 無 POST /file_parse。→ 是「server 端不再
  落地 / 連到的不是該 MinerU」這個**部署事實**變了，碼沒變。

**排序 2（需排除，非碼回歸）：doc_type 路徑差異。**
- 用戶記得能看圖的是「環義**新聞**」，現在沒圖的是「800-vdc（academic）」。
  `_stage_pdf_to_md`：`doc_type=='slides'` 走 SlidesProcessor
  （PyMuPDF+Gemini，**完全不用 MinerU scp**）；news/web/academic 走
  MinerU。若舊「環義新聞」當時被當 slides 或當時 MinerU server 端仍落地，
  圖自然有；800-vdc 走 MinerU scp 即踩中脆弱路徑。**這是路徑/時點差異，
  非 4.5/4.6 改動。**

**排序 3（已排除）：Stage A fitz 干擾。**
- 反證：三 fitz 函式全 `finally close`、render 純記憶體不落地、無 cwd/env
  /SSL 副作用（B、C）。即使 Stage A 整段失敗也 soft（不中止、不影響圖）。

**排序 4（已排除）：pdf_processor 重命名。**
- 反證：b912a71 即 original.pdf ⇒ `paper_name`==`mineru_name`==`"original"`，
  前後解析路徑 byte-identical。NFKC 只動 md 字串。

**排序 5（已排除）：paper_manager/models/Stage B。**
- 反證：純 DB / 純讀已落地 md；upsert 時 _tmp 早沒了；同執行緒無 race。
