## 真因

Commit 10 回退多檔上傳時把 `setBusy(true)` 的 lock 範圍保留為「整個 pipeline 跑完」（trackProgress done 才 unlock）。

baron 觀察：上傳 800-vdc 後跑到 18%、想再上傳第二份、upload-btn 灰著點沒反應。

正確設計：
- 上傳完成（confirm_type 成功啟動 trackProgress）就立刻 unlock upload-btn
- 後端 thread pool 並行能力本來就有、不需要前端擋
- cleanup-btn 仍 lock 直到所有跑完（既有 `isProcessing` 邏輯保留）

---

## 修法

### 1. `setBusy` 拆解：upload-btn vs cleanup-btn 分開鎖（L1757-1763）

`setBusy` 之前同時 lock upload-btn 與 cleanup-btn。改為**只 lock cleanup-btn**：
```js
function setBusy(busy) {
  isProcessing = busy;
  document.getElementById('cleanup-btn').disabled = busy;
}
```
upload-btn 的 disabled 由各別上傳流程短期控制（見 2、3）。

### 2. upload-btn 短期 lock：只在「選檔 → upload API 回應」期間（L2419-2444）

- 進 handler 時 `btn.disabled = true; setBusy(true)`（既有）
- **`await fetch('/api/papers/upload', ...)` 回應後**、`showConfirmModal` 被呼叫之前：`btn.disabled = false; setBusy(false)`（新增）
- 失敗 catch 內既有 `btn.disabled = false; setBusy(false)`：保留

### 3. `showConfirmModal` 內 confirm 後不再 lock（L2554-2555）

- confirm-ok-btn handler 內 `btn.disabled = true`：**移除**
- 改為 comment 註明「上傳階段已在 upload handler 結束、使用者可獨立操作下一份」
- 失敗 catch 內 `btn.disabled = false; setBusy(false)`：保留（容錯路徑）

### 4. `trackProgress` 不動

`trackProgress` 內 done / error / onerror 既有：
```js
btn.disabled = false;
setBusy(false);
```
- `btn.disabled = false`：本 commit 後上傳階段已 unlock、此處 idempotent、保留為多重保險
- `setBusy(false)`：保留——它現在只控 cleanup-btn

**已知邊角 case**：cleanup-btn 應「所有 paper 都跑完」才 unlock，但 `setBusy(false)` 是 per-paper 觸發；多份同時跑時、第一份 done 會錯誤地解鎖 cleanup-btn。

**處理**：保守做法、本 commit 不重構。引入 `activePapers` 計數的事**留下次再做**——cleanup-btn 本來就是破壞性按鈕、使用者按下會跳 confirm 對話框、不嚴重。

### 5. Help modal 文案（L1069）

原：「每次只能上傳一份文件；如選多份會出現提示」
新：「每次只能上傳一份文件；如選多份會出現提示；上傳期間可繼續上傳下一份」

### 6. `design/docs/copywriting.md` §6.1.1 互動契約

加一段：「Phase 4.7d Commit 11：上傳完成（API 回應 + confirm modal 開啟）後 upload-btn 立刻解鎖、使用者可上傳下一份；pipeline 平行跑、無需等待。`setBusy` 只 lock cleanup-btn（破壞性按鈕、所有 paper 跑完才解鎖）；upload-btn 的 disabled 只在「選檔 → upload API 回應」極短期間 lock。」
