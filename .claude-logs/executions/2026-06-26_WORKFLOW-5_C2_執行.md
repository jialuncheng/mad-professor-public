## §4 修法說明（baton/README.md §2 改寫設計）

§2 由「階段 A/B/C」重構為三相交易，**每相對帳 WORKFLOW_SOP §3**：

1. **Phase 1 — Staging（暫存區寫入）**：發起方產出檔命名暫存 `baton/`；時機鐵律「Run 嚴禁 mv/git add、僅 Checkout 歸檔」（對帳 §3）；保留 baron 人類交接環節。
2. **Phase 2 — Deterministic Validation（歸檔前確定性自檢）**：在 `mv` 前逐項自檢，任一不過即暫停回報 baron（**靠執行期 SOP 查核、非提示詞自報**）。四維表格：
   - **Provenance**：檔名任務代號 + 元數據塊齊備、可回溯來源。
   - **Schema**：對應 template 必備章節齊備。
   - **Non-destructive**：目標路徑無同名既有檔 / 確認 append / 新版本命名；**嚴禁覆寫·截斷**。
   - **Scope**：歸檔目錄正確（依 WORKFLOW_SOP §2）。
3. **Phase 3 — Scoped Commit（驗證通過一次性歸檔）**：僅 Checkout 一次性 `mv` + `git add`（對帳 §3）；保留 `git mv` 禁令（baton gitignore→`fatal: bad source`）；保留 Audit Trail（_執行.md §7 寫 baton 檔名→hash 映射）。

頂部新增**非破壞性寫入核心鐵律**，並標明此為 WORKFLOW-5 三道防線中**唯一不可繞過**的保證（呼應 plan §1 Threat Model：截斷守衛可被 sentinel 繞過、DIRTY-RESET 僅 observable，唯本 3-Phase 在 mv 前確定性驗證）。

**邊界**：僅改 §2 + §99.2；§1 暫存隔離原理、§99.1 治理規格表本體未動；C6 將另追加「跨環境部署 SOP」段（本 commit 不碰）。
