## 4. 真因分析（依框架 §3）

### 為什麼 textarea 改 contenteditable 是必要的？

**真因**：原 `<textarea>` 不支援 inline HTML 元素（如藍色 token span）、所有內容只能是純文字。Claude `/skill` 風格 token 必須是 DOM 元素（`<span contenteditable="false">`）才能：
- 被 Selection API 跳過、Backspace 一次刪整顆
- 用 CSS 顯示為一整塊原子（藍底白字 + × 按鈕）
- 跟周圍純文字混排但視覺區隔

`contenteditable div` 是業界標準解（Slack / Discord / Notion 對話框、Claude 全採用此模式）。

### 為什麼 §3.3.5 四點防護必做？

**真因（依 plan v2）**：v1 plan 漏列下列細節、實作時必爆 UX：

1. **§3.3.5-#1（placeholder）**：contenteditable div 沒有原生 `placeholder` 屬性、僅用 `data-placeholder` 不會顯示 → 用戶看到空白方塊
2. **§3.3.5-#2（disabled）**：`disabled` 屬性對 div 無效、paper 未載入時用戶仍能輸入 → 體驗破碎
3. **§3.3.5-#3（grep 替換）**：`chatInput.value` 對 div 永遠回 `undefined`、`chatInput.disabled = true` 對 div 是 no-op → submit 永遠送空字串 + 禁用態失效
4. **§3.3.5-#4（dropdown 定位）**：若綁 cursor 座標、會撞三個邊界問題（右側溢出 / 底部截斷 / 多行抖動） → autocomplete 視覺破裂

四點全採納並落地、`tests/test_phase2_p2_3_hashtag_token_ui.py` 9 個 pytest 中 5 個直接 grep 驗證這 4 點防護存在。

### 為什麼 autocomplete 來源用前端 cache 而非新 API？

**真因**：
- 前端已有 `allPapers` cache（`/api/papers` 一次 GET 載入、之後 client-side filter）
- 每次輸入 `#` 都呼叫新 API 會增加網路延遲 + 後端壓力
- user_tags 規模小（< 1000 個 distinct tag）、前端遍歷成本可忽略
- Q9 plan 推薦答案明確：**前端 cache**

副作用：autocomplete 來源跟 PATCH 寫入有時序差（新加的 tag 要重新 `loadPapers()` 才出現）。本期不修、未來若用戶頻繁加 tag 再加 hot-reload hook。

### 為什麼 collectAllUserTags 防禦雙 field shape？

**發現的既有 Phase 1 inconsistency**：
- 後端 `_to_dict` 序列化為 `'metadata'` key
- 前端某些既有 R2 程式碼讀 `p.metadata_json.user_tags`（PATCH save 後 local 寫入的 shape）
- 兩個 shape 並存、不修也能 ship Phase 1 R2

依禁區「Phase 1 R1/R2/R3 ship 範圍：100% 不動」、本 P2-3 **不修 Phase 1 既有 inconsistency**、而是在 P2-3 新 `collectAllUserTags` 內**防禦讀兩個鍵**（union），保證 autocomplete 在任何時序下都能取到 user_tags。這是純加法、不破壞既有行為。
