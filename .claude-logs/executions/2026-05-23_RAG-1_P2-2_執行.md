## 4. 真因分析（依框架 §3）

### 為什麼之前跨多 paper 查詢做不到？

**真因**：既有 `rag_retriever.retrieve_with_context(owner_id, query, paper_id, top_k)` 簽名綁定**單一 paper_id**、`AI_professor_chat._get_rag_context` 也是傳單一 `effective_paper_id`。整條路徑沒有「同時對 N 篇 paper 做 FAISS 檢索並合併」的入口。

Phase 1 ship 後 `metadata_json.user_tags` 已有完整 tag 資料、但**沒有 dispatcher** 把 user 的 hashtag 翻譯成 paper_ids 集合 + 餵到多 paper retriever。P2-2 補這條缺漏的「user_tags 集合 → paper_ids → 多 paper Merge-Sort context」管道。

### 為什麼用 Merge-Sort 而不是各 paper 等比例取 N/k？

依 Hashtag Backend Plan + MODEL-1+2 B2 ship：L2 normalize 後 FAISS `similarity_search_with_score` 回 cosine similarity（`MAX_INNER_PRODUCT` 距離度量）、**跨 paper score 可比**。等比例配額會稀釋強匹配的 paper（譬如 paper A 有 5 個高分 chunk、paper B 全是低分）。全域 Merge-Sort 讓「最相關的 7 個 chunk 不論來源」進 context、grounding 更精準。

### 為什麼用 `cleaned_query` 而非原 `query` 送 LLM？

原 query 含 `#hr ` 前綴是視覺糖、router prompt 跟 character prompt 看到 `#` 會把它當特殊 token 解讀（誤判 doc_type / 走錯分支）。`parse_query_hashtag` 切 `#hr` 後剩餘 query 才是真實意圖、送 LLM 跟 retriever 都用 cleaned 版、結果更穩定。

### 為什麼多篇走多 retrieve、單篇走既有單篇路徑而非統一走多 retrieve？

統一走 multi 會破壞 P2-1 / R1 子項 F 的中文 abstract / `_get_macro_context` / `page_content_analysis` 三條路徑的單篇優化（這些路徑依賴 `effective_paper_id` 與 `effective_paper_data`）。Plan §3.2.4 明確分流：單篇 hashtag = 替換 paper_id 後跑既有路徑、多篇 hashtag = 走新 multi 直跑 LLM。這樣既有單篇行為對單篇 hashtag 100% 保留、多篇才走新路徑、最小破壞面。
