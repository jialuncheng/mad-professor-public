## 修法

### 1. 新增 `prompt/doc/heading_fix_resume.txt`（19 行）

格式與既有 `heading_fix_academic.txt` 對齊：
- `{headings}` placeholder（位置與 academic 一致）
- 輸出 JSON 格式：`{"行號": 數量, ...}`
- 規則分四層 #/##/###/####

履歷專屬規則：
- `#`：人名 / "Resume" / "CV" / "個人簡歷"（履歷主標題）
- `##`：Working Experience / Education / Skills / Projects / Publications / Awards / Certifications / Languages 等頂層分區
- `###`：每段工作（公司名 / 職稱）、每個學位（學校名）、每個專案——**彼此平行**
- `####`：單一公司內部子標題（職責分區 / 子模組 / 晉升軌跡 Role 1/Role 2）

新增「關鍵注意」三條，明確覆蓋 DeHunt 履歷的 bug：
- 公司名 / 學校名 / 專案名彼此一律平行
- **絕不**把後出現的公司判為前一個的子節
- 無法判斷時優先給 ###（保守維持平行 > 錯誤巢狀）

### 2. `processor/doc_analyzer.py:22`

```diff
-    'resume':    'prompt/doc/heading_fix_academic.txt',  # Phase 1 reuse academic
+    'resume':    'prompt/doc/heading_fix_resume.txt',  # Phase 4.7d RAG-7b：履歷專用 prompt
```

### 3. 為何 `STRUCTURE_PROMPTS['resume']` 不動

依 baron Q3 決議：`STRUCTURE_PROMPTS['resume']`（L34）**留下次**處理。

理由：
- structure 階段只決定章節 hierarchy + 內容摘要、不直接決定 # 數量
- DeHunt 履歷 bug 真正源頭在 heading_fix（# 數量錯）、structure 是繼承 heading_fix 結果
- 先驗證 heading_fix prompt 是否真能解、避免兩個變因同改後找不到貢獻者
- 若 7b 驗收後 structure 仍有 resume 特性問題，再開 RAG-7c 補 `structure_resume.txt`
