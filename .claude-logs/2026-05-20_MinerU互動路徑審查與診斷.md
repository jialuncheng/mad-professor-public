## 核心結論（先講）

**「task_id 抓到但 GCP 無對應目錄」不是圖片遺失的真正阻因，而是症狀。**
MinerU 以 `response_format_zip=true` 同步回傳的 **ZIP 內本來就含 images**
（`<stem>/auto/images/*`）。`process()` 解壓到 `_tmp`、只搬走 `.md`、
**line 90 `shutil.rmtree(_tmp)` 把含圖的 `_tmp` 整包刪掉**，再改去 server 端
`MINERU_OUTPUT_DIR/{task_id}/.../images` 用 scp/copytree 另抓一次。一旦
server 端不存在該目錄（本部署即如此）→ 圖片全失，**即使圖片剛剛就在手上的
ZIP 裡**。dry-run 情境 d 已完全重現此鏈（見下 D）。

→ task_id / GCP 目錄存不存在，對「能否拿到圖」其實無關緊要：可靠來源是
已下載的 ZIP，現行碼卻把它丟了。GCP 無目錄只是讓「備援的 scp 路徑」也失敗。

## A. `pdf_processor.process()` 邏輯審查（line 34–102）

| 步驟 | 行為 | 風險 |
|---|---|---|
| 送 PDF | `requests.post(MINERU_API_URL, files={"files":(pdf_path.name,f,"application/pdf")}, data={return_md,response_format_zip:true,backend:pipeline}, timeout=300)` | 同步、單請求；`pdf_path.name` 一律 `original.pdf` |
| 狀態碼 | `status_code != 200` → `RuntimeError` raise | 4xx/5xx 會中止 pipeline（情境 c） |
| task_id | `response.headers.get("x-mineru-task-id")`；無則 WARNING、`task_id=None` | **此 header 非 upstream opendatalab MinerU web_api 內建**（待實證，見 E-H5） |
| 解析回應 | `response.content` 當 **ZIP** bytes：`zipfile.ZipFile(io.BytesIO(...))` → `extractall(out/_tmp)` | response **是 ZIP 不是 JSON**（因 `response_format_zip=true`） |
| 取 md | `tmp_md=_tmp/{mineru_name}/auto/{mineru_name}.md` → rename 到 `out/{paper_name}.md` | `tmp_md` 不存在則**不 rename**，後續 `read_text` 直接 raise（情境 b） |
| 取圖 | `_copy_images(out_dir, task_id)` —— **不從 `_tmp` 取**，改 scp/copytree server 端 `{task_id}` 路徑 | **致命設計點**：手上 ZIP 已含圖卻不用 |
| 清理 | `shutil.rmtree(out/_tmp)` | **把 `_tmp/原/auto/images/` 連同證據一起刪** |

關鍵：**response 是 ZIP；ZIP 解到 `out/_tmp`；`_copy_images` 卻不碰 `_tmp`，
而去遠端 `MINERU_OUTPUT_DIR/{task_id}/{original}/auto/images/` 另撈。**
md 與 images 在 ZIP 內是兄弟目錄（`{stem}/auto/{stem}.md`、
`{stem}/auto/images/`）——程式自己的 `tmp_md` 路徑就證明作者知道 ZIP 結構，
卻只取 md。

## B. 「上傳檔名」相關（grep `files=|filename|name=`）

- 唯一送出點 line 49：`files={"files": (pdf_path.name, f, "application/pdf")}`。
- `pdf_path` 來自 web_server.py:276 恆為 `…/original.pdf` → multipart filename
  恆為 `original.pdf`。
- **MinerU 端據此 filename stem 命名 ZIP 內子目錄 = `original`**，故
  `_tmp/original/auto/{md,images}`。與本次 Phase 4.6 引入的
  `MINERU_PAPER_NAME="original"` 一致——即「正確的圖來源」就在
  `_tmp/original/auto/images/`，命名完全可預測、零猜測。

## C. `response.headers` / `task_id` 使用與理論驗證（grep）

使用點：line 58（status）、61（抓 task_id）、87（傳入 `_copy_images`）、

「MinerU 處理失敗時會怎樣？」理論 + dry-run 實證：

- 推論：**若 800-vdc 的 markdown 有產出、pipeline 有往後跑（user 只缺圖、
  非整篇失敗），代表 MinerU 並非「處理失敗」——它成功回了含內容的 ZIP。**
  這直接弱化「MinerU 失敗回假 task_id」假設（見 E-H1）。

## E. 根因假設（佐證 / 反駁）

**H1：MinerU 處理失敗但回 200 + 假 task_id**
- 佐證：fact #8 無 POST log、fact #3 無目錄。
- 反駁（強）：失敗→ZIP 空/500→情境 b/c→`process()` **會 raise、pipeline
  整篇中止**。但 user 症狀是「只缺圖、markdown/後續正常」⇒ ZIP 非空 ⇒
  MinerU **解析成功**。**H1 基本排除**（除非 800-vdc 其實整篇失敗——D 節
  指標題：先確認 markdown 有沒有產出）。

**H2：ZIP 解壓成功（本地 md 有），但 MinerU server 端根本不落地 / 落地到別處 / 被清**
- 佐證：=情境 d，與**所有** fact 一致（md 有、圖無、ZIP 本含圖、fact#3 無
  目錄、fact#4 /srv 12h 沒變、fact#8 那台 GCP MinerU 沒收到 POST）。
- 反駁：無實質反駁。**最強假設。** 機制可能是：該 MinerU 以 zip 同步回傳
  為主、不持久化到被檢視的 `/srv/mineru-output`；或落地在 container 內
  ephemeral 路徑（≠ bind mount）。

**H3：SSH tunnel 只 forward 8000，scp 走 22 沒通（從 web_server container 內）**
- 佐證：fact #5 手動 scp 成功**可能是在 host 跑、非 container 內**；container
  內可能無 22 路由/金鑰。
- 反駁：scp 失敗會 log `圖片複製失敗: <stderr>` 或 returncode≠0，且**不會**
  造成 fact #3「GCP 無此目錄」（scp 不建/刪 server 目錄）。最多是 H2 之後
  的次要放大因子，非主因。需 G 指令 #7 驗 container 內 scp 可達性。

**H4'：web_server 連到的 MinerU ≠ 被檢視的 GCP MinerU（兩個 endpoint / localhost:8000 在 container 內不是那條 tunnel）**
- 佐證：fact #8（那台 GCP MinerU 無 POST log）、fact #4（其 FS 沒動），但
  API 仍回 200+task_id+**有效 ZIP**——表示「回應方」與「被檢視方」可能不是
  同一台/同一 FS。
- 反駁：需「回應方」能真的解析 800-vdc 出 ZIP（非隨便服務做得到）⇒ 若成立，
  代表另有一台真在跑的 MinerU。與 H2 並列、常一起成立（回應方不落地到被檢視
  的 /srv）。需 G 指令 #4/#6 釐清 endpoint 身分。

**H5：`x-mineru-task-id` 非 upstream MinerU header（task_id 來源存疑 / 別層注入 / 此為 fork）**
- 佐證：opendatalab/MinerU `projects/web_api` 同步 `/file_parse` 印象中**不發**
  此 header；若真無 → `task_id` 恆 None → 走 `ls -t` fallback（非現觀察）。
- 反駁：user 確有抓到 `6a30a9b8…`（UUID4 風格）⇒ 此 MinerU 為**有 task 概念
  的 fork**，或前層（gateway/uvicorn proxy）注入。**但無論哪種，task 目錄
  ≠ `MINERU_OUTPUT_DIR` 即重現 H2/情境 d。** 需 G 指令 #1 dump 全 headers
  證實 header 真實性與來源。

**H6：MinerU 落地在 container 內 ephemeral 路徑，非 bind-mount 到 /srv/mineru-output**
- 佐證：API 正常回 ZIP，但 fact #4 /srv 12h 未變、fact #3 無 dir。
- 本質是 H2 的具體機制之一。需 G 指令 #5 看 MinerU 啟動參數的 output dir。

**綜合最可能**：**H2（+H4'/H6 為其機制） + 設計缺陷（A/D 節：丟棄 `_tmp`
內 ZIP 自帶的圖、改賴脆弱的 server 端 scp）。** task_id/GCP 目錄之爭對
「拿圖」是假議題——可靠來源（ZIP）被現行碼主動丟棄。

## F. 下一步診斷指令（不修碼，OrcStack 可跑，能用 log/FS 判真因）

> 目標排序：先證「ZIP 是否本就含圖」（一刀斃命）→ 再證 endpoint 身分 →
> 最後才查 server 端落地/scp。

**F1（最高優先，單指令定生死）— 從 web_server container 內手動 curl 重現，看 ZIP 內容**
```
docker exec <web_server_container> sh -lc '
  curl -sS -D /tmp/h.txt -o /tmp/m.zip \
    -F "files=@<該 paper 的 original.pdf 絕對路徑>;type=application/pdf" \
    -F return_md=true -F response_format_zip=true -F backend=pipeline \
    "$MINERU_API_URL";
  echo "---HEADERS---"; cat /tmp/h.txt;
  echo "---ZIP SIZE---"; wc -c /tmp/m.zip;
  echo "---ZIP LIST---"; unzip -l /tmp/m.zip | grep -E "auto/(images|/)" || unzip -l /tmp/m.zip'
```
判讀：`unzip -l` 若見 `original/auto/images/*.jpg` → **證實 H2/情境 d：圖
本就在 ZIP，現行碼丟掉**（修復方向＝改從 `_tmp` 取圖、勿 rmtree 前搬走；
此處不寫碼）。若 ZIP 無 images 或 size 極小 → 走 H1（MinerU 真沒出圖）。
`cat /tmp/h.txt` 同時回答 H5：`x-mineru-task-id` 是否真存在、值為何、
有無 `server`/`via` 等 proxy 標頭（H4'）。

**F2 — 確認回應方 endpoint 身分（H4'）**
```
docker exec <web_server_container> sh -lc '
  echo "API=$MINERU_API_URL HOST=$MINERU_HOST OUT=$MINERU_OUTPUT_DIR";
  curl -sS -o /dev/null -w "docs=%{http_code} ip=%{remote_ip}:%{remote_port}\n" \
    "$(echo $MINERU_API_URL | sed s,/file_parse,/docs,)";
  curl -sS "$(echo $MINERU_API_URL | sed s,/file_parse,/openapi.json,)" | head -c 400'
```
判讀：`remote_ip` 是否真指向 GCP MinerU；openapi 是否含 `/file_parse` 且
是否標示 task/async（辨別 fork vs upstream，呼應 H5）。

**F3 — 把 F1 抓到的 task_id 在被檢視的 GCP 上全域追蹤（H2/H4'）**
```
# 在 GCP MinerU 主機：
T=<F1 headers 內的 task_id>
docker logs <mineru_container> 2>&1 | grep -i "$T" || echo "MinerU log 無此 task"
sudo find /srv/mineru-output -maxdepth 3 -iname "*$T*" -o -newermt "today 21:00" 2>/dev/null
docker logs <mineru_container> 2>&1 | grep -i "POST /file_parse" | tail -5
```
判讀：log 完全無此 task 且無近時段 POST → **回應方 ≠ 這台 GCP MinerU**
（H4' 成立，去 F2 的 `remote_ip` 追真正那台）。

**F4 — 確認那台真 MinerU 的落地目錄（H2/H6）**
```
# 在「真正回應的」MinerU 主機（可能就是 F2 remote_ip）：
docker inspect <mineru_container> --format '{{json .Mounts}}' | python -m json.tool
ps -ef | grep -i mineru-api    # 看 --output / 工作目錄參數
# 上傳當下另一視窗：
sudo inotifywait -m -r -e create --format '%w%f' /srv/mineru-output &
```
判讀：Mounts 是否真 bind `/srv/mineru-output`；inotify 在 upload 時有無
新建 → 證實「server 端到底落不落地、落哪」（H2 vs H6）。

**F5 — container 內 scp/22 可達性（H3，次要、僅排除放大因子）**
```
docker exec <web_server_container> sh -lc '
  ssh -o BatchMode=yes -o ConnectTimeout=5 "$MINERU_HOST" \
    "echo SSH_OK; ls -d \"$MINERU_OUTPUT_DIR\" && ls -t \"$MINERU_OUTPUT_DIR\" | head -3" \
  || echo "container 內 SSH/scp 不可達 → 遠端模式取圖本就不可行"'
```
判讀：若不可達 → 即使 server 端有目錄、本部署遠端取圖路徑亦無效，更印證
「應改用手上 ZIP」方向（H2 結論不變，H3 為附帶）。
