baron 連續上傳多份 paper 後出現「Server disconnected without sending a response.」、retry 沒救起來、3 份新 paper 全部跑壞變殘檔。

### 觀察 A：retry 詞表漏 'disconnect'

## 修法

### A. llm/retry.py — 補 retryable token

`_RETRYABLE_TOKENS` 加入 6 個新 token：

```python
'disconnect',         # httpx「Server disconnected without sending a response.」
'remote protocol',    # httpx.RemoteProtocolError
'protocol error',     # 部分變體
'incomplete read',    # 串流中斷
'closed',             # connection closed
'reset',              # connection reset by peer
```

`_is_retryable` 演算法不變（字串子串匹配）；只擴詞表。

### B. llm/client.py — 全域 LLM 並發 Semaphore

新增 class-level Semaphore：

```python
class LLMClient:
    _instance = None
    _lock = threading.Lock()
    _api_semaphore = threading.Semaphore(LLM_MAX_CONCURRENT)  # 預設 6
```

3 個 method body 全用 `with LLMClient._api_semaphore:` 包：

- `chat`：method body 全段縮排進 with
- `chat_with_image`：同
- `chat_stream_by_sentence`：**整個 generator body**（含 inner functions `_build_config / _collect_sources / _run` 與末段 `yield from _run(...)`）

### settings.py — 新 env var

```python
LLM_MAX_CONCURRENT = int(os.getenv("LLM_MAX_CONCURRENT", "6"))
```

預設 6；env override 可調整（如付費 Tier 拉高到 12）。

### tests/test_llm_retry.py — 補 3 個測試

- `test_is_retryable_disconnect`：「Server disconnected ...」應 retryable
- `test_is_retryable_protocol_error`：`httpx.RemoteProtocolError` / `Protocol Error` 變體
- `test_is_retryable_reset`：`connection reset by peer` / `Connection closed`

Semaphore 行為涉及多執行緒、本 commit 不加單測；靠 integration test（手動）驗證。

## Semaphore 持有期分析

| 階段 | 是否持有 lock | 說明 |
|---|---|---|
| `wrapper` 進入（retry_call / retry_stream） | ❌ 無 | wrapper 在 fn 外、進 fn 才 acquire |
| `fn` 進入、執行 `with LLMClient._api_semaphore:` | ✅ acquire | 進 with block |
| LLM API call（generate_content / stream） | ✅ hold | 包在 with 內 |
| `chat_stream_by_sentence` 的 yield | ✅ hold（**caller 拉完才釋放**） | with 包含 yield、generator lifetime |
| fn 內部例外、退出 with | ❌ release | with 自動釋放 |
| `wrapper` 內 `time.sleep(delay)` | ❌ no lock | sleep 在 fn 外、lock 已隨例外釋放 |
| 重試下一次進 fn | ✅ acquire | 重新進 with |

**關鍵**：retry 期間 sleep **不持有 lock**——sleep 在 `wrapper` 外層 catch block 內、`fn` 已退出 with、lock 已釋放。其他 thread 可在 sleep 期間取得 lock 進場。這正是 §5 plan 設計的點。

**chat_stream_by_sentence 邊角 case**：generator 若 caller 拉到一半就丟棄（沒 close / 沒 exhaust），lock 要等 GC 才釋放——可能導致 lock 滯留。緩解：caller 端用 `for ... in ...:` 完整迭代或顯式 `gen.close()`；既有 caller `process_query_stream` / `chat_stream_by_sentence` 都是完整迭代、不會卡。
