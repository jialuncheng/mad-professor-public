# 2026-05-20 Phase 4.7b：PDF 檔名 original.pdf → {paper_id}.pdf

只動 3 檔（web_server.py / paper_manager.py / scripts/diagnose_mineru.py）。
未動 Phase 4.7a DB schema（models.Paper 未加 original_filename）、未動
4.7c 前端、未動 pdf_processor 任何邏輯、未動 ai_core/rag_retriever、
未動 tests（採推薦方案 A）。

## 改動

### A. paper_manager.original_pdf_path（新規範 + 向後相容）
回傳優先序：`{paper_uuid}.pdf` 存在 → 新；否則 `original.pdf` 存在 → 舊；
皆無 → 回新規範路徑（供上傳寫入）。既有 DB 8 篇舊資料（原 original.pdf）
照舊可讀；新上傳一律新命名。

### B. web_server.py:276 上傳寫入
`paper_dir / "original.pdf"` → `paper_dir / f"{paper_id}.pdf"`。
`paper_id` 已由 `sanitize_paper_id` 清過（`[^\w\-]→_`），無特殊字元風險，
與資料夾名一致。

### C. scripts/diagnose_mineru.py（dry-run 工具同步）
- `make_zip` docstring：原註解「本系統一律上傳 original.pdf 故 inner=
  original」已過時且推理錯誤；改為正確說明——4.7b 後上傳檔名為
  {paper_id}.pdf，但 MinerU 端 inner 由 `MINERU_PAPER_NAME`（固定
  "original"）**解耦**，故 inner 仍 'original'（不受 4.7b 影響）。
- 合成 PDF `tmp/"original.pdf"` → `tmp/f"diag-{name}.pdf"`，反映新命名
  慣例（檔名 = sanitize 後的 paper_id 風格）。`name` 為 run_scenario 首參，
  作用域內可用。對 dry-run 無功能影響（pdf_processor 僅用 stem 命名本機
  md；MinerU 端 inner 由 make_zip 的 "original" 決定，與此檔名無關）。

### C-tests（採推薦方案 A，**不改 tests/**）
`tests/test_metadata_extractor.py` 的 real-PDF 路徑硬編 `…/original.pdf`
（line 186/187/291）為 conditional-skip，且其指向的是**既有舊資料**
（800-vdc/kahneman），舊資料經向後相容 fallback 仍命名 original.pdf →
保留 "original.pdf" 才是正確測舊資料、且既有行為不變（本環境仍 skip）。

`original_pdf_path` 四情境（臨時目錄實測）：
| 情境 | 目錄內檔案 | 回傳 | 預期 | 結果 |
|---|---|---|---|---|
| 舊資料（如 800-vdc）| `original.pdf` | `original.pdf` | 舊路徑 | ✓ |
| 新上傳 | `{uuid}.pdf` | `{uuid}.pdf` | 新路徑 | ✓ |
| 遷移期並存 | 兩者 | `{uuid}.pdf` | 優先新 | ✓ |
| 上傳前（web_server 取寫入路徑）| 無 | `{uuid}.pdf` | 新路徑 | ✓ |

→ 既有 DB 8 篇舊資料**零遷移**即可正常讀取；新上傳走新命名；無破壞。
