# 2026-05-19 文件資料夾結構功能 設計分析（純設計，未改任何程式碼）

## A. 現有 schema 是否滿足需求
models.py 實況：
- Folder：id / owner_id(FK users, RESTRICT) / parent_id(FK folders, **CASCADE**, nullable) /
  name(255) / sort_order(int, default 0) / created_at；UNIQUE(owner_id,parent_id,name)；
  Index(owner_id,parent_id)。
- Paper.folder_id：FK folders **ON DELETE SET NULL**，nullable（NULL=根/未分類）；Index(owner_id,folder_id)。
- 行為：刪 folder → 其 papers folder_id SET NULL（論文回根，不刪）；
  刪 parent folder → child folder CASCADE（子資料夾整棵刪）；其內論文因 SET NULL 回根（不丟）。

結論：**schema 已足夠**支撐「巢狀資料夾 + 一對多論文歸屬 + 排序」MVP，不需改 models.py。
缺的欄位（icon / color / description）皆 **非 MVP 必要**；要做屬日後 additive nullable 欄 + Alembic migration。
is_collapsed 屬 UI 狀態，**不入 DB**（前端 localStorage 記憶）。

⚠ 既知 schema 邊界（沿用 Phase 0 標註）：UNIQUE(owner_id,parent_id,name) 在 SQLite 中
parent_id 為 NULL 時多個 NULL 視為相異 → **根層同名資料夾不會被 DB 擋**，需 API 層自行檢查。

## B. 功能需求釐清（建議定案）
1. 基本操作：建立(在根或某 parent)、改名、移動(改 parent)、刪除(論文回根、子資料夾連帶刪)。
2. 論文互動：建立論文預設無資料夾(根)；可移到某資料夾；可移回根(folder_id=null)。
3. 階層深度：parent_id 遞迴技術上無限；**建議 API 軟上限（如 5 層）**並 UI 用「filter 模型」
   （見 D）避免窄面板縮排爆掉。
4. 一篇多資料夾：現 schema 單值 folder_id＝**一對多**。多對多需中介表＝Phase 4+，MVP 不做。
5. 拖曳：HTML5 drag 可行但 260px 窄欄 + 可收合 + 行動裝置體驗差。**MVP 不做拖曳**，
   改用論文列「移動到資料夾」選單；拖曳列為 Phase 3.3 增強。

## C. API 設計（建議）
- `GET /api/folders` → 當前 user 的資料夾樹 `[{id,name,parent_id,sort_order,children:[...]}]`
- `POST /api/folders` body `{name, parent_id?}` → 建立（API 層擋同層同名、parent 須同 owner）
- `PATCH /api/folders/{id}` body `{name?,parent_id?,sort_order?}` → 改名/移動/排序
  （移動需**防環**：新 parent 不可為自己或自身子孫）
- `DELETE /api/folders/{id}` → 刪除（DB 自動：論文 SET NULL、子資料夾 CASCADE）
- `PATCH /api/papers/{paper_uuid}` body `{folder_id?}`（null=回根）→ **新端點**
  （現無 PATCH /api/papers；改名暫不納入此端點，title 來自 rag_tree 非使用者可改，維持現狀）
- `GET /api/papers`：URL 不變，但每筆 dict **新增 `folder_id` 欄位**
  （paper_manager._to_dict 補 folder_id）。MVP **不做** server-side `?folder_id` filter，
  改前端 client-side 依 folder_id 分組（資料量小、少一次往返、實作簡單）；
  大量論文時再加 server filter（延後）。
所有 folder/paper 端點：沿用既有 `get_current_user` 依賴 + owner_id 範圍檢查（與 Phase 1.3 一致）。

## D. 前端 UI 設計（重點）

### 現有約束（已核對 index.html）
- `#sidebar` 寬 **260px**、`flex-direction:column`、可收合（`.collapsed{width:0}`）。
- 三段固定結構：`#sidebar h1`（48px 標題列）→ `#paper-list`（`flex:1; overflow-y:auto`，主捲動區）
  → `#sidebar-bottom`（上傳 + 清理按鈕，~68px）。
- `.paper-item` hover 顯示 `.delete-btn`（`opacity:0→1`）—— 既有「hover 出現操作鈕」慣例。
- Mies 極簡 token：細框、無陰影、accent≈近黑、active 反白。行動裝置側欄已很擠。

### 設計取捨：filter 模型 vs inline tree 模型
- **inline tree**（整棵樹常駐、論文巢狀縮排）：260px 寬下每層縮排吃掉可視寬，深層幾乎無法讀，
  論文標題（已 -webkit-line-clamp:2）會被擠爆。**不建議**作 MVP。
- **filter 模型**（推薦 MVP）：上方一塊精簡「資料夾區」，點資料夾＝選取並 filter；
  下方 `#paper-list` 只顯示「當前選取資料夾」的論文 + 一條 breadcrumb 可回上層。
  縮排需求最小、深度不破版、與既有「點 paper-item 開論文」互動一致。

### 推薦版面（單一捲動容器，不做上下分割雙 pane）
260px 垂直空間稀缺，**不要**硬切「上樹/下列表」兩個各自捲動的 pane。改為：
```
#sidebar h1                     ← 48px（不動）
#paper-list (flex:1, scroll)：
  ── 資料夾區（精簡，常駐頂部）──
  ▸ 全部            （pseudo，無 filter＝該 owner 全部論文）   ← 預設選中
  ▸ 未分類          （folder_id IS NULL）
  ▾ 研究            （真實資料夾，可摺疊；右側 hover ⋯ 選單）
      ▸ LLM
      ▸ 自由車
  ── 分隔線 ──
  ── 論文列表（當前選取資料夾）──
  [breadcrumb：全部 / 研究 / LLM]
  .paper-item ...
  .paper-item ...
#sidebar-bottom                 ← 上傳 + 清理 +（新增）新增資料夾
```
- 資料夾列樣式比照 `.paper-item`（padding/hover/active 同 token），左側 chevron `▸/▾`
  （收合狀態存 localStorage），右側 hover 顯示 `⋯` 選單（沿用 `.delete-btn` 的 opacity-hover 慣例）。
- 縮排：每層左 padding 階梯（如 depth×12px，視覺上限 ~3 階後不再加深），名稱 `text-overflow:ellipsis`。
- 「全部 / 未分類」為兩個固定 pseudo 節點置頂：
  - **全部**＝該 owner 所有論文（不論 folder_id）；MVP 預設選此（與現行為一致：現在就是列全部）。
  - **未分類**＝`folder_id IS NULL`（含處理中、剛上傳未歸檔者）。
- 操作 UI：
  - 「新增資料夾」：放 `#sidebar-bottom`，與上傳/清理同列的小 ghost icon 鈕（風格一致、不另佔高度）。
  - 資料夾 rename/move/delete：hover 出現 `⋯` → 輕量選單（重命名 inline input、刪除前確認
    「子資料夾將一併刪除，論文移回未分類」）。
  - 論文歸檔：`.paper-item` hover 既有區域加一個「移動」icon → 點開小 folder picker
    （`<select>` 或輕量選單，含「未分類」選項）。**MVP 不用拖曳**。
- breadcrumb：選到深層時頂部顯示 `全部 / 研究 / LLM`，點任一層回該層 filter；省去深縮排。

### 「全部」與處理中論文
- 剛上傳/處理中的論文 folder_id 預設 NULL → 出現在「全部」與「未分類」；
  「閱讀提前/問答延後」狀態（依 paper_uuid）與資料夾**完全獨立**，filter 不影響其進度/解鎖。
- 建議預設選「全部」以維持與現行體驗一致（使用者不會「東西不見了」）。

## E. 既有程式碼影響
- **models.py**：MVP 不需改（schema 已足夠）。
- **paper_manager.py**：新增 folder CRUD（list_folders 樹、create/rename/move/delete_folder）、
  `set_paper_folder(owner_id,paper_uuid,folder_id|None)`（驗證 folder 同 owner、移動防環）；
  `_to_dict` 補 `folder_id`。全部沿用 owner_id 範圍 + `_ensure_db` 模式。
- **web_server.py**：新增 /api/folders 4 端點 + PATCH /api/papers/{uuid}；
  皆掛 `get_current_user` + owner 檢查；GET /api/papers URL 不變（dict 多 folder_id）。
- **ai_core / pipeline_core / rag_retriever**：**零影響**（資料夾純 metadata，不入路徑）。
- **前端 index.html**：大改 —— loadPapers 改為「先取 folders 樹 + papers(含 folder_id)」、
  渲染資料夾區 + filter 狀態 + breadcrumb + 新 API 呼叫 + 新增/移動/刪除互動 +
  收合狀態 localStorage。

## F. 階段拆解（對齊需求）
- **Phase 3.1 後端 API**：paper_manager folder 函式 + web_server 端點 + GET /api/papers 加 folder_id +
  PATCH paper folder_id。可純 curl 測，無 UI。
- **Phase 3.2 前端基礎 UI（MVP 可用門檻）**：資料夾區（filter 模型）+ 全部/未分類 +
  新增資料夾 + 論文「移動到資料夾」picker + 資料夾 rename/delete + 收合 localStorage。
- **Phase 3.3 進階**：HTML5 拖曳移動、多層樹視覺優化、context menu、深度/RWD 細修。

## G. 風險與相依
1. 「閱讀提前/問答延後」：不受影響（status 邏輯依 paper_uuid，與 folder 正交）；
   需確保處理中論文仍可見（歸 全部/未分類），filter 別把它藏起來。
2. paper_uuid 路徑：folder **不入路徑**（`output/{owner_id}/{paper_uuid}` 不變）→
   移動資料夾＝純 DB folder_id 更新，**零檔案系統變動**（重大優點，低風險）。
3. UI 狀態：需 `selectedFolderId` + `expandedFolderIds`(localStorage)；與既有
   `paperReadiness` map / `loadPaper`(by paper_uuid) 正交，移動後僅需重抓列表。
4. 防環：移動資料夾到自身子孫須 API 擋；根層同名須 API 擋（SQLite NULL 不擋，見 A）。
5. 刪資料夾破壞性：子資料夾 CASCADE 刪除（論文 SET NULL 保留），刪除前 UI 必須明確警告。
6. RWD/行動：260px 已擠；filter 模型 + 縮排上限 + ellipsis + 既有可收合側欄為緩解。
7. cleanup 端點：`cleanup_orphaned` 掃 output/{owner}/ 對 DB papers，與 folders 無關
   （folders 無對應目錄），不受影響、安全。

## H. 推薦 MVP
**必做（Phase 3.1 + 3.2）**：
- 後端：folder CRUD、set_paper_folder、GET /api/papers 加 folder_id、防環/同層同名/owner 檢查。
- 前端：filter 模型資料夾區、全部/未分類 pseudo 節點、新增資料夾、論文移動 picker、
  資料夾改名/刪除（含警告）、收合狀態 localStorage。
- 可巢狀（schema 支援），UI 用 filter+breadcrumb 不受深度破版；建議軟上限 5 層。

**可延後**：
- 拖曳（3.3）、多層常駐 tree 視覺、icon/color/description（需加欄+migration）、
  一篇多資料夾（中介表，Phase 4）、server-side `?folder_id` 分頁（大量論文時再做）。

**優先級**：3.1（後端，必先；可獨立測試）→ 3.2（前端 MVP，達「可用」）→ 3.3（體驗增強，非阻塞）。

## 驗證/限制
- 純設計分析，無任何程式碼/設定變更。
- 結論基於實際 models.py（Folder/Paper schema、FK ondelete）與 index.html 側欄結構核對。
