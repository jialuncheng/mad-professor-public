## §1 TL;DR

- **問題與挑戰**：（1）四角色流程的 Claude Web 中介層冗餘；（2）文書類別命名飄移、職責不清、易重複；（3）四類修改場景（前端 vs 非前端 × 改版 vs hotfix）未明確分流、每次都讀全套文件浪費 token；（4）改版規劃書無標準格式、Antigravity / baron / Claude Design 寫出來各不一致；（5）文件無「改版規則 §0」、長大後冗餘無法整治
- **核心根因**：當前框架（PROJECT_PROGRESS_CONTROL_FRAMEWORK.md）只規範了 `_plan.md` / `_執行.md` / `_hotfix.md` 三個 template、但對「改版規劃書」與「工作流分類」「文件治理」「跨文件去重複機制」皆無強制約束、依賴人類記憶
- **設計解法**：
  - **流程層**：四角色 → 雙角色（Antigravity 規劃 + Claude Code 執行）+ Claude Design 按需召喚
  - **工作流層**：四類細分（前端改版 / 非前端改版 / 前端 hotfix / 非前端 hotfix）、每類獨立 SOP 子章節、Claude Code 依任務性質只讀對應子章節（節省 token）
  - **文書層**：四類文書（改版規劃書 / 執行計劃 / 執行報告 / hotfix 報告）+ 每類有強制定義（目的 / 約束 / 改版需求 / 不重複機制）
  - **格式層**：新增 `template_revision_plan.md`（改版規劃書標準格式）+ 既有 `template_plan.md` 加 §0 來源欄位
  - **命名層**：新增強約束命名規則（防止專案長大後混亂）
  - **約束層**：CLAUDE_CODE_ENTRY.md + WORKFLOW_SOP.md + 框架 §9 補充條款
  - **治理層**：所有文件強制加入「§0 改版規則」、可隨時刪冗 / 簡化舊流程 / 跟隨專案進程
  - **工具層**：評估開源知識管理工具（Logseq 推薦、AppFlowy / AFFiNE 次選、Obsidian / Foam 為加分項）
- **影響範圍**：
  - **新增**：`WORKFLOW_SOP.md`（流程主導手冊、4 個工作流子章節）+ `CLAUDE_CODE_ENTRY.md`（repo 根層）+ `template_revision_plan.md`（改版規劃書標準格式）+ `template_file_governance.md`（每份文件治理規格表）
  - **修改**：`PROJECT_PROGRESS_CONTROL_FRAMEWORK.md` 追加 §9 / `template_plan.md` 加 §0 / `template_execution.md` 加 §0 / `template_hotfix.md` 加 §0
  - **不動**：所有 SOP（logging / database）/ 既有 plan & 執行檔 / 提示詞歸檔機制 / TODO.md 結構

## §3 觀察到的問題與證據

### 問題 #1：Claude Web 提示詞中介層的冗餘性
- **證據**：`.claude-logs/prompts/INDEX.md` 內 80% 提示詞是重新包裝 PK 既有 SOP
- **影響**：baron round-trip 多 1 跳

### 問題 #2：取消 Claude Web 後、約束強度斷層
- **證據**：§2.4 表中 3 項依賴 Claude Web 提醒
- **緩解方向**：強制檔案入口（CLAUDE_CODE_ENTRY.md + 自我檢核）

### 問題 #3：文書命名飄移
- **證據**：`_可行性評估.md` / `_plan.md` / `_執行計劃.md` 三種並存、實質相同
- **緩解方向**：WORKFLOW_SOP §2 註明同義、不強制改名

### 問題 #4（v3 新增）：四類修改場景未分流、每次讀全套 SOP
- **證據**：
  - `BUG-F1` 是純前端、卻被 Claude Code 強制讀 database SOP（無用、浪費 token）
  - `LOGGING-1` 是純後端、卻被 Claude Code 強制讀 design/docs（無用）
  - hotfix 跟正式改版混在同一條 SOP 章節、判定條件分散
- **影響**：每次 session 讀 5+ 份 SOP、80% 跟當前任務無關、token 浪費 + 注意力稀釋
- **緩解方向**：四類工作流（§4.2）+ 每類獨立 SOP 子章節 + 入口檔指引「依任務性質讀對應子章節」

### 問題 #5（v3 新增）：改版規劃書無標準格式
- **證據**：
  - `2026-05-24_RAG-1_Bug_Fix_Report.md`（Antigravity 風格）
  - `model_optimization_blueprint.md`（自由文體）
  - `api_audit_and_performance_report.md`（純表格）
  - 三份格式不一、Claude Code 評估時容易抓不到關鍵欄位
- **影響**：執行計劃的可行性評估品質受規劃書品質牽制、且 baron 寫規劃書時無範本
- **緩解方向**：新增 `template_revision_plan.md`（§11）

### 問題 #6（v3 新增）：文件無改版規則、無法跟隨專案進程
- **證據**：
  - `PROJECT_PROGRESS_CONTROL_FRAMEWORK.md` 沒有「本框架自身的改版規則」
  - `2026-05-23_logging_SOP_手冊.md` 沒寫「未來如何更新本 SOP」
  - 文件越長越多、無清理機制、舊章節跟新章節邏輯衝突無處仲裁
- **影響**：3-6 個月後 SOP 累積 5000+ 行、Claude Code 讀不完、新流程無法簡化舊流程
- **緩解方向**：每份文件強制加 `§0 改版規則`（§15）

### 問題 #7（v3 新增）：文件間職責重複
- **證據**：
  - 框架 §4.1 寫了 `_plan.md` 8 章節
  - `template_plan.md` 也寫了 8 章節
  - 兩處同步維護、不一致風險高
- **影響**：改一處忘了改另一處、Claude Code 抓不準權威源
- **緩解方向**：文件治理規格表（§14、明確標註權威源 vs 引用方）

### 問題 #8（v3 新增）：缺少知識管理軟體支援
- **證據**：當前所有文件用純 markdown + 手動維護 INDEX.md / TODO.md、無雙向連結 / 標籤 / 圖譜
- **影響**：跨文件關聯靠人腦記憶、Claude Web 退場後尤其難維護
- **緩解方向**：評估 Logseq / AppFlowy / AFFiNE / 其他開源（§13）

### §4.2 [子改動 B] — 四類工作流細分（v3 核心新增）

每類工作流獨立一個 SOP 子章節、Claude Code 依任務性質只讀對應子章節：

```
WORKFLOW_SOP.md
├── §1 角色定義
├── §2 文書類別釐清
├── §3 強制觸發鏈（通用）
├── §4 四類工作流分流（v3 新增）
│   ├── §4.1 前端改版（FE-Refactor）
│   ├── §4.2 非前端改版（BE-Refactor）
│   ├── §4.3 前端 hotfix（FE-Hotfix）
│   └── §4.4 非前端 hotfix（BE-Hotfix）
├── §5 自我檢核五問
└── §6 違規後果
```

**四類定義表**：

| 工作流類別 | 觸發條件 | 必讀 SOP（精簡） | 強制 template | 典型範例 |
|---|---|---|---|---|
| **FE-Refactor**<br/>前端改版 | 改動 ≥ 10 行 + 涉及 `static/*` / `design/*` | WORKFLOW_SOP §4.1 + design/docs（依需求） | template_plan + template_execution | RAG-1 前端 / BUG-F1~F6 |
| **BE-Refactor**<br/>非前端改版 | 改動 ≥ 10 行 + 涉及 `*.py` / `tests/*` / `tools/*` | WORKFLOW_SOP §4.2 + logging SOP + database SOP（依需求） | template_plan + template_execution | MODEL-3 / MODEL-8 / LOGGING-1 |
| **FE-Hotfix**<br/>前端 hotfix | 改動 < 10 行 + 純 `static/*` + 無 schema 影響 | WORKFLOW_SOP §4.3 | template_hotfix | 視覺微調 / typo 修正 |
| **BE-Hotfix**<br/>非前端 hotfix | 改動 < 10 行 + 純 `*.py` + 無 schema/API 簽名影響 | WORKFLOW_SOP §4.4 | template_hotfix | bug fix 邊界處理 / NPE 修補 |

**判定流程圖**：
```
收到 baron 提示詞
       ↓
[判定 1] 改動規模 < 10 行 且 無 schema/API 簽名影響？
       ↓ Yes                          ↓ No
   進入 hotfix                    進入 refactor
       ↓                              ↓
[判定 2] 主要影響範圍是 static/* / design/*？
       ↓ Yes        ↓ No          ↓ Yes        ↓ No
    FE-Hotfix    BE-Hotfix    FE-Refactor   BE-Refactor
```

**Token 節省效益**：
- 既有：每次讀 5 份完整 SOP（框架 + WORKFLOW_SOP + logging SOP + database SOP + design/docs）≈ 20k tokens
- v3 後：FE-Hotfix 場景只讀框架 + WORKFLOW_SOP §4.3 ≈ 5k tokens（節省 75%）

## §8 推薦 Commit 拆分與順序（v3 移除工時、改以影響程度排序）

```markdown
## §0 改版規則與治理規格

| 維度 | 內容 |
|---|---|
| **目的（Purpose）** | 一句話：本文件存在的唯一原因 |
| **用途（Usage）** | 誰會讀 / 何時讀 / 讀後做什麼 |

| **約束事項（Constraints）** | 本文件嚴禁包含的內容（防止職責蔓延） |
| **改版觸發條件（Update Triggers）** | 什麼情況下需要動本文件 |
| **改版規則（Update Rules）** | 動的時候要遵守什麼（新增 Revision / 不覆寫舊內容 / 通知引用方等） |
| **刪除條件（Deletion Criteria）** | 什麼情況下本文件可被刪除（例如：已被新文件取代、所述功能已下線） |
| **重複機制防護（Duplication Guard）** | 跟本文件高度相關但職責不同的文件、本文件如何避免複寫它們的內容 |
```
